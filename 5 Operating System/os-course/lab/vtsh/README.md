## 1. 实验目标

开发**简单命令行解释器**，展示用户程序如何通过操作系统系统调用运行其他程序、传递参数和环境、等待结束、管理后台进程。

任务不是完整复刻 Bash，也不要求支持全部 POSIX Shell 语法。重点理解：

- 操作系统为什么需要 shell。
- 进程如何创建、结束。
- 父进程与子进程的区别。
- 参数和环境变量的传递。
- shell 如何取得程序退出码。
- 如何实现顺序、条件和后台执行。
- 信号、进程组、管道的工作方式。

指南刻意不提供完整实现。系统调用名称、算法步骤、输入示例和检查问题，用于帮助自行设计方案。

## 2. 任务组成

### 2. VTSH 功能

Shell 必须：

1. 用 C，或能通过 C API 直接执行系统调用的其他低级语言编写。
2. 显示输入提示符。
3. 按绝对路径运行外部程序。
4. 支持 `cd` 和 `exit`。
5. 向新程序传递参数和 shell 当前环境。
6. 正确等待子进程结束并取得状态。

按变体实现附加功能：

1. 使用 `|` 支持管道。
2. 使用 `&` 后台运行单个简单命令。
3. 支持指定逻辑运算符。
4. 限制所运行程序的指定资源。

## 3. 最小语法

基础版可采用以下模型：

- 命令由程序名和零个或多个参数组成。
- 单词由一个或多个空白字符分隔。
- `;`、`&&`、`||`、`&`、`|` 运算符两侧有空格。
- `&` 只用于没有其他运算符的单个简单命令。
- 错误或不完整语法产生清晰错误，不能令 shell 崩溃。

合法输入示例：

```text
/bin/echo hello world
printf one ; printf two
false && echo not-run
false || echo fallback
sleep 2 &
```

可以扩展语法，但必须在报告说明限制，并用测试验证。

## 4. 推荐架构

可分为四个逻辑部分：

1. **REPL**：提示、读取行、结束 shell。
2. **parser（解析器）**：把输入转换为命令、参数、运算符。
3. **executor（执行器）**：运行命令，应用逻辑运算规则。
4. **process manager（进程管理器）**：等待、保存后台任务、回收结束进程。

不必每个部分一个文件，但职责不能混杂。例如 parser 不应创建进程，信号处理函数不应解析新命令行。

建议先定义两个内部对象：

- **简单命令**：参数数组，第一个元素是程序名。
- **执行计划**：命令及其间运算符的列表。

后台任务还需要任务 ID、PID 或 PGID、原始命令文本、当前状态。

## 5. 分步开发指南

### 第一步：实现 shell 循环

每次迭代：

1. 交互运行时显示提示符。
2. 完整读取一行。
3. 去除末尾换行。
4. 跳过空行。
5. 交给 parser。
6. 执行解析得到的计划。
7. 显示下一个提示符前，检查已结束的后台进程。

建议只在标准输入连接终端时输出提示符，方便通过输入重定向自动测试。

`Ctrl-D` 不发送信号。输入缓冲区为空时，终端向程序报告 EOF。Shell 应结束循环、释放内存，并决定如何处理仍运行的后台任务；在报告说明该策略。

### 第二步：解析简单命令

先只支持程序名与参数，测试：空行、首尾空格、单词间多个空格、无参数命令、大量参数、过长输入行。

传给程序的参数数组必须以空指针元素结束。确定分配内存的所有者和释放时机。

不要从引号和替换开始；先可靠地运行简单命令。

### 第三步：运行一个程序

一般流程：

1. 父进程按指定变体（`fork` 等）创建子进程。
2. 子进程准备状态，再通过 `exec` 家族替换为外部程序。
3. `exec` 失败时，子进程输出诊断并立即结束。
4. 父进程保存 PID；非后台命令使用 `wait` 类函数等待。
5. 父进程将等待结果转为命令执行状态。

禁止使用 `system`、`popen` 或 `/bin/sh -c` 运行外部程序，因为任务要求自行开发 shell。

推荐错误约定：

- 找不到程序：状态 `127`。
- 程序存在但不能运行：状态 `126`。
- 创建进程失败：当前命令失败，但 shell 本身继续接收命令。

实现前阅读：

- [`fork(2)`](https://man7.org/linux/man-pages/man2/fork.2.html)、[`vfork(2)`](https://man7.org/linux/man-pages/man2/vfork.2.html)、[`clone(2)`](https://man7.org/linux/man-pages/man2/clone.2.html)。
- [`exec(3)`](https://man7.org/linux/man-pages/man3/exec.3.html)、[`execve(2)`](https://man7.org/linux/man-pages/man2/execve.2.html)。
- [`wait(2)` / `waitpid(2)`](https://man7.org/linux/man-pages/man2/wait.2.html)。
- [`_exit(2)`](https://man7.org/linux/man-pages/man2/_exit.2.html)。

### 第四步：传递环境

新程序应获得 shell 环境变量。用 `env` 或 `printenv` 检查。

### 第五步：正确处理结束状态

使用对应宏区分：正常退出、被信号终止，以及需要跟踪时的暂停/继续。

等待可能被 `SIGINT` 等信号中断，此时系统调用可能返回 `EINTR`。如果该信号不应结束等待，则处理后重新等待。

被信号终止的进程可用 `128 + 信号编号` 形成非零内部状态；执行器内必须统一约定。

## 6. 扩展

### 6.1. 管道

将前一程序的标准输出连接到后一程序的标准输入：

```text
printf hello | wc -c
```

相邻环节之间用 `pipe` 建立管道。创建子进程后，用 `dup2` 将所需端点连接到 `STDIN_FILENO` / `STDOUT_FILENO`。父子进程都应关闭不用的文件描述符。

常见挂起原因：父进程保留了写端，最后一个读进程收不到 EOF。先实现两个程序，再扩展到任意数量。父进程须等待前台管道中的全部进程；通常用最后一个程序的状态作为管道状态。

思考如何借助管道进一步实现文件重定向，如 `cat kek.txt lol.txt > idk.txt`，并测试。

### 6.2. 后台执行

遇到 `&`，父进程不作阻塞等待，保存任务信息，立刻显示下一个提示符。

后台子进程结束后仍必须回收。应周期性执行**非阻塞等待**：

- 显示提示符前。
- 处理输入行后。
- 若实现更完整的信号管理，则收到 `SIGCHLD` 时。

> [!NOTE]
> `SIGCHLD` 处理函数只做最少工作，复杂结构更新和打印最好放在主循环。
>
> 一个信号可能对应多个进程结束；必须持续检查，直到没有可取得状态的子进程。

### 6.3. 逻辑运算符

Parser 先分离命令和运算符，检测语法错误。Executor 保存最后一个**实际执行**命令的状态，再决定是否运行下一条：

- `;` 后总是执行。
- `&&` 后仅成功才执行。
- `||` 后仅失败才执行。

执行采用短路规则：若第一个操作数已决定结果，不计算第二个；被跳过的命令不创建进程，也不改变最后实际执行命令的状态。

| 运算符 | 行为 |
|---|---|
| `cmd1 ; cmd2` | 执行 cmd1，再无条件执行 cmd2 |
| `cmd1 && cmd2` | cmd1 成功才执行 cmd2 |
| `cmd1 \|\| cmd2` | cmd1 失败才执行 cmd2 |

退出码 0 表示成功，非零退出码或信号终止表示失败。除两条命令外，还应测试命令链：

```text
true && echo recovered && false
false ; echo no ; echo yes
false || false || echo recovered
```

### 6.4. 辅助资源限制

按教师指定扩展，为所运行的程序实施**资源限制**：

| 变体 | 限制 | 检查方法 |
|---|---|---|
| 1 | `RLIMIT_NPROC`：用户的进程/线程数 | 有限次创建子任务，验证拒绝 |
| 2 | `RLIMIT_NOFILE`：文件描述符 | 打开文件/套接字并保持，直到失败 |
| 3 | `RLIMIT_FSIZE`：单个文件大小 | 写入超过限制，检查文件大小与状态 |
| 4 | `RLIMIT_STACK`：栈大小 | 有控制的深递归，确保实际消耗栈 |
| 5 | `RLIMIT_AS`：虚拟地址空间 | 持续分配并保持内存，直到失败 |

使用 `getrlimit()` / `setrlimit()`；限制值应可配置。限制应作用于所运行程序，并被其后代继承，不要无故修改 shell 自身限制。见 `man 2 getrlimit` / `man 2 setrlimit`。

测试小型辅助程序：先给充足限制，再降低限制。验证实际操作被拒绝或信号终止，而不只是 `setrlimit()` 成功；确认 shell 继续工作。不要运行真正的 fork bomb。

Linux 细节和测试说明见下方附录 A。

## 7. 自行编写 Python 测试

测试是实验的一部分，不仅是评分手段。创建独立测试集，将编译后的 shell 作为子进程，通过 `stdin` 发送命令，读取 `stdout` / `stderr`。

推荐标准模块 `subprocess`、`unittest`，也可用 `pytest`。不要使用 `shell=True`，因为要测试自己的 vtsh，而不是系统 shell。

根据变体，至少覆盖：

1. 空行与 EOF。
2. 绝对路径程序。
3. 无参数与多参数。
4. 多余空格。
5. 自行设定的环境变量传递。
6. 不存在或不可执行的命令。
7. 错误语法不会终止 shell。
8. 零与非零退出码。
9. `;`、`&&`、`||` 每个分支。
10. 三条及以上命令链。
11. 后台命令不阻塞下一条。
12. 后台任务结束后不留 zombie（僵尸进程）。
13. 管道传递数据并收到 EOF。
14. `cd` 后的新命令在目标目录执行。
15. 资源限制有效。

## 8. 推荐实现顺序

不要一次实现全部功能。每步保存可运行版本并增加测试：

1. REPL 与 EOF。
2. 单命令 parser。
3. 绝对路径启动。
4. 等待与状态。
5. `;` / `&&` / `||`。
6. 管道 `|`。
7. `&` 与后台回收。
8. 资源限制。
9. 附加测试。

诊断可用 `strace`、进程树、记录模式的 `atop`、GDB、内存错误检查工具（sanitizer）。

即便只实现自己的变体，也要能解释 `fork`、`vfork`、`clone`、`exec`、`wait`、`pipe`、`rlimit` 的差别。

## 附录 A：Linux 资源限制

### 设置和继承

通常在 `fork` 后、`exec` 前的子进程中设定。后代创建时继承，`exec` 后仍保留；大多数限制按各进程分别计算，而不是把进程树加总。`RLIMIT_NPROC` 特殊，按真实用户计算。

限制有 **soft（软）**与 **hard（硬）**两个值。请弄清区别以及各自何时设定。设置时考虑 `getrlimit()` 取得的初始值。

检查设置错误。设置失败时，shell 应继续接收命令，不能无视限制去启动目标程序。

> [!WARNING]
> `vfork()` 后、`exec()` 或 `_exit()` 前，不能任意调用函数，包括 `setrlimit()`。该变体需通过 `exec` 启动独立包装程序，由包装程序设置限制并运行目标。
>
> `clone()` 需考虑内存和资源共享标志，不要未经查阅文档就套用 `fork()` 流程。

可通过 `/proc/<pid>/limits` 检查当前限制，见 `man 5 proc_pid_limits`。Shell 之外的实验可用 `prlimit`，见 `man 1 prlimit`。

补充材料：

- [`getrlimit(2)` / `setrlimit(2)`](https://man7.org/linux/man-pages/man2/getrlimit.2.html)：语义、继承、错误。
- Michael Kerrisk，《The Linux Programming Interface》，**Process Resources** 章。
- [cgroup v2 PIDs 控制器](https://docs.kernel.org/admin-guide/cgroup-v2.html#pid)：`pids.max` 限制整个 cgroup 及子 cgroup 的任务数，与 `RLIMIT_NPROC` 按 real UID 计数不同。
