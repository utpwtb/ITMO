# Лекция 3. 软件变更管理 / Управление изменениями

> **课程 (Course):** Введение в программную инженерию
> **日期 (Date):** 2019-2020 уч. год
> **来源 (Source):** Конспект лекций v1.4.0.pdf

---

## 📋 本讲概览 (Обзор лекции)

本讲聚焦软件工程中的变更管理流程。随着项目参与人数增加，变更数量呈雪崩式增长，必须通过规范化的流程来管理。内容涵盖变更管理的定义、动机、核心流程模型（从客户请求到验证闭环）、变更的关键属性以及相关的自动化支持系统（如版本控制工具的配合）。重点理解变更控制委员会的作用以及影响分析的必要性。

---

## 🎯 核心概念 (Ключевые понятия)

### 概念 1: 变更管理 / Управление изменениями

**定义 (Определение):**
> Управление изменениями — контролируемое, журналируемое обновление системы. Атрибуты изменения: идентификатор, дата, ответственный, описание, журнал изменения.
> **中文翻译：** 变更管理是对系统进行受控、可记录的更新。每个变更的属性包括：标识符、日期、负责人、描述以及关联的变更日志。

**解释：**
在大型项目中，同时修改多个组件几乎不可能，因此变更需要被分解成一系列单独的动作，每个动作被记录和跟踪。版本控制系统（例如 SVN、Git）就是实现变更记录的工具，它们可以帮助查看修改历史并评估对系统的影响。

**关键特性 / 语法 / 结构**
- 管理对象不仅包括源代码，还包括需求、缺陷、架构和设计工件
- 每个变更都拥有唯一的属性集，便于审计和回溯

---

### 概念 2: 变更管理流程模型

**定义 (Определение):**
> Модель процесса управления изменениями включает: запрос от заказчика → анализ менеджером → решение комитета → анализ влияния → планирование → реализацию → тестирование → верификацию.
> **中文翻译：** 变更管理流程模型包括：客户请求 → 项目经理分析 → 变更委员会决策 → 影响分析 → 计划制定 → 实施 → 测试 → 验证。

**解释：**
流程始于客户提出新功能需求或问题报告，形成变更请求（Change Request）。项目经理进行技术可行性及成本效益分析，随后由变更委员会（Change Control Board）决定是否批准。批准后，分析变更对系统其他部分的影响，制定详细计划，交由开发人员实施，测试后经项目经理（有时还有客户）验证并正式关闭。

**关键特性 / 语法 / 结构**
- 角色：客户、项目经理、变更委员会、分析师、实施者（Change builder）
- 关键工件：Requirements / Problem Report → Change Request → Change Log → Change Impact Analysis → Change Planning → System Release → Change Verification

> **Примечание (备注):** 在复杂系统中，对一个部分的修改几乎总会波及其他部分，因此影响分析至关重要。

---

### 概念 3: 版本控制系统 / Системы контроля версий

**定义 (Определение):**
> Системы контроля версий (СКВ) управляют изменениями в программном коде и поддерживают групповую работу. Основные типы: на основе файловой системы, централизованные, распределённые.
> **中文翻译：** 版本控制系统管理代码变更并支持团队协作。主要类型包括：基于文件系统的、集中式的和分布式的。

**解释：**
版本控制的核心挑战是多人同时修改同一文件。两种典型解决方案：Lock-modify-unlock（独占编辑，会降低并行效率）和 Copy-modify-merge（每个开发者有完整工作副本，合并时解决冲突）。

**关键特性 / 语法 / 结构**
- 集中式：SVN 为代表，仓库在中央服务器
- 分布式：Git 为代表，每个开发者本地保存完整仓库历史
- 冲突解决需要开发者之间的沟通与协调

## 💡 例题与实验 (Примеры и лабораторные работы)

**例 (Пример):** 描述 SVN 中并发修改同一文件导致的冲突场景及解决步骤。
**中文：** 两位开发者同时修改同一文件的同一行。

**解 / 分析 (Решение / Анализ):**
当第二个开发者执行 `svn update` 时，SVN 检测到冲突。此时会创建 `filename.mine`（本地修改）、`filename.rOLDREV`（原始版本）、`filename.rNEWREV`（仓库当前版本）。开发者选择 `(p) postpone`，然后与另一位开发者协商，手动编辑文件合并修改，最后执行 `svn resolved`。

**关键点 / Вывод:**
无法自动解决的冲突必须通过沟通处理；频繁更新可以降低冲突概率。

## 📋 本讲概览 (Обзор лекции)

本讲系统介绍软件构建自动化的动机、工具演化及核心方法。从手工重复构建的痛苦出发，依次讲解 Make 的依赖图原理、Ant 的指令式 XML 构建、Maven 的声明式 POM 与依赖管理、Gradle 的 Groovy DSL 灵活构建，以及跨平台构建系统 GNU autotools 和持续集成服务器。理解声明式与命令式构建的差异、传递性依赖管理、项目对象模型等核心概念是本章重点。

## 🎯 核心概念 (Ключевые понятия)

### 概念 1: 构建自动化的动机 / Зачем автоматизировать сборку?

**定义 (Определение):**
> При ручной сборке необходимо многократно повторять одинаковые последовательности команд; скрипты ОС сложно поддерживать при изменении структуры проекта.
> **中文翻译：** 手动构建需要反复重复相同的命令序列；用操作系统脚本容易在项目结构变化时失于维护。

**解释：**
手动执行 `javac`, `cp`, `jar` 等命令对小型项目尚可，但项目包含数十个模块且有外部依赖时，手工构建几乎不可行。硬件架构（32/64 位、缓存组织）、操作系统差异（库路径、配置文件位置）、编译速度慢和缺乏并行化都促使构建过程必须自动化。自动化不仅能消除重复劳动，还保证了构建的可重复性，使团队能在任何平台上一致地生成最终产品。

**关键特性 / 语法 / 结构**
- 跨平台差异：POSIX 标准试图统一 API，但配置文件位置等仍各不相同
- 长时间编译催生了“夜间构建”（nightly build）的做法
- 现代构建系统支持并行编译甚至多机构建

---

### 概念 2: Make — 基于依赖图的构建 / Make

**定义 (Определение):**
> Make — утилита, управляющая сборкой на основе файла Makefile, в котором описаны цели, зависимости и действия. Если время модификации цели старше любой из её зависимостей, цель пересобирается.
> **中文翻译：** Make 是基于 Makefile 管理构建的工具，文件中描述了目标、依赖和动作。如果目标的修改时间早于任一依赖的修改时间，该目标就会被重新构建。

**解释：**
Make 是隐式构建系统的鼻祖。`Makefile` 中通过 `<цель>: <зависимости> ...` 定义构建规则，下一行（以 Tab 开头）是 Shell 命令。Make 从 `all` 目标开始，递归分析依赖图，只重新编译需要更新的部分。但 Make 的语言对开发者不够友好，需维护大量宏变量和隐式规则。

**关键特性 / 语法 / 结构**
- 依赖图是树状结构（或 DAG）
- 变量、模式规则和条件判断提供了一定程度的灵活性
- 示例：32 位和 64 位内核模块共享部分源文件，Makefile 通过条件变量区分编译选项

---

### 概念 3: Ant — 指令式 XML 构建 / Apache Ant

**定义 (Определение):**
> Ant — императивная система сборки для Java, использующая XML файл build.xml с целями (target), зависимостями и командами-задачами.
> **中文翻译：** Ant 是面向 Java 的指令式构建系统，使用 build.xml 文件描述目标、依赖关系和任务命令。

**解释：**
Ant 的设计目标是将构建从平台特定的 Shell 命令中解放出来。所有操作都以 `<target>` 组织，通过 `depends` 声明依赖，内部使用 Ant 内置任务（如 `javac`, `jar`, `copy`）完成实际工作。Ant 支持属性系统，可通过属性文件或环境变量配置。虽然比 Make 跨平台，但 XML 冗长，大型项目的 build.xml 会变得难以阅读。

**关键特性 / 语法 / 结构**
- 任务丰富：文件操作、压缩、编译、部署、测试、VCS 集成等
- 属性（property）：可用 `<property file="build.properties"/>` 加载
- 可以调用 Ant 自身及外部文件中的目标

---

### 概念 4: Maven — 声明式构建与依赖管理 / Apache Maven

**定义 (Определение):**
> Maven — декларативное средство сборки, основанное на POM (Project Object Model) и управляемое жизненным циклом. Зависимости описываются в GAV-формате (groupId:artifactId:version) и автоматически разрешаются из репозиториев.
> **中文翻译：** Maven 是基于 POM 和生命周期的声明式构建工具。依赖用 GAV 格式描述，自动从仓库中解析。

**解释：**
Maven 的核心是“约定优于配置”：只要项目目录结构符合约定（`src/main/java`, `src/main/resources`, `src/test/java` 等），构建就能自动运行，无需显式指定每步操作。依赖管理是通过传递性解析实现的：如果 A 依赖 B，B 依赖 C，则 A 也自动获得 C。依赖的 scope（compile, provided, test 等）控制其在不同阶段的使用。

Maven 的生命周期包含标准阶段：compile → test-compile → test → package → integration-test → install → deploy。插件在这些阶段被触发执行。但声明式也有局限：一旦需要非常规操作，就需要开发自定义插件，这并不简单。

**关键特性 / 语法 / 结构**
- GAV 坐标：`<groupId> : <artifactId> : <version>`
- POM 文件示例（见代码部分）
- 仓库：本地仓库缓存依赖，`mvn install` 将产物安装到本地

---

### 概念 5: Gradle — 灵活的 DSL 构建 / Gradle

**定义 (Определение):**
> Gradle — система сборки, использующая DSL на Groovy. Нейтральна к языкам, поддерживает инкрементальную и параллельную сборку, может использовать репозитории Maven и Ivy.
> **中文翻译：** Gradle 是基于 Groovy DSL 的构建系统，语言中立，支持增量构建和并行构建，可使用 Maven 和 Ivy 仓库。

**解释：**
Gradle 融合了 Ant 的灵活性和 Maven 的约定与依赖管理。`build.gradle` 文件用简洁的 Groovy 编写，通过 `apply plugin: 'java'` 即可获得标准 Java 构建任务。依赖声明与 Maven 类似，但语法更简洁。它还支持增量构建（只运行必须的任务）和并行执行。

**关键特性 / 语法 / 结构**
- 插件：`java`, `application` 等，每个插件自带任务集合
- 仓库：`mavenCentral()`, `jcenter()`, 自定义仓库
- 依赖：`compile 'group:name:version'`
- 任务定义和修改非常灵活

---

### 概念 6: GNU autotools — 跨平台配置与构建

**定义 (Определение):**
> GNU autotools — семейство утилит (autoscan, autoconf, automake, ...), генерирующих Makefile на основе анализа платформы. Пользователю достаточно выполнить `./configure && make && make install`.
> **中文翻译：** GNU autotools 是一套通过平台分析自动生成 Makefile 的工具集。用户只需执行配置、构建、安装三步。

**解释：**
autotools 由 autoscan（扫描代码生成 `configure.scan`）、autoconf（生成 `configure` 脚本）、automake（根据 `Makefile.am` 生成 `Makefile.in`）等组成。`configure` 脚本在目标平台上测试编译器、库函数、头文件等，生成 `config.h` 和最终的 `Makefile`。这一机制是 Linux 开源软件的标准分发方式，使程序可以在多种 Unix 系统上编译。

**关键特性 / 语法 / 结构**
- `configure.ac` 包含项目信息和宏检查（AC_PROG_CC, PKG_CHECK_MODULES 等）
- `Makefile.am` 声明程序名、源文件和编译选项
- 高度依赖于 m4 宏处理器

---

### 概念 7: 持续集成 / Непрерывная интеграция (CI)

**定义 (Определение):**
> Сервер ссоорки (билд-сервер) автоматически собирает продукт при изменениях в репозитории или по расписанию, запускает тесты и генерирует отчёты.
> **中文翻译：** 构建服务器在代码仓库有变化或定时触发时自动构建产品，运行测试并生成报告。

**解释：**
持续集成服务器（如 Jenkins、GitLab CI、Travis CI）监控版本控制系统，一旦检测到新提交就自动执行构建、测试、代码检查甚至部署。这确保集成问题能被快速发现。它们还维护构建历史，可随时回溯和下载任意版本。

**关键特性 / 语法 / 结构**
- 触发条件：代码推送、定时计划、手动触发
- 产物管理：war/jar 等部署包
- 集成质量门禁：测试不通过时阻止代码合并

## 💻 代码示例 (Примеры кода)

### Makefile 示例
```makefile
all: mylib.so myapp

mylib.o: mylib.c mylib.h
	gcc -c -fPIC mylib.c -o mylib.o

mylib.so: mylib.o
	gcc -shared -o mylib.so mylib.o

myapp.o: myapp.c mylib.h
	gcc -c myapp.c -o myapp.o

myapp: myapp.o mylib.so
	gcc myapp.o -L. -lmylib -o myapp
```
**中文解读：** all 目标依赖最终产物；每个 `.o` 文件依赖对应的 `.c` 和 `.h`；动态库需要 `-fPIC` 编译；链接时指定库路径。

### Ant 目标示例
```xml
<project name="MyProject" default="dist">
    <property name="build.dir" value="build"/>
    <target name="clean">
        <delete dir="${build.dir}"/>
    </target>
    <target name="compile" depends="clean">
        <mkdir dir="${build.dir}/classes"/>
        <javac srcdir="src" destdir="${build.dir}/classes"/>
    </target>
    <target name="dist" depends="compile">
        <jar destfile="${build.dir}/app.jar" basedir="${build.dir}/classes"/>
    </target>
</project>
```
**中文解读：** 默认目标 `dist` 依赖 `compile`，后者又依赖 `clean`，形成清理-编译-打包流程。`${build.dir}` 引用之前定义的属性。

### Maven POM 依赖示例
```xml
<dependencies>
    <dependency>
        <groupId>javax.servlet</groupId>
        <artifactId>servlet-api</artifactId>
        <version>2.5</version>
        <scope>provided</scope>
    </dependency>
    <dependency>
        <groupId>log4j</groupId>
        <artifactId>log4j-core</artifactId>
        <version>2.12.1</version>
    </dependency>
</dependencies>
```
**中文解读：** servlet-api 的 scope 为 `provided`，意为运行时由容器提供，不打包到 war 中；log4j 是默认的 `compile` scope，编译和运行时都需要。

### Gradle 构建脚本示例
```groovy
plugins {
    id 'java'
    id 'application'
}
mainClassName = 'com.example.Main'
repositories {
    mavenCentral()
}
dependencies {
    implementation 'com.google.guava:guava:30.1-jre'
    testImplementation 'junit:junit:4.13.2'
}
```
**中文解读：** `java` 插件提供编译、测试等任务；`application` 插件用于生成可执行 JAR；依赖使用紧凑的 `groupId:artifactId:version` 字符串。

### GNU autotools 示例
**configure.ac 片段:**
```m4
AC_PREREQ([2.69])
AC_INIT([hello], [1.0], [bug@example.com])
AM_INIT_AUTOMAKE
AC_PROG_CC
AC_CHECK_LIB([m], [sqrt])
AC_CONFIG_FILES([Makefile src/Makefile])
AC_OUTPUT
```
**Makefile.am 片段:**
```makefile
bin_PROGRAMS = hello
hello_SOURCES = main.c hello.c
hello_LDADD = -lm
```
**中文解读：** `AC_PROG_CC` 检查 C 编译器；`AC_CHECK_LIB` 检查数学库；`Makefile.am` 声明可执行文件及其源文件和链接库。

## 📝 重要结论与最佳实践 (Выводы и рекомендации)

**结论 (Вывод):** Автоматизация сборки является обязательной практикой в профессиональной разработке. Выбор инструмента (Make → Ant → Maven → Gradle) зависит от сложности проекта, необходимости в гибкости и предпочтений команды. Декларативные системы (Maven, Gradle) заметно снижают усилия по поддержке сборки по сравнению с императивными (Make, Ant). / **中文：** 构建自动化是专业开发的必备实践。工具的选择需根据项目复杂度、灵活性需求和团队偏好决定，声明式系统通常能显著降低构建维护成本。

**最佳实践 (Лучшие практики):**
- 采用约定优于配置，遵循标准目录结构以减少配置
- 将构建脚本纳入版本控制，确保全团队使用一致的构建过程
- 配置 CI 服务器，在每次推送时自动构建并运行测试
- 外部依赖版本应明确指定，避免使用 SNAPSHOT 快照版于正式发布
- 利用增量构建和并行构建缩短反馈循环

## 💡 例题与实验 (Примеры и лабораторные работы)

**例 (Пример):** 解释 Maven 传递性依赖可能带来的“依赖地狱”及如何通过排除解决冲突。
**中文：** 项目 A 依赖 B 和 C，B 依赖 X 1.0，C 依赖 X 2.0，最终会引入哪个版本的 X？

**解 / 分析 (Решение / Анализ):**
Maven 会采用“最近定义优先”和“最先声明优先”的冲突调解原则，最终只会保留一个版本的 X（通常是 2.0，但可能不是开发者期望的版本）。如果需要使用特定版本，可使用 `<exclusions>` 排除传递性依赖，或通过 `<dependencyManagement>` 统一管理版本。

```xml
<dependency>
    <groupId>com.example</groupId>
    <artifactId>B</artifactId>
    <exclusions>
        <exclusion>
            <groupId>com.example</groupId>
            <artifactId>X</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

**关键点 / Вывод:**
传递性依赖节省了大量手动管理，但可能引发版本冲突；`dependencyManagement` 是集中控制版本的最佳手段。

# Лекция 5. 软件测试 / Тестирование ПО

> **课程 (Course):** Введение в программную инженерию
> **日期 (Date):** 2019-2020 уч. год
> **来源 (Source):** Конспект лекций v1.4.0.pdf

---

## 📋 本讲概览 (Обзор лекции)

本讲是软件测试的完整知识体系。首先澄清 ISTQB 标准术语（Mistake, Fault, Failure, Error），分析测试的目的并非证明无缺陷，而是提升质量信心。随后沿着 V 模型展开测试层级（模块、集成、系统、验收），讲解静态与动态测试、黑盒与白盒方法、测试用例与场景设计、等效划分和边界值分析等覆盖选择技术，以及功能测试、性能测试（CARAT）和自动化的回归测试。最后简述测试人员角色与活动。

---

## 🎯 核心概念 (Ключевые понятия)

### 概念 1: 测试术语 / Терминология тестирования

**定义 (Определение):**
> Mistake (ошибка человека) → Fault (дефект в ПО) → Failure (отказ/сбой) → Error (невозможность выполнить задачу). «BUG» — неформальный термин.
> **中文翻译：** 人的失误（Mistake）→ 软件缺陷（Fault）→ 故障/崩溃（Failure）→ 任务无法完成（Error）。BUG 是非正式说法。

**解释：**
这些术语有严格的因果链：程序员犯下失误，在代码中留下缺陷；当程序运行时，缺陷暴露为故障（如崩溃、挂起）；最终导致用户无法完成业务目标。测试的目标是发现缺陷，而不是证明无错。

**关键特性 / 语法 / 结构**
- 示例：循环从 `i=1` 开始而不是 `i=0` 是一个缺陷，可能多年不被触发
- 环境因素（硬件、OS 版本）也能导致故障

---

### 概念 2: 测试层级 (V-模型) / Уровни тестирования

**定义 (Определение):**
> Модульное тестирование → Интеграционное тестирование → Системное тестирование → Приёмочное тестирование. Валидация — «правильно ли мы сделали продукт?», верификация — «сделали ли мы продукт правильно?»
> **中文翻译：** 模块测试 → 集成测试 → 系统测试 → 验收测试。Validation（确认）验证产品是否正确，Verification（验证）验证实现是否正确。

**解释：**
V 模型左侧的开发活动（需求、设计、编码）分别对应右侧的测试活动。模块测试用驱动器和桩隔离单个模块；集成测试检查模块间接口和交互；系统测试在真实环境下端到端验证需求；验收测试由用户执行，决定是否付款。

**关键特性 / 语法 / 结构**
- 模塊测试常见框架：JUnit (Java)
- 集成策略：自顶向下、自底向上、端到端、核心优先、大爆炸
- 系统测试阶段：Alpha（开发方环境，用户参与）、Beta（用户环境，开发方监控）、验收（用户独立进行）

---

### 概念 3: 测试用例与场景 / Тестовый случай и сценарий

**定义 (Определение):**
> Тестовый случай: входные значения, предусловия, ожидаемый результат, постусловия. Тестовый сценарий — последовательность тестовых случаев.
> **中文翻译：** 测试用例包括输入值、前置条件、预期结果和后置条件。测试场景是一系列用例的序列。

**解释：**
测试用例必须可重复执行、可自动化。用例的设计要覆盖正常和异常路径（如连续 3 次输错 PIN 码导致锁卡）。用例的执行应独立，顺序尽可能不依赖。

**关键特性 / 语法 / 结构**
- 预期结果必须在执行测试前确定（或由 TDD 驱动先行编写）
- 我国实践中“用例”和“场景”常有混用

---

### 概念 4: 黑盒与白盒测试 / Чёрный и белый ящик

**定义 (Определение):**
> "Чёрный ящик" — тестирование без знания внутренней структуры, на основе спецификации. "Белый ящик" — тестирование с анализом исходного кода и оценкой покрытия.
> **中文翻译：** 黑盒测试不依赖内部结构，依据规格说明；白盒测试分析源码并评估覆盖度。

**解释：**
黑盒方法的数据来源是需求、设计、领域经验；输入输出比对即可。白盒方法构建控制流图，计算圈复杂度来确定独立路径数，然后为每条路径设计测试用例。实际测试中常结合两者。

**关键特性 / 语法 / 结构**
- 覆盖准则：语句覆盖、分支覆盖、路径覆盖、条件覆盖等
- 额外源：UML 模型、经验清单

---

### 概念 5: 等效划分与边界值 / Эквивалентное разбиение и граничные значения

**定义 (Определение):**
> Эквивалентное разбиение — разделение входных данных на группы, где система ведёт себя одинаково. Граничные значения — проверка границ этих групп.
> **中文翻译：** 等效划分是将输入数据分成行为相同的若干组；边界值分析则测试这些组的边界。

**解释：**
以“吃馅饼满意度”函数为例：还没吃到（0 个）满意为 0；1~3 个线性增长；4~6 个达到饱和，增速减缓；7 个以上因过食满意度暴跌。据此划分出四个等价区间，每区间只需少量测试点，但边界值必须单独测试。

**关键特性 / 语法 / 结构**
- 该方法显著减少测试用例数量，同时捕获常见错误

---

### 概念 6: 静态测试 / Статическое тестирование

**定义 (Определение):**
> Статическое тестирование (рецензирование) — анализ артефактов без запуска кода. Включает неформальные ревью, технический анализ, инспекции.
> **中文翻译：** 静态测试是在不运行代码的情况下分析工件，包括非正式评审、技术分析和正式审查。

**解释：**
早期发现缺陷成本极低。正式审查（Inspection）由 Michael Fagan 在 IBM 提出，每个审查者只关注两个质量维度。工具如 FindBugs、Lint 可自动检测空指针、资源泄露、缓冲区溢出等模式。静态测试能发现动态测试难以暴露的缺陷，如不符合标准的设计决策。

**关键特性 / 语法 / 结构**
- 典型审查步骤：准备 → 概览 → 独立检查 → 会议 → 返工 → 验证
- 静态分析工具可直接集成到 IDE 或 CI 流程中

---

### 概念 7: 性能测试 (CARAT) / Тестирование производительности

**定义 (Определение):**
> CARAT: Capacity, Accuracy, Response Time, Availability, Throughput.
> **中文翻译：** CARAT 包括容量、精度、响应时间、可用性和吞吐量。

**解释：**
- Capacity：测试系统在最大规格负载下的行为
- Accuracy：确保计算误差在规定范围内
- Response Time：交互系统 1~5 秒为宜
- Availability：可用性 = (MTBF - MTTR) / MTBF，“五个九”代表年宕机仅 5 分钟
- Throughput：每秒事务数

常用工具：Apache JMeter（Java）、HP LoadRunner、IBM RPT 等。

**关键特性 / 语法 / 结构**
- 负载模型可模拟逐步增加直到超过极限，观察饱和点和降级行为

## 💻 代码示例 (Примеры кода)

### JUnit 4 测试示例
```java
import org.junit.*;
import static org.junit.Assert.*;

public class CalculatorTest {
    private Calculator calc;

    @BeforeClass
    public static void setUpClass() {
        // 一次性初始化资源
    }
    @Before
    public void setUp() {
        calc = new Calculator();
    }
    @Test
    public void testAdd() {
        assertEquals(5, calc.add(2, 3));
    }
    @Test(expected = ArithmeticException.class)
    public void testDivideByZero() {
        calc.divide(10, 0);
    }
    @After
    public void tearDown() {
        calc = null;
    }
    @AfterClass
    public static void tearDownClass() {
        // 释放资源
    }
}
```
**中文解读：** `@Before` 在每个 `@Test` 方法前执行，保证各测试独立；`expected` 属性检查是否抛出预期异常；`assertEquals` 是典型的断言方法。

### 有缺陷的 countPositive 示例
```java
public int countPositive(int[] data) {
    int count = 0;
    for (int i = 1; i < data.length; i++) { // defect: should start from 0
        if (data[i] > 0) count++;
    }
    return count;
}
```
**中文解读：** 循环从索引 1 开始会跳过第一个元素；若 `data` 为 null，调用 `data.length` 将抛出 NullPointerException，这是另一个缺陷。该示例说明静态分析和边界测试的价值。

## 📝 重要结论与最佳实践 (Выводы и рекомендации)

**结论 (Вывод):** Тестирование — это многогранная деятельность, охватывающая статический анализ, модульные, интеграционные, системные и приёмочные испытания. Эффективная стратегия комбинирует техники и уровни, понимая, что 100% покрытие недостижимо, а баланс между качеством и скоростью выхода на рынок критичен. / **中文：** 测试是多层面的活动，需结合静态分析、各级动态测试；100% 覆盖不可能实现，必须在质量与上市速度间寻求平衡。

**最佳实践 (Лучшие практики):**
- 尽早开展静态测试（评审需求、设计）以降低缺陷修复成本
- 坚持“先写测试再编码”或至少先定义预期结果
- 使用等效划分和边界值分析设计高效测试集
- 自动化回归测试，保证修改不会破坏已有功能
- 性能测试应在与生产环境一致的配置下进行，并收集 CARAT 指标

# Лекция 6. 性能分析与优化 / Анализ и оптимизация производительности

> **课程 (Course):** Введение в программную инженерию
> **日期 (Date):** 2019-2020 уч. год
> **来源 (Source):** Конспект лекций v1.4.0.pdf

---

## 📋 本讲概览 (Обзор лекции)

本讲深入计算机软件性能的工程分析方法。从系统、硬件、软件、人四个角度考察性能影响因素，建立“科学实验”式的性能调优循环，系统讲解自上而下的瓶颈定位方法论，涵盖 Linux/Windows 平台的实用监控工具、JVM 内存管理与垃圾回收、Java 应用分析方法，以及针对高系统态、高 IO 等待、高空闲、高用户态等典型症状的优化配方。强调算法选择、权衡取舍（trade-off）和架构视角的重要性。

---

## 🎯 核心概念 (Ключевые понятия)

### 概念 1: 性能的四个维度 / Четыре аспекта производительности

**定义 (Определение):**
> Аспекты производительности: системный и архитектурный, аппаратный, программный (алгоритмический), человеческий фактор (ошибки).
> **中文翻译：** 性能的四个方面：系统与架构层面、硬件层面、软件（算法）层面、人为因素（错误）。

**解释：**
- 系统架构：单体、多层、集群、虚拟化环境中的资源竞争
- 硬件：CPU 主频、核心数、缓存大小与层级、内存带宽、磁盘 IO
- 软件：算法复杂度、数据结构、多线程同步、锁粒度
- 人为：不合理的架构决策、不充分的领域知识

**关键特性 / 语法 / 结构**
- 性能优化总是多种因素的综合权衡
- 最容易获得的性能提升往往来自算法和架构的改进，而非微优化

---

### 概念 2: 科学实验式性能调优 / Научный эксперимент

**定义 (Определение):**
> Анализ производительности — это научный эксперимент: выбрать критерии → выбрать средства измерения (неинтрузивные по возможности) → нагрузить → проанализировать → изменить один параметр → повторить.
> **中文翻译：** 性能分析是科学实验：选择指标 → 选择测量工具（尽量非侵入） → 施加负载 → 分析结果 → 修改一个参数 → 重复循环。

**解释：**
测量工具本身会有开销，非侵入式工具（如 OS 内置计数器）影响最小。每次实验只改变一个变量，才能准确归因。负载应尽可能接近真实场景。分析结果时需扣除测量引入的噪声（如日志写入的 IO）。这一循环持续进行直到满意为止。

**关键特性 / 语法 / 结构**
- 负载类型：真实业务重放、合成负载
- 实验环境：最好是生产环境的克隆

---

### 概念 3: 自上而下的瓶颈定位 / Нисходящий метод

**定义 (Определение):**
> 1) Исключить ошибки аппаратуры и конфигурации; 2) Общесистемный мониторинг; 3) Мониторинг приложения; 4) Мониторинг микроархитектуры.
> **中文翻译：** 1) 排除硬件和配置错误；2) 系统级监控；3) 应用级监控；4) 微架构监控。

**解释：**
- 第一步：检查系统日志（dmesg）、配置文件、JVM 内存参数等低级错误
- 第二步：用 vmstat、iostat、mpstat、netstat 观察资源全局利用
- 第三步：使用 Profiler 定位热点函数、锁竞争和内存分配
- 第四步：用 perf 等工具分析 CPU 缓存未命中、TLB 缺失、分支预测失败等微观事件

**关键特性 / 语法 / 结构**
- 检查硬件错误比草率优化代码更优先
- 多数应用层优化停留在第三步即可

### 概念 4: 关键性能指标 / Ключевые показатели

**定义 (Определение):**
> Время отклика (latency), полное время обслуживания, пропускная способность (throughput), утилизация (%busy), ожидание (%wait), точка насыщения, масштабируемость, эффективность.
> **中文翻译：** 响应延迟、完整服务时间、吞吐量、利用率、等待率、饱和点、可扩展性、效率。

**解释：**
利用率 100% 不代表高效；可能程序在忙等自旋锁。饱和点之后吞吐量可能指数衰减。可扩展性衡量资源增加带来的性能提升。这些指标彼此关联：提高吞吐可能增加延迟。

**关键特性 / 语法 / 结构**
- 可用性公式：`Availability = (MTBF - MTTR) / MTBF`
- 响应时间和吞吐量通常存在矛盾

### 概念 5: Java 性能分析 / Профилирование Java

**定义 (Определение):**
> JVM память: Young Generation (Eden + S0/S1), Old Generation. Minor GC, Major GC. Средства мониторинга: jstat, jVisualVM, JConsole, jmap.
> **中文翻译：** JVM 内存划分为年轻代（Eden + 两个 Survivor）和老年代。Minor GC 发生在年轻代，Major GC 清理老年代。监控工具包括 jstat、jVisualVM 等。

**解释：**
对象先在 Eden 分配；Minor GC 后存活对象复制到 Survivor 区并在 S0、S1 间轮换，经过一定次数后晋升到老年代。频繁 Full GC 是严重性能问题的信号。通过 `-Xmx`、`-Xms`、`-XX:NewRatio` 等参数可调优。

**关键特性 / 语法 / 结构**
- 内存泄漏在 Java 中表现为不必要的对象引用导致 GC 无法回收
- 用 jmap 生成堆转储（heap dump），用 MAT 或 jhat 分析

### 概念 6: 微架构级优化 / Микроархитектурная оптимизация

**定义 (Определение):**
> Оптимизация на уровне микроархитектуры: выравнивание данных, работа с кэш-линиями, уменьшение TLB промахов, предсказание переходов, использование аппаратных счётчиков производительности (PMU).
> **中文翻译：** 微架构优化包括数据对齐、缓存行利用、减少 TLB 缺失、分支预测优化，以及使用硬件性能计数器（PMU）。

**解释：**
Linux 的 `perf` 工具可读取 CPU 内部性能计数器，跟踪 cache-misses、branch-misses、instructions 等事件。通过数据布局优化（如经常共同访问的字段放在同一缓存行）、使用大页内存减少 TLB 缺失、消除条件分支中的可预测模式等，能获得显著提升。

**关键特性 / 语法 / 结构**
- 一般应用程序极少需要这一层优化
- 需要深入了解 CPU 微架构和编译器行为

## 💻 代码示例 (Примеры кода)

### Linux 监控命令示例
```bash
# CPU 和内存
vmstat 1 5
# 各 CPU 使用率
mpstat -P ALL 1
# 磁盘 IO 详情
iostat -xz 1
# 网络接口流量
sar -n DEV 1

sar -n TCP,ETCP 1

pidstat 1

top
```
**中文解读：** 这些命令输出连续的采样值，可通过观察变化趋势和异常值快速定位瓶颈资源。

### JVM 参数示例
```bash
java -Xms512m -Xmx2g -XX:NewRatio=2 -XX:+PrintGCDetails -jar app.jar
```
**中文解读：** `-Xms` 和 `-Xmx` 设置堆的初始和最大大小；`-XX:NewRatio=2` 意味老年代与年轻代之比为 2:1；`PrintGCDetails` 输出 GC 日志，是分析 GC 行为的基础。

## 📝 重要结论与最佳实践 (Выводы и рекомендации)

**结论 (Вывод):** Производительность — это свойство, которое необходимо проектировать и постоянно измерять. Не существует серебряной пули; улучшения достигаются методом последовательных приближений: измерять, анализировать, изменять одну переменную, повторять. Понимание trade-off между памятью, процессором и скоростью IO — ключ к успешной оптимизации. / **中文：** 性能是需要设计和持续度量的属性。优化的成功来自系统化方法：度量→分析→单变量更改→重复。理解内存、CPU、IO 之间的权衡是关键。

**最佳实践 (Лучшие практики):**
- 从不猜测瓶颈，必须通过监控数据证实
- 先确保正确性，再优化；优先选择收益最大的算法/架构优化
- 使用非侵入式工具建立基准，改变代码后重新衡量
- 对于 Java 应用，密切关注 GC 日志并调整堆尺寸
- 在生产环境无法监控时，建立高度模拟的测试环境

## 💡 例题与实验 (Примеры и лабораторные работы)

**例 (Пример):** 应用响应缓慢，CPU 用户态占用 30%，IO wait 60%，空闲 10%。分析可能原因和对策。
**中文：** 某系统用户态 CPU 只占 30%，IO wait 高达 60%，空闲 10%，如何定位和优化？

**解 / 分析 (Решение / Анализ):**
高 IO wait 表明 CPU 在等待磁盘或网络 IO。用 `iostat -xz 1` 查看各磁盘的 `await` 和 `%util`。如果某磁盘 `%util` 接近 100% 且 `await` 高，说明磁盘成为瓶颈。
对策：
1. 应用层：检查是否可减少 IO（缓存、批量写入、压缩）
2. 数据库层：优化查询，增加索引，减少全表扫描
3. 系统层：扩大文件系统缓存，使用 SSD 替代 HDD
4. 架构层：引入读写分离、CDN 等

**关键点 / Вывод:**
IO 等待高不代表 CPU 不工作，而是 CPU 在空等 IO 完成；优化时应首先减少不必要的 IO。
