### 第1题（原题 1）：ISO/IEC 12207:2010: Жизненный цикл ПО. Группы процессов ЖЦ.

**必答点：** 生命周期；过程组。

**讲座依据：** 第 7–8 页。

**俄语答题 / Русский ответ**

1. Жизненный цикл ПО — время от появления идеи до вывода программы из эксплуатации. Основные этапы: требования, анализ, проектирование, реализацию, тестирование, внедрение, эксплуатацию, сопровождение и вывод из эксплуатации.

1. 软件生命周期从产生想法开始，到软件退役结束。主要阶段：需求、分析、设计、开发、测试、部署、运行和维护。
2. 七个过程组：协议、组织项目保障、项目管理、技术过程、软件实现、软件支持、软件复用。
3. 过程将输入数据和资源转化为结果。过程可以重复、并行执行。

### 第3题：Рецепты повышения производительности при высоком %IO wait. + Рецепты повышения производительности при высоком %User.

#### A（原题 78）：Рецепты повышения производительности при высоком %IO wait.

**必答点：** iowait 含义；应用；缓存；设备。

**讲座依据：** 第 169 页。

**俄语答题 / Русский ответ**

1. Высокий `%iowait` показывает простой CPU при незавершённом I/O. Нужно проверить диски и подкачку, например через `iostat` и `vmstat`.
2. **Приложение:** уменьшить число и объём обращений, объединять запросы, подобрать размер блока под систему и устройство.
3. **Кэши и буферы:** настроить их размер; при нехватке памяти добавить RAM.
4. **Аппаратура:** если ограничение в устройстве, использовать более быстрое хранилище, например SSD. Особенно полезно это при случайном доступе.

**中文对应**

1. %iowait 高表示有未完成 I/O 时 CPU 空闲，应以 iostat、vmstat 等检查磁盘和换页。
2. 应用：减少访问次数与总量、合并请求，按系统和设备选择块大小。
3. 缓存与缓冲：调整大小，内存不足时增加 RAM。
4. 硬件：确认设备限制后使用更快存储，如 SSD，随机访问尤其受益。

#### B（原题 80）：Рецепты повышения производительности при высоком %User.

**必答点：** User 含义；算法；对象；忙等待；缓存/TLB；同步；硬件。

**讲座依据：** 第 171–172 页。

**俄语答题 / Русский ответ**

1. Высокий `%User` означает, что CPU занят кодом приложения. Профилировщик помогает найти самые затратные методы.
2. Улучшают алгоритмы, убирают повторные вычисления и активное ожидание в циклах.
3. Уменьшают создание и копирование объектов. Повторно используют объекты, если это снижает затраты.
4. Улучшают размещение данных, уменьшают промахи кэша и TLB, упрощают синхронизацию. При необходимости проверяют эффект привязки потоков к CPU.
5. Используют оптимизацию компилятора. При подходящей задаче добавляют ядра, применяют GPU или более быстрый CPU. Улучшение подтверждают измерением.

**中文对应**

1. %User 高表示 CPU 忙于应用代码，用剖析工具找出最耗时方法。
2. 改进算法，消除重复计算和循环忙等待。
3. 减少对象创建、复制；确实能降低成本时复用对象。
4. 改善数据布局，减少缓存和 TLB 未命中，简化同步；需要时测试线程绑核的效果。
5. 使用编译优化；任务适合时增加核心、使用 GPU 或更快 CPU，并测量确认收益。

### 第1题（原题 2）：Модели ЖЦ (последовательная, инкрементная, эволюционная).

**必答点：** 顺序；增量；演化；区别。

**讲座依据：** 第 10 页。

**俄语答题 / Русский ответ**

1. Последовательная модель: все требования определены заранее. Основные стадии проходят последовательно, продукт создают за один цикл.
2. Инкрементная модель: требования определены заранее, но продукт создают и поставляют по частям. Каждая часть добавляет функции.
3. Эволюционная модель: в начале известны не все требования. Требования и решение уточняют при создании следующих версий.
4. Различия — полнота начальных требований и число циклов разработки.

**中文对应**

1. 顺序模型：需求预先全部确定，主要阶段依次进行，一个周期完成产品。
2. 增量模型：需求预先确定，产品分批开发、交付，每批增加功能。
3. 演化模型：初期需求不完全明确，随着后续版本逐步细化需求和方案。
4. 区别是初期需求是否完整，以及开发周期的数量。

### 第2题：Системы автоматической сборки: предпосылки появления. + Сервера сборки/непрерывной интеграции.

#### A（原题 41）：Системы автоматической сборки: предпосылки появления.

**必答点：** 出现原因；构建系统作用。

**讲座依据：** 第 89–92 页。

**俄语答题 / Русский ответ**

Автоматизация сборки появилась из-за трёх проблем:

1. Приходится повторять много команд и учитывать зависимости файлов.
2. Среда разработки отличается от целевой системы: процессор, ОС, компилятор и библиотеки могут быть другими.
3. Сборка большого проекта занимает много времени.

Система сборки задаёт порядок действий, учитывает зависимости и настройки среды. Она может пересобирать только изменённые части и выполнять независимые задачи параллельно.

**中文对应**

自动构建针对三个问题出现：

1. 需要重复许多命令，并处理文件依赖。
2. 开发环境与目标环境的处理器、操作系统、编译器和库不同。
3. 大型项目构建耗时长。

构建系统规定执行顺序，处理依赖和环境配置，只重建变化部分，并行执行独立任务。

### 第3题（原题 69）：Мониторинг производительности: процессы.

**必答点：** 进程状态；调度；上下文切换；指标与工具。

**讲座依据：** 第 153–154、158 页。

**俄语答题 / Русский ответ**

1. Основные состояния процесса: готов к выполнению (Runnable), выполняется на CPU, ждёт I/O или другого события.
2. Планировщик выбирает процесс по приоритету и выделяет ему время CPU.
3. **Добровольное переключение контекста** происходит, когда процесс ждёт. **Вынужденное** — когда его вытесняет планировщик.
4. Наблюдают CPU, память, состояния, число потоков, переключения контекста и очередь выполнения.
5. Инструменты: `top`, `ps`, `pidstat`. В `top`: PR — приоритет, VIRT — виртуальная память, RES — память в RAM, SHR — разделяемая память.
6. Linux load average учитывает выполняемые и готовые задачи, а также задачи в непрерываемом ожидании. Это не процент загрузки CPU.

**中文对应**

1. 进程主要状态：就绪、CPU 上运行、等待 I/O 或其他事件。
2. 调度器依据优先级选择进程并分配 CPU 时间。
3. 主动上下文切换来自进程等待；被动切换来自调度器抢占。
4. 观察 CPU、内存、状态、线程数、上下文切换和运行队列。
5. 工具：top、ps、pidstat。PR 是优先级，VIRT 是虚拟内存，RES 是驻留物理内存，SHR 是共享内存。
6. Linux 平均负载包含运行、就绪及不可中断等待任务，不是 CPU 使用百分比。

**必答点：** 定义；阶段；优缺点。

### 第2题（原题 42）：Системы сборки: Make и Makefile.

**必答点：** Make 作用；规则；重建条件；Makefile 例子。

**讲座依据：** 第 93 页。

**俄语答题 / Русский ответ**

1. Make собирает цели по правилам файла `Makefile`. Правило содержит цель, зависимости и команды.
2. Цель пересобирается, если её нет или зависимость новее неё.
3. Команда начинается с TAB. `$@` — имя цели, `$<` — первая зависимость, `$^` — все зависимости без повторов, `$?` — зависимости новее цели.
4. Пример:

```makefile
main.o: main.c
	$(CC) -c $< -o $@

.PHONY: clean
clean:
	rm -f main.o
```

`make main.o` собирает объектный файл. `.PHONY` означает, что `clean` — действие, а не файл. `make -f file` выбирает другой файл правил.

**中文对应**

1. Make 根据 Makefile 的规则构建目标；规则包含目标、依赖和命令。
2. 目标不存在，或依赖比目标新时，重新构建。
3. 命令以 TAB 开头。$@ 是目标，$< 是首个依赖，$^ 是去重依赖列表，$? 是更新的依赖。
4. 例子将 main.c 编译成 main.o；clean 删除目标文件，.PHONY 声明它不是实际文件；-f 指定其他规则文件。

### 第3题：Системный анализ Linux "за 60 секунд". + Создание тестовой нагрузки и нагрузчики.

#### A（原题 73）：Системный анализ Linux "за 60 секунд".

**必答点：** 十条诊断命令及用途。

**讲座依据：** 第 159–161 页。

**俄语答题 / Русский ответ**

Быстрая проверка Linux:

1. `uptime` показывает среднюю нагрузку за 1, 5 и 15 минут.
2. `dmesg | tail` показывает последние сообщения и ошибки ядра.
3. `vmstat 1` показывает очередь, память, подкачку и CPU.
4. `mpstat -P ALL 1` показывает загрузку каждого CPU.
5. `pidstat 1` находит процессы с высокой нагрузкой.
6. `iostat -xz 1` показывает работу и ожидание I/O.
7. `free -m` показывает доступную память и swap.
8. `sar -n DEV 1` показывает трафик интерфейсов.
9. `sar -n TCP,ETCP 1` показывает TCP-соединения и повторные передачи.
10. `top` показывает общую картину в реальном времени.

Вывод делают по нескольким показателям вместе.

**中文对应**

Linux 快速检查：

1. uptime：1、5、15 分钟平均负载。
2. dmesg | tail：最近内核消息和错误。
3. vmstat：队列、内存、换页、CPU。
4. mpstat：每个 CPU 的使用率。
5. pidstat：高负载进程。
6. iostat：I/O 工作与等待。
7. free：可用内存和 swap。
8. sar -n DEV：接口流量。
9. sar -n TCP,ETCP：TCP 连接和重传。
10. top：实时整体状态。

结合多个指标判断。

#### B（原题 74）：Создание тестовой нагрузки и нагрузчики.

**必答点：** 创建测试环境；两种造负载方式；负载参数；工具。

**讲座依据：** 第 146、162 页。

**俄语答题 / Русский ответ**

1. Если измерять рабочую систему нельзя, создают похожую тестовую систему и дают ей нагрузку, близкую к реальной.
2. Первый способ — синтетическая нагрузка. Генератор имитирует действия пользователей; настраивают запросы, число пользователей, объём данных и длительность.
3. Второй способ — записать реальную нагрузку и воспроизвести её в тестовой системе.
4. Примеры нагрузчиков: JMeter и LoadRunner. Нагрузку можно повышать постепенно. Важно, чтобы сам генератор не ограничивал тест.

**中文对应**

1. 不能在生产系统测量时，建立相似的测试系统并施加接近真实的负载。
2. 第一种是合成负载：模拟用户操作，配置请求、用户数、数据量和时长。
3. 第二种是记录真实负载，在测试系统中重放。
4. 工具有 JMeter、LoadRunner；可逐步增加负载，并确保生成器不成为限制。

## Билет 4 · 变体 4

### 第1题（原题 4）：Методология Ройса.

**必答点：** 罗伊斯的五项措施。

**讲座依据：** 第 13 页。

**俄语答题 / Русский ответ**

Методология Ройса снижает риски разработки с помощью пяти мер:

### 第3题（原题 70）：Мониторинг производительности: виртуальная память.

**必答点：** 虚拟内存；缺页；换页/扫描指标；判断。

**讲座依据：** 第 155 页。

2. Minor 缺页无需磁盘 I/O；major 缺页需要从设备读取。
3. 观察空闲与可用 RAM、换入换出、缺页、扫描和回收。
4. free、vmstat、sar -B 提供指标：fault/s 缺页，majflt/s 主缺页，pgscan* 扫描，pgsteal/s 回收。
5. 频繁主缺页和换页可能表示 RAM 不足，单凭 minor 缺页不能判断。

3. **Снизу вверх:** сначала нижние модули, верхние заменяют драйверами.
4. **Функциональная стратегия:** по одному собирают полные сценарии «интерфейс → логика → БД».
5. **Ядро:** сначала собирают минимальную работающую систему, затем расширяют её.
6. **Большой взрыв:** объединяют всё сразу. При ошибке трудно найти её источник, поэтому постепенная интеграция удобнее для поиска дефектов.

**中文对应**

1. 集成测试检查模块间的调用、接口和数据传递。
2. 自顶向下：先上层，桩替代下层。
3. 自底向上：先下层，驱动替代上层。
4. 功能策略：逐个集成“界面→逻辑→数据库”的完整场景。
5. 核心策略：先最小可运行系统，再扩展。
6. 大爆炸：全部一次合并，出错难定位；逐步集成更便于定位缺陷。

В модели Git Flow ветви имеют разные задачи:

2. `develop` объединяет изменения для следующей версии.

3. feature 从 develop 建立，开发单一功能后合回。

5. hotfix 从 master 建立，紧急修复后合入 master 和 develop。

### 第3题：Ключевые характеристики производительности. + Нисходящий метод поиска узких мест.

#### A（原题 66）：Ключевые характеристики производительности.

**必答点：** 响应与服务时间；吞吐；利用与等待；饱和；扩展；效率；加速；Java 指标。

**讲座依据：** 第 150 页。

**俄语答题 / Русский ответ**

1. **Время отклика** в лекции — от запроса до первого результата. **Время полного обслуживания** — до полного завершения запроса.
2. **Пропускная способность** — число обработанных запросов за единицу времени.
3. **Утилизация** — доля времени, когда ресурс занят. **Ожидание** — время до получения ресурса; также наблюдают длину очереди.
4. **Насыщение:** нагрузка растёт, а пропускная способность почти не увеличивается. **Масштабируемость** — возможность увеличить производительность добавлением ресурсов.
5. **Эффективность** — соотношение полезной работы и затрат. Занятость CPU на 100% не означает высокую эффективность.
6. **Ускорение:** `S = Tдо / Tпосле` для одинаковой работы. Прирост скорости равен `(S - 1) × 100%`. Для Java также важны время запуска и объём занятой памяти — memory footprint.

1. 讲座中响应时间是请求到首个结果；完整服务时间是请求到完全完成。
2. 吞吐量是单位时间处理的请求数。
3. 利用率是资源忙碌时间比例；等待是取得资源前的时间，也要观察队列长度。
4. 饱和是负载增加但吞吐量几乎不再增加；可扩展性是通过增加资源提升性能的能力。
5. 效率是有效工作与成本之比；CPU 满载不代表高效率。
6. 相同工作量的加速比 S 为修改前耗时／修改后耗时，速度提升百分比为 (S−1)×100%。Java 还关注启动时间与内存占用。

### 第3题（原题 71）：Мониторинг производительности: буферизированный файловый ввод-вывод.

**必答点：** 缓冲 I/O 路径；读写机制；顺序/随机；监控。

**讲座依据：** 第 156 页。

**俄语答题 / Русский ответ**

1. При буферизированном I/O данные проходят через кэш ОС. Упрощённый путь чтения: `fread` → системный вызов `read` → VFS → кэш → файловая система и драйвер → диск.
2. Если данные есть в кэше, чтение с диска не нужно. При записи изменённые страницы обычно записываются на диск позже.
3. Последовательный доступ к HDD быстрее случайного: требуется меньше перемещений головки.
4. `iostat -x 1` показывает `r/s`, `w/s` — операции в секунду; `rkB/s`, `wkB/s` — объём передачи; `await` — время запроса вместе с очередью; `%util` — занятость устройства. Также проверяют длину очереди и размер запросов.

**中文对应**

2. 命中缓存就不读磁盘；写入修改的页通常稍后写回。
3. HDD 顺序访问比随机访问快，因为磁头移动较少。
4. iostat -x 1：r/s、w/s 是操作数，rkB/s、wkB/s 是传输量，await 是含排队的请求时间，%util 是设备忙碌比例；还要观察队列和请求大小。

Оценка риска включает три деятельности:

2. 节点是计算资源，画成立体矩形；可以是设备（device）或执行环境（executionEnvironment），例如服务器或 GlassFish。
3. 组件是具有明确接口的程序组成部分，画矩形并加组件图标或 «component»。
4. 制品是程序或数据文件，例如 Karlson.war，画矩形并加 «artifact» 或文档图标。
5. 将组件和制品放在节点内部。节点通信通道画实线，依赖画虚线箭头。
6. 讲座例子：客户端运行 Firefox；服务器运行 GlassFish 和 Oracle；Karlson.war 部署在 GlassFish 中。客户端通过 HTTP 访问应用，应用通过 JDBC 访问数据库。

### 第2题（原题 45）：Системы сборки: Maven. POM. Репозитории и зависимости.

**必答点：** Maven；POM；仓库；依赖获取与产物。

**讲座依据：** 第 97–98 页。

**俄语答题 / Русский ответ**

1. Maven — декларативная система сборки: разработчик описывает проект, а Maven выбирает нужные действия.
2. POM — Project Object Model. Файл `pom.xml` содержит имя, версию, тип проекта, зависимости, плагины и профили.
3. Зависимости — внешние библиотеки, нужные проекту. Maven берёт их из локального репозитория, обычно `~/.m2/repository`, или скачивает из удалённого.
4. `mvn package` создаёт пакет в `target`. `mvn install` также помещает его в локальный репозиторий. `mvn deploy` публикует пакет в удалённом репозитории.

**中文对应**

1. Maven 是声明式构建系统：描述项目，由 Maven 确定动作。
2. POM 是项目对象模型；pom.xml 包含名称、版本、类型、依赖、插件和配置方案。
3. 依赖是项目需要的外部库；先查本地仓库，通常是 ~/.m2/repository，缺失时从远程下载。
4. package 在 target 生成包；install 还安装到本地仓库；deploy 发布到远程仓库。

### 第3题：Статическое и динамическое тестирование. + Техники статического тестирования. Статический анализ кода.

#### A（原题 54）：Статическое и динамическое тестирование.

**必答点：** 静态；动态；区别和例子。

**讲座依据：** 第 120 页。

**俄语答题 / Русский ответ**

1. **Статическое тестирование** проверяет требования, документы, модели и код без запуска программы. Пример — просмотр кода коллегой или автоматический статический анализ.
2. **Динамическое тестирование** запускает модуль или всю систему с тестовыми данными. Фактический результат сравнивают с ожидаемым.
3. Главное различие — выполняется ли программа. Оба подхода помогают находить дефекты и дополняют друг друга.

**中文对应**

1. 静态测试不运行程序，检查需求、文档、模型和代码；例如同事审查代码或自动静态分析。
2. 动态测试输入测试数据，运行模块或整个系统，比较实际与预期结果。
3. 关键区别是是否执行程序；两者相互补充。

#### B（原题 62）：Техники статического тестирования. Статический анализ кода.

**必答点：** 静态测试技术；各方法区别；代码分析；工具与例子。

**讲座依据：** 第 139–142 页。

**俄语答题 / Русский ответ**

1. Статические техники проверяют артефакты без запуска программы.
2. **Неформальное ревью:** коллега просматривает материал. **Технический анализ:** специалисты проверяют решения. **Management review:** проверяют планы и состояние проекта.
3. **Сквозной контроль:** автор проводит участников по материалу. **Инспекция:** проверка по формальной процедуре с ролями и списком дефектов.
4. **Статический анализ кода** автоматически ищет возможные дефекты. Примеры: неинициализированная переменная, незакрытый файл, переполнение буфера, ошибки копирования кода.
5. Инструменты из лекции: Lint и FindBugs. Раннее обнаружение дефектов уменьшает стоимость исправлений.

**中文对应**

1. 静态技术不执行程序，检查开发制品。
2. 非正式评审由同事查看；技术评审由专业人员检查方案；管理评审检查计划和项目状态。
3. 走查由作者带领阅读材料；正式审查按规定流程进行，有角色分工和缺陷记录。
4. 静态分析自动查找可能的缺陷，例如未初始化变量、文件未关闭、缓冲区溢出和复制代码错误。
5. 讲座工具是 Lint、FindBugs；早发现可降低修复成本。
