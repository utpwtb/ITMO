## 4. JMeter 场景的构造

在 `movie-lab/jmeter/lab2-concurrency.jmx` 中组织独立场景组；提供 `README.md`、样例配置、夹具生成器和 `verify-results` 脚本。实际组名/参数应在文件中实现，不能只写在说明里。

建议组件与执行顺序：

1. `setUp Thread Group`：建立当轮数据、共享目标 ID/版本、共享唯一键；准备测试文件。创建夹具失败立即使整轮失败。
2. 每用户线程登录 `/api/auth`，HTTP Cookie Manager 管理 Cookie，JSON Extractor 提取 csrf；写请求添加 `X-CSRF-Token`。
3. 对竞争场景，先完成目标对象读取，确认所有线程持有相同的初始版本，然后用 Synchronizing Timer 汇合并同时发出目标操作。给屏障设置有限超时；人数不足超时算本轮设置失败，不算并发验证通过。
4. C02 这类不同操作的参与者放在同一个场景线程组中，并参数化请求方法/路径/正文，使其经过同一汇合点。每组独立运行，避免两个不共享屏障的线程组只是在时间上“可能重叠”。
5. JSON CRUD 请求设置 `application/json`；导入 sampler 使用 multipart 文件上传，file 字段名为 `file`，文件内容类型 `application/json`，不能复用覆盖 boundary 的 JSON Header Manager。
6. HTTP 响应断言校验状态码与业务错误码；JSR223/Groovy 断言汇总成功数、冲突数及操作 ID。跨线程共享数据使用线程安全容器；用户身份/CSRF 使用线程私有变量。
7. 所有操作结束后再做最终状态检查，并记录通过/失败；teardown 保留失败证据后，只清理本轮专用测试对象。

Cookie Manager 为各线程保存独立 Cookie；Synchronizing Timer 可等待指定线程数后一起释放。[JMeter 组件说明](https://jmeter.apache.org/usermanual/component_reference.html)

推荐先用 2 线程验证竞争结果，再用 10 线程运行 20 轮；同一对象更新/删除也可在 2 人组内重复 20 轮。每轮刷新目标与版本。记录实际参数，不把这些推荐值当成教师规定。

JMeter 的客户端同时发请求不能独自证明数据库事务必然发生交叠。保留时间/锁等待证据；关键事务窗口用真实数据库集成测试的 latch/barrier 确定性覆盖，与 JMeter 的多用户证据互补。

## 5. 并发场景与判定

以下竞争场景除 C10 外，都使用隔离的当轮数据。成功次数必须是**提交成功**，不能把收到请求或创建 RUNNING 历史算作成功。

| ID | 场景 | 预期结果/数据库不变量 |
|---|---|---|
| C01 | 两名管理员读取同一电影版本 v，再并发写入不同内容 | 恰好一个更新成功，一个 409；最终值属于获胜者，版本推进一次，无丢失更新 |
| C02 | 同一版本的 update 与 delete 竞争；另外测试 delete 与 delete | 更新先提交：删除 409，保留更新后的对象；删除先提交：更新 404，对象消失。双删除恰好一次成功，另一次 404 |
| C03 | N 用户普通创建同名＋同一已有导演 | 恰好 1 个 201、N−1 个 DUPLICATE_MOVIE；最终该键数量=1 |
| C04 | N 用户创建同名＋director=null | 与 C03 相同，证明空值分支受保护 |
| C05 | 同名不同导演；不同名同导演并发创建 | 全部合法请求成功；不存在错误的单字段唯一限制 |
| C06 | 两个不同电影并发改成相同目标组合 | 恰好一个成功；失败者原记录保持；目标键数量=1；无误删 |
| C07 | 多人同时上传完全相同的多电影文件 | 仅一整批成功；其他整批 409；最终每个键一条、辅助对象只来自成功批次；每个已接受上传各有历史 |
| C08 | 普通创建与导入竞争同一组合 | 只允许一个路径提交该键；导入输时，其余原本合法电影和新建辅助对象也全部回滚 |
| C09 | 两个导入文件各有独有电影，并共享一个冲突组合 | 恰好一整批提交；失败文件的独有电影也不存在，不能只跳过共同记录 |
| C10 | 一个文件触发回滚，同时其他用户做独立创建/修改/删除 | 失败导入零领域写入，其他独立事务按其结果保留；不因一个请求回滚而回退别人的成功写入 |
| C11 | 导入在第一个 insert/flush 后暂停，另一用户读取，再放行提交/回滚 | 提交前看不到本批部分结果；提交后看到全部，回滚后看不到本批；历史计数不提前显示成功 |
| C12 | 混合多个用户持续创建、编辑、删除、导入，并执行原特殊操作 | 无非预期 5xx、无组合重复、无孤立引用；同对象冲突符合版本约定，特殊操作无丢失更新；实际成功导入历史可追溯 |

C11 的确定性暂停可放在测试配置的服务器/集成测试中；JMeter 并行读场景作为端到端补充。生产版本去除测试注入点。若轮询看不到完整数量是分页导致，测试必须拉全该轮数据再判断。

复用同一已有导演的竞争用例与“并发创建相同护照的新导演”分开：前者验证新组合唯一，后者补充验证人物复用及原护照约束，避免人物唯一冲突掩盖 Movie 查重缺陷。

预期 409/404 可以经断言标记为该业务场景通过，但必须同时检查最终状态和精确计数。不得统一忽略所有非 2xx；503、非预期 500、屏障超时和连接失败都需要单独记录、分析和重跑。

## 6. 隔离级别实验与最终决策

### 6.1 先量出真实配置

在**执行实际业务事务的同一数据库连接**上读取隔离级别，例如 `SHOW transaction_isolation`。单独用 psql 查看默认值只能作辅助证据；还需记录 ORM、连接池及当前事务是否覆盖默认配置。

记录 `Database.write` 从事务开始到提交之间的顺序，确认锁是在最终查重前取得；验证锁等待/事务超时实际生效。现有 JPA lock.timeout hint 不能未经验证就当成数据库已严格执行的超时保障。

### 6.2 首选策略及理由

本计划首选保留 **READ COMMITTED＋AppState 全局写锁＋实体/客户端版本检查**，以最少改动完成实验。此选择是基于当前源码的工程推论，必须通过 C 场景验证。

原因分工：

- 同一个 AppState 行锁串行化全部领域写事务；锁内重新查重并写入，可以让后来的请求观察前一请求已提交的结果。
- Movie 的版本与客户端期望版本防止旧表单覆盖；只靠行锁，晚到请求仍可能携带过期输入。
- 单个批量业务事务保证回滚；单独提高隔离级别不能修复“每条电影分别提交”。
- 只靠 `SELECT 查重 → INSERT` 而没有并发保护不够；`@Version` 也不保护原本不存在的两条新电影。

READ COMMITTED 每条查询使用该语句开始时的已提交视图；SERIALIZABLE 下应准备处理序列化失败并从头重试事务。[PostgreSQL 官方说明](https://www.postgresql.org/docs/18/transaction-iso.html)

全局锁属于应用调用的并发控制手段，不是数据库声明的新组合唯一规则。它能跨使用同一数据库的应用进程起作用；仅用 JVM `synchronized` 不能作为该保障的替代品。局限是所有领域写操作互相等待，长导入会增加延迟。

### 6.3 有控制变量的比较

至少保存“新增功能完成后的当前策略”与“最终策略”两组记录。若最终配置未变化，明确记录两次复核结果，不编造改动。

为支撑级别选择，建议在专用环境比较：

| 配置 | 应记录的内容 |
|---|---|
| A：实测当前级别＋当前全局写锁 | C01–C12 结果、冲突、等待、超时、响应耗时 |
| B：显式 READ COMMITTED＋同一锁策略 | 若 A 已相同则注明；验证代码/连接配置确实生效 |
| C：SERIALIZABLE＋同一锁策略 | 观察是否增加序列化失败/重试及代价，不能预设更快或更安全 |

每组使用相同版本、数据规模、线程及轮次，除待比较配置外保持一致。不得悄悄关闭生产写锁来制造“旧实现错误”。如需演示无保护的查重竞态，用独立测试示例并明确它不是原应用基线。

按实验结果决策：

1. 当前全局锁路径全部正确：保留/显式配置经验证的级别，解释无需额外提高的原因。
2. 发现某写入口绕过事务/锁：先统一该入口，再重测；这属于事务边界错误，不能用“已升级隔离级别”掩盖。
3. 如果后续选择去掉全局锁以提高并发：另行设计并验证所有相关入口的 SERIALIZABLE 事务及重试，或其他完整并发协议。此优化不属于本实验必需，不与基本完成路径混在一起。
4. 如果提高级别：在事务第一次数据查询/修改前生效。对 PostgreSQL SQLSTATE 40001，回滚并用新的 EntityManager 重跑完整业务事务；重试上限例如 3 次且配置化，历史操作 ID 保持同一个。超过上限返回明确的临时故障，正常最终测试不得把重试耗尽当通过。
5. 对用户旧版本冲突、非法字段和 DUPLICATE_MOVIE 不做自动事务重试；对提交是否成功未知的连接异常，先查持久化历史。

同一全局状态行在 SERIALIZABLE 下的竞争可能触发重试；这不是可以把隔离级别改高后忽略的异常。实际测量后说明最终选择。

## 7. 可复现命令与交付要求

在 Helios 的实际项目目录内，按 [Helios 计划](lab2_helios_plan.md) 修复测试映射/表前缀后执行服务器测试脚本（内部运行 Maven verify）。`mvn -B verify` 也可作为已正确配置环境下的等效命令。不要把未连接数据库导致的失败写成测试通过；本地 `start-local.ps1` 仅供开发检查。

JMeter 正式运行使用 CLI，并保存 JTL/HTML 报告；GUI 用于编辑和调试。[JMeter 运行说明](https://jmeter.apache.org/usermanual/get-started.html#load_test_running)

以下是本地调试用命令模板；最终服务器命令及端口见 Helios 计划。`-Jscenario` 等参数不会自动创建场景，必须在 `.jmx`/脚本中接线：

