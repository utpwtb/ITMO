## 1. 任务边界与阅读顺序

在现有实验一 Movie 信息系统上完成实验二，不另建一套无关应用。用户已说明以下两项获得老师批准，执行时无需再次确认：

“JSON”指实验要求中的导入文件格式；本计划用 Markdown 编写以便阅读，JMeter 场景仍使用其原生 `.jmx` 格式。

### P3：统一事务边界和组合唯一检查

操作：

1. 抽出 `saveInTransaction(EntityManager, ...)` 或同等职责的方法。普通 CRUD 外层保留 `Database.write`；导入在自己的同一 `Database.write` 回调中调用内部持久化逻辑。内部方法不提交事务。
2. 建立专用组合唯一校验器。新增、编辑（排除自身）、变更导演和导入全部调用；合并部分更新后的完整实体再检查。
3. 在获得现有 AppState 写锁后，才执行用于最终决策的关联读取、版本检查、查重和写入；持锁至提交/回滚。事务外预检仅用于提前提示。
4. 保留实体 `@Version` 与客户端期望版本检查，覆盖同一电影编辑/删除竞争。现有批量特殊操作也继续经过统一写入边界。
5. 为仅写入历史元数据的短事务提供独立方法；它不递归调用正在执行的业务事务，不增加电影 revision。成功导入的历史终态仍与电影在同一业务事务内提交。
6. 核对隔离级别与锁等待超时在实际 PostgreSQL 会话中生效；实现明确的超时/并发错误分类，详见验收计划。

产物：事务封装、公共校验组件、CRUD 改造、版本冲突测试。

完成条件：重复组合由业务异常拒绝；数据库没有新增该组合的 UNIQUE、唯一索引或触发器；原护照号唯一约束仍在；无逐条提交或嵌套事务；旧 CRUD 测试通过。

### P4：实现原子批量导入及上传接口

执行流程：

```text
认证、CSRF、文件存在/大小检查
  → T1：单独提交一条 RUNNING 历史记录
  → 服务器解析 JSON、结构与字段校验
  → T2：开启一次业务事务，先取得 AppState 写锁
       → 解析/复用人物、写入嵌套对象
       → 文件内及数据库组合查重
       → 写入全部 Movie，必要时 flush 以暴露数据库错误
       → 更新该历史为 SUCCESS，addedCount=电影条数
       → 电影 revision 增加一次，与上述变更一起提交
  → 返回成功

解析失败或 T2 明确回滚
  → T3：单独事务将同一条历史设为 FAILED，addedCount=null
  → 返回含 operationId、错误码、记录路径的失败响应
```

T1/T3 与 T2 分别使用独立 EntityManager/事务；当前项目采用 `RESOURCE_LOCAL`，不要仅添加一个事务注解就宣称流程已经生效。

操作：

1. 新增 ImportResource、ImportService/解析器和 HistoryService，职责可按项目习惯合并，但保留上述事务边界。
2. 实现 `POST /api/imports` 的真实文件上传；新增资源到 ApiApplication 注册表。服务器校验原始文件，浏览器不能只发送已解析的数组来代替上传。
3. 任何字段、关联、组合唯一或数据库错误都终止整批；新建 Movie/Person/Coordinates/Location 均回滚，原有对象不被隐式改写。
4. 提交阶段异常也进入处理范围。若连接断开造成提交结果不明，先用新连接检查历史终态；不能把已经 SUCCESS 的操作覆盖为 FAILED，也不能自动重放不确定是否提交的请求。
5. 单实例部署重启时，先确认旧业务事务已经结束，再核实并恢复遗留 RUNNING；无法确认时保留待核实状态并记录诊断。若支持多实例，增加操作归属/存活判断，避免误判另一实例正在执行的操作。

产物：导入接口、历史接口、事务测试、结构化错误。

完成条件：合法 N 条只增加 N 个电影；最后一条出错及 flush 后注入异常均导致全部领域对象无净增加；失败历史独立保留；成功计数与实际提交数一致。

### P5：导入及历史 Web 界面

1. 在既有菜单增加“导入”和“导入历史”；按用户最终要求，界面仅使用俄语，不要求中文或双语切换，文案进入 `ui-text.js`。
