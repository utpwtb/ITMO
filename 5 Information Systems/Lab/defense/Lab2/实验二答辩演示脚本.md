## 5. 第 3、4 项｜在 IDEA 讲组合唯一性、写锁和版本

**动作 1｜IDEA 定位**　打开 `check()`，依次指第 14 行构造 `MovieKey`、第 15 行 `IS NULL`、第 19 行排除当前电影 ID 和第 22 行抛出 `DUPLICATE_MOVIE`。如果要展示共用校验器，打开普通保存和导入的方法。 [MovieUniquenessValidator.java 第 14 行](../../movie-lab/src/main/java/ru/itmo/movie/service/MovieUniquenessValidator.java) · [MovieService.java 第 117 行](../../movie-lab/src/main/java/ru/itmo/movie/service/MovieService.java) · [MovieService.java 第 193 行](../../movie-lab/src/main/java/ru/itmo/movie/service/MovieService.java)

**俄语直接读**

> По третьему требованию я согласовал с преподавателем новое правило уникальности. Ключ состоит из точного названия фильма и ID режиссёра. Если у режиссёров одинаковые имена, но разные ID, ключи различаются. Если у двух фильмов одно название и у обоих нет режиссёра, ключи совпадают. При редактировании проверка исключает текущий фильм по его ID. Создание, редактирование и импорт вызывают один и тот же валидатор. Это правило проверяет сервис приложения. Для этой пары в базе нет ограничения UNIQUE.

**中文对照**

> 对于第三项，我和老师确认了新的唯一性规则。组合键由电影的精确名称和导演 ID 组成。导演同名但 ID 不同，组合键就不同。同名电影都没有导演时，组合键相同。编辑时按 ID 排除正在编辑的电影。新增、编辑和导入共用同一个校验器。这条规则由应用服务检查，数据库没有给这对字段加 UNIQUE 约束。

**俄语直接读**

> Если два пользователя одновременно создают фильм с одним ключом, оба запроса могли бы сначала не найти дубль. Поэтому транзакция записи сначала блокирует общую строку AppState. Проверка и запись выполняются после получения блокировки. Второй запрос ждёт. Когда первый фиксирует изменения, второй начинает проверку и при READ COMMITTED уже видит сохранённый фильм. #### 第四步｜回到代码解释为什么

打开 [Database.java 第 76 行](../../movie-lab/src/main/java/ru/itmo/movie/persistence/Database.java#L76)。依次指第 76 行设置隔离级别、第 80 行锁住 AppState、第 82 行执行写操作、第 83 行更新版本计数和第 85 行提交。接着打开 [MovieUniquenessValidator.java 第 13 行](../../movie-lab/src/main/java/ru/itmo/movie/service/MovieUniquenessValidator.java#L13)，指查重查询和第 22 行抛出的 `409 DUPLICATE_MOVIE`。

```java
em.createNativeQuery("SET TRANSACTION ISOLATION LEVEL " + (domain ? isolation : "READ COMMITTED")).executeUpdate();
// 第 80 行起，省略超时设置和空值检查
AppState state = domain ? em.find(AppState.class, 1L, LockModeType.PESSIMISTIC_WRITE) : null;
T result = work.apply(em);
if (domain) state.revision++;
em.flush();
tx.commit();
```

**中文**　第一个事务拿锁，查重后写入电影，更新 AppState 并提交。在 SERIALIZABLE 下，已经取得旧快照的等待事务再尝试锁住被改过的行时，可能收到 SQLSTATE 40001。READ COMMITTED 下，后一个事务拿到锁后才执行查重查询，这次查询能看到前一事务提交的电影，所以返回业务上的 409。默认允许重试时，SERIALIZABLE 也能通过，因为失败的事务可以重新开始。

**俄语**　Первая транзакция блокирует AppState, проверяет ключ, сохраняет фильм и обновляет счётчик перед фиксацией. При SERIALIZABLE ожидающая транзакция может получить SQLSTATE 40001, если строка изменилась после получения её снимка. При READ COMMITTED проверка ключа после получения блокировки уже видит зафиксированный фильм и возвращает бизнес-конфликт 409. С повторами SERIALIZABLE тоже проходит, потому что транзакция может начаться заново.

先用 `PESSIMISTIC_WRITE` 锁住预先存在的 `AppState` 行，再执行 `work.apply(em)` 里的查重和写入。锁一直持有到提交或回滚。`READ COMMITTED` 下，后一个拿到锁的事务在查重时能看到前一次提交。应用中的业务写入会因此排队。 [Database.java](../../movie-lab/src/main/java/ru/itmo/movie/persistence/Database.java) 的 `once()` · [Helios 实测隔离级别](../../verification/Lab2/compact-20261110/configuration.json)

```java
private <T> T once(Function<EntityManager, T> work, boolean domain, String isolation) {
    try (EntityManager em = factory.createEntityManager()) {
        EntityTransaction tx = em.getTransaction();
        tx.begin();
        try {
            em.createNativeQuery("SET TRANSACTION ISOLATION LEVEL " + (domain ? isolation : "READ COMMITTED")).executeUpdate();
            int timeout = Integer.parseInt(config("MOVIE_LOCK_TIMEOUT_MS", "10000"));
            if (timeout < 1) throw new IllegalArgumentException("lock timeout must be positive");
            em.createNativeQuery("SET LOCAL lock_timeout = '" + timeout + "ms'").executeUpdate();
            AppState state = domain ? em.find(AppState.class, 1L, LockModeType.PESSIMISTIC_WRITE) : null;
            if (domain && state == null) throw new IllegalStateException("Сначала выполните database/schema.sql");
            T result = work.apply(em);
            if (domain) state.revision++;
            em.flush();
            tx.commit();
            return result;
        } catch (RuntimeException e) {
            if (tx.isActive()) {
                try {
                    tx.rollback();
                } catch (RuntimeException rollback) {
                    e.addSuppressed(rollback);
                }
            }
            throw e;
        }
    }
}
```

```java
        } catch (ReflectiveOperationException e) {
            throw new IllegalStateException(e);
        }
```
