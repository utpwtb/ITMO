# 实验二答辩演示脚本

建议用 **8 分钟**。先展示成功导入，再让文件末条发生重复冲突，随后切换账号对比历史。最后用代码和已保存的 JMeter 结果解释，为什么整批能回滚，并发时也不会插入重复电影。

## 答辩前准备

1. 在 Helios 的 `~/is-lab2-4101` 运行 `python3.11 scripts/helios.py status` 检查实验二实例。按照项目 README 建立 SSH 隧道，打开 [实验二网页](http://127.0.0.1:18083/movie-lab/)。登录完成后再开始共享屏幕。[启动和隧道步骤](../../movie-lab/README.md)
2. 准备普通用户 A、普通用户 B、管理员三个独立浏览器会话。可用不同浏览器配置文件。让管理员先打开 **История импорта**（导入历史），后面用同一批操作 ID 对比。
3. 生成本次专用的两个 JSON 文件。每次彩排或正式演示都重新生成，避免上一次成功导入影响这一次。把命令输出的电影名留在手边，现场可直接复制到筛选框。
4. 预先打开 IDE 中的 `ImportService.java`、`Database.java`、`MovieUniquenessValidator.java)，以及 [C03 的导入回滚断言](../../verification/Lab2/compact-20261110/jmeter/C03/assertions.json)。老师问代码分层时，可以先指一下[包图](../../report/Lab2/uml/packages.pdf)，再打开对应类。[俄语报告 PDF](../../report/Lab2/report.pdf)

在 **Windows 的 Lab 目录**运行下面的 PowerShell。它以项目样例为模板，在系统临时目录生成两份文件。

```powershell
$labTag = "LAB2-$(Get-Date -Format 'MMdd-HHmmss')-$([guid]::NewGuid().ToString('N').Substring(0,6))"
$labDemoDir = Join-Path $env:TEMP $labTag
New-Item -ItemType Directory -Path $labDemoDir | Out-Null

$labSuccess = Get-Content -LiteralPath 'movie-lab/src/main/webapp/examples/import-valid.json' -Raw -Encoding UTF8 | ConvertFrom-Json
for ($i = 0; $i -lt $labSuccess.movies.Count; $i++) {
    $labSuccess.movies[$i].name = "$labTag-$($i + 1)"
    $labSuccess.movies[$i].director.passportID = "$labTag-D1"
}
$labSuccessJson = $labSuccess | ConvertTo-Json -Depth 12
$labSuccessJson | Set-Content -LiteralPath (Join-Path $labDemoDir '01-success.json') -Encoding UTF8

$labRollback = $labSuccessJson | ConvertFrom-Json
$labRollback.movies[0].name = "$labTag-rollback"
$labRollback.movies[0].director.passportID = "$labTag-D2"
$labRollback.movies[0].director.name = "$labTag-rollback-director"
$labRollback.movies[0].director.location.name = "$labTag-rollback-location"
$labRollback | ConvertTo-Json -Depth 12 | Set-Content -LiteralPath (Join-Path $labDemoDir '02-duplicate-last.json') -Encoding UTF8

Write-Output "Files: $labDemoDir"
Write-Output "Success movie: $($labSuccess.movies[0].name)"
Write-Output "Duplicate movie: $($labSuccess.movies[1].name)"
Write-Output "Rolled-back movie: $($labRollback.movies[0].name)"
```

## 1. 开场 · 30 秒

> 我在实验一的电影管理系统上增加了 JSON 批量导入、按角色查看导入历史，以及只在业务层执行的「电影名称＋导演」唯一性规则。我会先演示整批成功和整批失败，再展示并发测试结果。

## 2. 成功导入两部电影 · 1 分钟

1. 展开 `01-success.json` 的一条记录，指给老师看 `coordinates` 和嵌套在同一记录里的 `director.location`。两部电影共用同一个导演护照号。
2. 普通用户 A 打开 **Импорт JSON** → **Выбрать файл** → **Загрузить**，选择 `01-success.json`。记下响应里的操作 ID 和新增数量 `2`。
3. 在 **Фильмы** 查看新电影。需要定位时，在筛选区选择 **Название**，把完整电影名填进 **Точное значение**，勾选 **Включить фильтр**，点击 **Применить**。

**指着代码讲。** 浏览器把文件放入 `FormData`。`ImportResource.upload()` 接收上传，`ImportParser.parse()` 校验结构和字段，`ImportService` 按护照号复用资料一致的人物。这个例子提交的是两部电影，它们关联同一个导演，所以历史里的 `2` 是电影数。[上传入口](../../movie-lab/src/main/java/ru/itmo/movie/web/ImportResource.java) · [解析校验](../../movie-lab/src/main/java/ru/itmo/movie/service/ImportParser.java)

## 3. 让最后一条撞重，现场展示整批回滚 · 2 分钟

1. 展示 `02-duplicate-last.json`。第一条电影名以 `-rollback` 结尾，并使用新导演及地点。第二条沿用刚成功入库的电影名称和导演资料，会撞上同一个组合键。
2. 仍用 A 上传。预期看到 `DUPLICATE_MOVIE`、第二条的字段路径 `movies[1].director` 和失败操作 ID。这里的接口响应是 HTTP 409。
3. 在 **Фильмы** 按完整名称查 `-rollback` 那部电影，预期无匹配。再查成功批次的第二部，预期仍能找到原有电影。
4. 打开 **История импорта**。对照刚记下的两个操作 ID，成功行显示 **Успешно** 且 **Добавлено** 为 `2`，失败行显示 **Ошибка**，新增数量为 `—`。

**指着代码讲。** `ImportService.upload()` 先用短事务写入 `RUNNING`。然后一次 `db.write(...)` 包住整个循环。每次 `saveImported(em, movie)` 都使用这个事务传进来的同一个 `EntityManager`。第一条虽已执行 `flush()`，提交仍要等整批结束。第二条抛错时，整批电影和新建的关联对象一起回滚。随后另开短事务保存 `FAILED`。成功时则把 `SUCCESS` 和电影放在同一次提交里。[导入事务边界](../../movie-lab/src/main/java/ru/itmo/movie/service/ImportService.java) · [单条保存的 flush](../../movie-lab/src/main/java/ru/itmo/movie/service/MovieService.java)

如果老师想看普通字段校验，再上传 [invalid-last-field.json](../../movie-lab/src/test/resources/import/invalid-last-field.json)。末条 `length=0` 会在字段预检阶段被拒绝。前面的末条撞重，以及新 C03 对获胜文件和数据库最终状态的核对，用来说明写入之后也能回滚。[字段校验实测](../../verification/Lab2/compact-20261110/functional/invalid-last-field.json)

## 4. 切换会话，证明历史按角色可见 · 1 分钟

在 A 的历史里指出本次成功和失败的操作 ID。打开普通用户 B 的历史，刚才 A 的两个 ID 都不出现。再切到管理员历史，找回这两个 ID，并指出 **Пользователь**（用户）列的发起人是 A。管理员预先打开的页面会在轮询后出现新记录。

**指着代码讲。** `ImportHistoryService.list()` 读取数据库中的角色。普通用户的列表和总数查询都带所有者条件，`get()` 查单条时也检查所有者。历史页独立轮询，因此一次失败可以更新历史，电影集合的 `revision` 不需要变化。[历史权限](../../movie-lab/src/main/java/ru/itmo/movie/service/ImportHistoryService.java) · [角色和历史表迁移](../../movie-lab/database/migrations/003_lab2_roles_imports.sql)

## 5. 讲清查重、加锁和版本 · 2 分钟

按下面的顺序定位代码，每处讲一句即可。

| 代码位置 | 答辩时怎么讲 |
|---|---|
| [`MovieUniquenessValidator.check()`](../../movie-lab/src/main/java/ru/itmo/movie/service/MovieUniquenessValidator.java) | 普通新建、编辑和导入共用这个校验器。组合键使用原样电影名和导演的 `Person.id`。同名且导演都为空也会冲突。同名导演如果是不同的人，ID 不同，就能区分。新组合约束只在业务层检查。 |
| [`Database.once()`](../../movie-lab/src/main/java/ru/itmo/movie/persistence/Database.java) | 先设隔离级别，锁住 `AppState(id=1)`，再查重并写入。假设 A 和 B 同时创建同一个组合，B 等 A 提交后才执行查重，在 `READ COMMITTED` 下能看到 A 刚提交的记录。代价是其他领域写入也要排队。 |
| [`MovieService.saveInTransaction()` 和 `delete()`](../../movie-lab/src/main/java/ru/itmo/movie/service/MovieService.java) | 共享行锁让写入按顺序执行。编辑时还要核对客户端打开表单时拿到的版本，防止后到的旧表单覆盖先提交的新值。 |

打开 `Database.once()` 时，可以停在这一小段源码，指出锁、业务执行和提交的顺序。

```java
AppState state = domain ? em.find(AppState.class, 1L, LockModeType.PESSIMISTIC_WRITE) : null;
if (domain && state == null) throw new IllegalStateException("Сначала выполните database/schema.sql");
T result = work.apply(em);
if (domain) state.revision++;
em.flush();
tx.commit();
```

**有时间再加演。** A、B 都打开刚导入的同一部电影的 **Редактировать** 表单，各填一个不同的 **Слоган**。先让 A 点击 **Сохранить**，再让 B 直接保存原表单。预期 B 收到冲突，重新打开后仍是 A 已提交的值。请用本次生成的电影做演示。

## 6. 展示实测证据并收尾 · 1 分 30 秒

1. 打开 [JMeter 场景](../../movie-lab/jmeter/lab2-concurrency.jmx) 或[场景表](../../movie-lab/jmeter/README.md)，指出测试覆盖创建、编辑、删除和导入。多个线程各用自己的会话，在同步点之后请求同一个对象或组合键。
2. [C01](../../verification/Lab2/compact-20261110/jmeter/C01/assertions.json) 展示编辑与删除竞争，20 轮里 9 次编辑获胜、11 次删除获胜。[C02](../../verification/Lab2/compact-20261110/jmeter/C02/assertions.json) 展示组合唯一性，20 次创建成功、180 次预期拒绝。[C03](../../verification/Lab2/compact-20261110/jmeter/C03/assertions.json) 展示部分重叠导入，20 次冲突均发生在第二条，数据库只留下获胜文件。
3. Helios 上三个场景各完成 20 轮，共 280 个目标请求，非预期失败为 0。指出数据库核对与 HTTP 响应都通过，并用 `AppState` 锁和版本检查说明为什么结果符合预期。[本轮汇总](../../verification/Lab2/compact-20261110/jmeter/summary.json)

老师问「谁管理事务」时，打开 [persistence.xml](../../movie-lab/src/main/resources/META-INF/persistence.xml)，指出项目实际使用 `RESOURCE_LOCAL` 和 `EntityTransaction`，由 `Database` 显式执行 `begin()`、`commit()`、`rollback()`。EJB 容器事务、JTA 和 Spring 声明式事务可以按[答辩提纲](README.md)作理论对照。

## 俄语口播备用

> Сначала я импортирую два фильма из одного JSON-файла. Оба фильма связаны с одним режиссёром.
>
> Во втором файле первая запись новая, а вторая дублирует уже сохранённый фильм. Из-за этого откатывается весь импорт, но запись об ошибке остаётся в истории.
>
> Обычный пользователь видит только свои операции. Администратор видит операции всех пользователей.
>
> Перед проверкой уникальности приложение блокирует строку AppState. При редактировании оно также проверяет версию, которую отправил клиент.
