# ЛР2: тезисы для защиты

1. **Бизнес-логика.** Правила предметной области и сценарии работы принадлежат service: проверка фильма, разрешение Person по паспорту, программная уникальность, импорт целиком, права истории. web принимает запрос и вызывает сервис; persistence управляет EntityManager и транзакциями; domain задаёт сущности и ограничения. Импорт и обычное сохранение используют общий валидатор.

2. **EJB.** Enterprise Beans предоставляют контейнерные сервисы для серверной логики. Stateless Session Bean не хранит разговорное состояние клиента, Stateful сохраняет его между вызовами, Singleton имеет один экземпляр на приложение. Message-Driven Bean асинхронно обрабатывает сообщения. Это приложение использует CDI @ApplicationScoped, не выдаёт их за EJB.

3. **Жизненный цикл Session Bean.** Stateless: создание, внедрение, PostConstruct, пул вызовов, PreDestroy. Stateful дополнительно может быть пассивирован и активирован; разговор заканчивается remove. Singleton создаётся один раз, возможен Startup; контейнер управляет конкуренцией. CDI @ApplicationScoped в нашем коде не приобретает автоматически CMT-семантику EJB.

4. **ACID.** Atomicity: Movie и все новые вспомогательные объекты коммитятся вместе; ошибка после flush откатывает всё. Consistency: Bean Validation, бизнес-ключ и прежние ограничения PostgreSQL. Isolation: READ COMMITTED плюс AppState lock и ожидаемая версия. Durability: сохранённые роли и история переживают перезапуск. FAILED намеренно сохраняется другой транзакцией, потому что это журнал операции, а не частично импортированный фильм.

5. **Конкурентные конфликты.** Dirty read — чтение незафиксированного; non-repeatable read — значение меняется между чтениями; phantom — меняется набор строк; lost update — новая запись затёрта старым вводом; write skew — разные строки совместно нарушают правило. PostgreSQL READ UNCOMMITTED ведёт себя как READ COMMITTED. SERIALIZABLE может отменить транзакцию с 40001; требуется новый EntityManager и повтор всей транзакции. Итоговый выбор обосновывается реальными результатами в verification/Lab2/isolation-analysis.md.

6. **Границы.** Один HTTP-запрос не равен одной транзакции автоматически. T1 фиксирует RUNNING; T2 — весь файл и SUCCESS; после подтверждённого отката T3 фиксирует FAILED. Flush отправляет SQL, но не коммитит. Наименование+режиссёр проверяется после получения общей строки-блокировки, иначе два запроса могут оба не увидеть ещё отсутствующую строку. @Version сама по себе не защищает уникальность новых объектов.

7. **JTA.** Jakarta Transactions включает UserTransaction, TransactionManager и Synchronization; распределённый commit может объединять XA-ресурсы. Контейнер координирует enlist/delist и prepare/commit. Здесь один PostgreSQL и RESOURCE_LOCAL с EntityTransaction; JTA не используется. Три независимых локальных EntityManager имеют реальные отдельные транзакции.

8. **Jakarta EE.** Декларативные транзакции: EJB CMT с TransactionAttribute и CDI/Jakarta Transactions @Transactional, включая REQUIRED/REQUIRES_NEW и правила rollback. Программные: UserTransaction в JTA или EntityTransaction в RESOURCE_LOCAL. Простое добавление аннотации к классу не изменит существующую локальную конфигурацию. Вызов собственного метода также требует учитывать обход контейнерного proxy.

9. **Spring.** Платформенный TransactionManager, TransactionTemplate и @Transactional; propagation, isolation, timeout, readOnly, rollbackFor. Стандартные proxy-перехватчики не охватывают self-invocation. REQUIRES_NEW приостанавливает внешнюю транзакцию и создаёт независимую; REQUIRED присоединяется. Для независимого журнала ошибка/rollback внешней транзакции не должна откатывать запись о неуспехе. Эти сведения теоретические: Spring в проекте не используется.

Для демонстрации: загрузить examples/import-valid.json через Web; повторить файл и показать полный отказ с FAILED; открыть историю обычного пользователя и администратора; показать JMX и реальные JTL/DB assertions; объяснить реальный AppState lock, границу commit, роль версии и выбор уровня изоляции.
