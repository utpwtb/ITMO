### 1. 线程组：C01、C02、C03 的参数从哪来？

**在 GUI 看**　展开线程组 `${__P(scenario,C02)}`。右侧的线程数是 `${__P(threads,2)}`。轮数在它下面的 **Fresh target per round**。

**中文**　三个场景共用一份 JMX。Python 启动时传入场景编号、线程数和轮数。C01 和 C03 各有 2 个线程，C02 有 10 个，完整测试每组跑 20 轮。`${__P(threads,2)}` 里的 `2` 是没有传线程数时的默认值。外层循环执行一次，所以每个线程只登录一次。内层循环才决定业务请求执行多少轮。

**Русский**　Один файл JMX используется для трёх сценариев. При запуске Python передаёт номер сценария, число потоков и число раундов. В C01 и C03 по два потока, в C02 — десять. В полном прогоне каждый сценарий выполняется двадцать раундов. Число `2` в выражении `${__P(threads,2)}` — значение по умолчанию. Внешний цикл выполняется один раз, поэтому каждый поток входит в систему один раз. Внутренний цикл задаёт число раундов.

### 2. 登录：`Load private credentials` 做什么？

**在 GUI 看**　在线程组下找 **Load private credentials**，它在同一级的 **Login** 上面。点开后，右侧脚本文件指向 `jmeter/init.groovy`。再展开 **Login**，下面有 **Extract CSRF**。

**中文**　`Load private credentials` 给当前线程选一个测试账号，并准备登录请求体。下面的 `Login` 才真正发送 `POST /auth`。Cookie Manager 给每个线程保留自己的会话，`Extract CSRF` 从登录响应里取出 token。后续写请求带着这个会话 Cookie 和 `X-CSRF-Token`。

**Русский**　`Load private credentials` выбирает тестовую учётную запись для текущего потока и подготавливает тело запроса. Затем `Login` отправляет `POST /auth`. Cookie Manager хранит сеанс каждого потока отдельно, а `Extract CSRF` извлекает токен из ответа. Последующие запросы записи отправляют cookie сеанса и заголовок `X-CSRF-Token`.

### 3. 每轮取数据：`Prepare shared fixture` 和 `fixture.json` 是什么？

**在 GUI 看**　展开 **Fresh target per round → Prepare shared fixture**。这是循环里的第一个节点，右侧指向 `jmeter/prepare.groovy`。

**中文**　`fixture.json` 是 Python 为本次测试生成的**操作清单**。脚本根据「当前轮次 + 当前线程编号」选一条 `action`，再把方法、路径、请求体或文件路径填进 JMeter 变量。以 C03 为例，操作清单写着两个线程都发 `POST imports`，但一个上传 `r0-p0.json`，另一个上传 `r0-p1.json`。这两份 `r0-p*.json` 里面才是发给应用的电影数据。

**Русский**　`fixture.json` — это список действий, который Python готовит для текущего прогона. Скрипт выбирает действие по номеру раунда и номеру потока. Из него он берёт HTTP-метод, путь, тело запроса или путь к файлу. Например, в C03 оба потока отправляют `POST /imports`. Первый загружает `r0-p0.json`, второй — `r0-p1.json`. Данные фильмов находятся в этих двух файлах.

### 5. 检查结果：为什么 `409` 也能显示通过？

**在 GUI 看**　展开目标请求下面的 **Business status and raw result**，右侧指向 `jmeter/record.groovy`。

**中文**　`record.groovy` 检查当前响应是否符合这个操作的预期。比如 C01 的归档第一轮，编辑返回 `200`，删除因为旧版本返回 `409`。两条都符合预期，所以都显示 `passed: true`。整个场景结束后，Python 的 `verify()` 再检查最终数据。C01 要确认新标语和版本确实已保存，或者电影确实已被删除。C02 要确认每轮只保存一部匹配的电影。C03 要确认失败文件的第一条也被回滚，数据库里只留下成功文件的数据。

**Русский**　`record.groovy` проверяет, соответствует ли конкретный ответ ожидаемому результату. Например, в первом сохранённом раунде C01 редактирование получило `200`, а удаление со старой версией — `409`. Оба ответа ожидаемые, поэтому у обоих стоит `passed: true`. После завершения сценария функция `verify()` проверяет итоговые данные. В C01 она проверяет новый слоган и версию либо отсутствие фильма. В C02 она проверяет, что в каждом раунде сохранился только один фильм с нужным ключом. В C03 она проверяет, что откат затронул и первую запись отклонённого файла, а в базе остались только данные успешного импорта.
