## B1 后端结构与技术职责 / Архитектура и технологии

**操作：** 打开项目 Java 包结构 `web`、`service`、`persistence`、`domain`。只讲后端，不讲前端代码。

> Серверная часть имеет слоистую архитектуру. Пакет web содержит REST-ресурсы, фильтр авторизации и обработчик ошибок. Пакет service содержит бизнес-логику. Компонент Database управляет доступом к данным и транзакциями. В пакете domain находятся сущности и их отображение на таблицы базы данных.

**中文：** 后端采用分层架构。web 放 REST 资源、身份过滤和异常处理；service 放业务；Database 管理数据访问和事务；domain 放实体及映射。

> Jakarta EE задаёт набор серверных спецификаций. Payara предоставляет среду выполнения приложения. Jakarta Persistence, или JPA, определяет API работы с сущностями. EclipseLink реализует JPA и обращается к PostgreSQL через JDBC-драйвер. PostgreSQL хранит данные и контролирует ограничения.

**中文：** Jakarta EE 提供一组规范，Payara 提供运行环境；JPA 是持久化 API 规范，EclipseLink 是实现，通过 JDBC 驱动访问 PostgreSQL。PostgreSQL 保存并约束数据。

**提示：** 不把这些技术全部称为“框架”；不把 `Database` Java 类等同于 PostgreSQL；不把分层直接说成完整的经典 MVC。`MovieService` 同时包含查询和持久化操作，项目没有额外独立 Repository 层。

## B2 CDI、作用域和注入 / CDI, области видимости и внедрение зависимостей

**操作：** 展示 `MovieResource` 的 `@RequestScoped`、`@Inject`；`MovieService`、`Database` 的 `@ApplicationScoped`。

> Компоненты создаются и связываются контейнером CDI. Аннотация Inject позволяет получить зависимость без ручного создания объекта в ресурсе. MovieResource имеет область запроса: его контекст ограничен одним HTTP-запросом. MovieService и Database имеют область приложения. При этом EntityManager не разделяется между запросами: для каждой операции создаётся отдельный экземпляр.

**中文：** CDI 容器负责创建和连接组件。Inject 注入依赖；REST Resource 是请求作用域；Service 和 Database 是应用作用域。共享 Database 不意味着共享 EntityManager，每次数据库操作创建独立实例。

**追问要点：** `@ApplicationScoped` 不会自动串行化方法，也不自动提供数据库事务。当前写请求的协调来自 `Database.write()` 中的数据库锁。

## B3 一次新增请求 / Путь запроса на создание

**操作：** 展示 `ApiApplication` 的 `/api`、`MovieResource.create()`、`MovieService.save()`。以 `POST /movie-lab/api/coordinates`，请求体 `{"x":826,"y":-1}` 为例。

> Рассмотрим создание координат. Запрос сначала проходит проверку сессии и CSRF-токена. REST-ресурс получает тип объекта из пути, а значения полей — из JSON. Он вызывает метод save сервиса. Отсутствие идентификатора в аргументе означает создание нового объекта, а не сохранение пустого идентификатора в базе.

**中文：** 请求先通过会话与 CSRF 检查，REST 入口从路径拿类型、从 JSON 拿字段，并调用 save。传入的 ID 参数为 null 表示新增，不表示最终 ID 为空。

> Сервис создаёт сущность, преобразует значения к нужным Java-типам и проверяет ограничения. Ссылки на другие объекты разрешаются по существующим идентификаторам. После успешного сохранения и фиксации транзакции ресурс возвращает созданный объект и статус двести один. Если возникает ошибка, клиент получает ответ об ошибке, а не ответ об успешном создании.

**中文：** Service 创建实体、转型、检查约束、按已有 ID 解析关联。事务提交后返回创建对象和 201；异常时返回错误响应。

**源码准确性：** `save()` 的业务回调先返回实体给 `Database.write()`，外层还要更新 revision、flush 和 commit，最后才向 Resource 返回。不能把回调 `return entity` 当成整个事务完成。

## B4 JPA 实体、关系、ID 和日期 / Сущности, связи и автоматически создаваемые поля

**操作：** 展示 `Movie`、`Coordinates`、`Person`、`Location` 的实体注解与 `schema.sql`。

> Аннотация Entity обозначает сохраняемую сущность. Id задаёт первичный ключ. Для генерации идентификаторов используется стратегия IDENTITY, а в PostgreSQL настроены identity-колонки. Поэтому идентификатор формируется средствами базы данных. Удаление записи не требует повторного использования её номера.

**中文：** Entity 标记实体，Id 指定主键。IDENTITY 与数据库 identity 列对应，所以 ID 由数据库生成。删除记录后不要求复用号码。

> Связи фильма с координатами и людьми описаны как ManyToOne. Несколько фильмов могут ссылаться на один объект. В таблице фильма хранятся внешние ключи. Enum сохраняется в виде строки, поэтому база содержит понятные значения жанра и рейтинга, а не порядковые номера перечисления.

**中文：** 电影到坐标和人物使用多对一，多个电影可共享对象，电影表保存外键。枚举按字符串保存，避免依赖枚举顺序。

> Дата создания фильма задаётся автоматически. В базе используется значение CURRENT_DATE по умолчанию. Поле не включается JPA в INSERT и UPDATE, а после записи сущность перечитывается. В Java временная дата нужна для проверки обязательного поля до вставки. Клиенту запрещено присваивать идентификатор и дату создания через метод сохранения.

**中文：** 日期由数据库默认值产生；JPA 不把该字段写入 INSERT/UPDATE，之后 refresh 读回。Java 的临时日期满足插入前校验。API 禁止客户端指定自动字段。

**提示：** `@Column(updatable=false)` 约束 ORM 生成的 SQL，不意味着数据库管理员直接发 SQL 也不能改这个列。不要把 API/ORM 的不可修改策略说成数据库具有额外的不可变触发器。

## B5 EntityManager 和事务 / EntityManager и транзакции

**操作：** 打开 `Database.init()`、`read()`、`write()`、`close()`。

> EntityManagerFactory создаётся при инициализации компонента и закрывается при его уничтожении. Для каждой операции создаётся отдельный EntityManager. Он содержит контекст персистентности: отслеживает загруженные и изменяемые сущности. Конструкция try-with-resources гарантирует его закрытие после завершения операции.

**中文：** 工厂在初始化时创建、销毁时关闭；每次操作创建独立 EntityManager。它的持久化上下文跟踪实体，try-with-resources 确保关闭。

> В этом проекте используются локальные транзакции JPA. В методе write транзакция начинается явно через begin. Затем выполняется бизнес-операция, увеличивается ревизия коллекции и вызываются flush и commit. При исключении активная транзакция откатывается. Управление транзакцией реализовано явно, а не аннотацией Transactional.

**中文：** 这里是 `RESOURCE_LOCAL`，显式 begin、业务操作、revision 增加、flush、commit；异常回滚，不是靠 @Transactional 实现。

> Persist делает новый объект управляемым. Изменения уже загруженной управляемой сущности отслеживаются JPA, поэтому для каждого изменения не требуется отдельный вызов update. Flush синхронизирует изменения с базой, но не фиксирует транзакцию. Если после flush возникает ошибка до успешного commit, изменения этой транзакции могут быть отменены откатом.

**中文：** persist 让新对象受管理；已加载的受管理实体会被跟踪，不必手写每次 update。flush 同步但不提交；成功 commit 前出错，同一事务中修改可回滚。

**追问要点：** `read()` 没有显式开启同样的写事务，不把所有读取称作同一个一致性快照。`save()` 内的 `flush()`/`refresh()` 与外层的 `flush()`/`commit()` 分属不同职责，但在同一个写事务中。

## B6 并发控制、版本和自动更新 / Конкурентный доступ, версии и обновление клиентов

**操作：** 展示 `Database.write()` 中 `PESSIMISTIC_WRITE`、`Movie.version` 的 `@Version`、`save()` 中请求版本比较。

> Для операций изменения через Database используется пессимистическая блокировка одной строки AppState. Она заставляет такие записи выполняться последовательно. Это простой способ согласовать обычные изменения и массовые операции. Недостаток — ограниченная параллельность записи, потому что блокируется общий координационный объект.

**中文：** Database 写事务锁定同一个 AppState 记录，让经由该入口的写操作串行。实现简单，但写并行性受限。它没有锁住整张业务表；也不能阻止所有绕过应用、直接修改其他行的 SQL。

> Дополнительно у сущностей есть поле Version для оптимистической проверки JPA. При редактировании клиент передаёт версию, которую получил при открытии формы. Сервис сравнивает её с текущей версией объекта. Если они различаются, возвращается конфликт. Эта проверка защищает от отправки устаревшей формы даже тогда, когда сервер заново прочитал актуальную сущность.

**中文：** @Version 提供 JPA 更新冲突检查；额外比较表单打开时版本与当前实体版本，识别旧表单。仅加载最新实体再写入旧字段，不能让 JPA 自动知道表单旧在哪里。

> Ревизия коллекции отличается от версии отдельного объекта. Ревизия увеличивается в той же транзакции, что и изменения данных. Клиенты проверяют её примерно каждые две секунды и при изменении загружают актуальный список. Открытая форма и её исходная версия при этом не перезаписываются, чтобы сохранить ввод пользователя.

**中文：** 集合 revision 与单实体 version 不同。revision 随写事务一起提交；客户端约两秒轮询，变化后加载列表，但不覆盖编辑输入或编辑版本。

**实现边界：** 这是轮询，不是 WebSocket；不是承诺零延迟。客户端处于特殊操作页面时，当前刷新逻辑不重绘电影列表；返回列表会重新加载。结果弹窗是操作完成时的快照，不会随轮询改变历史结果。

## B7 校验、外键和异常响应 / Проверки, внешние ключи и ответы об ошибках

**操作：** 展示 `Coordinates.x` 的 `@NotNull`、`@Max(826)`；`Person.passportID` 的约束；`MovieService.save()` 中显式验证与重复查询；`ErrorMapper`。

> В сервисе сначала проверяются формат и диапазон Java-значений. Затем Bean Validation проверяет ограничения сущности: например NotNull, Positive, Size и Max. Для номера паспорта выполняется проверка существующих значений. Независимо от этих проверок, база содержит собственные ограничения и уникальный индекс.

**中文：** 先转型并检查格式、类型范围，再执行 Bean Validation，护照另查重。数据库仍独立保留约束及唯一性保障。

> Исключения преобразуются в JSON-ответы компонентом ErrorMapper. Некорректные данные обычно дают код четыреста. Отсутствие авторизации даёт четыреста один, неверный CSRF-токен — четыреста три. Если объект не найден, возвращается четыреста четыре. Конфликт версии или повторяющийся паспорт дают четыреста девять. Неожиданная внутренняя ошибка даёт пятьсот, а технические подробности записываются в журнал.

**中文：** ErrorMapper 统一组织 JSON 错误。通常：非法输入 400、未登录 401、CSRF 403、不存在 404、版本或重复护照冲突 409、未预期内部错误 500。过滤器的 401/403 是直接构造响应，并非先抛异常再进入 ErrorMapper。

**提示：** 当前通用 `PersistenceException` 映射为 409；它并未精细区分所有数据库故障。不能说“每一种数据库错误都一定被正确归类为约束冲突”。

## B8 查询、精确匹配、分页与注入防护 / Запросы, точное совпадение и пагинация

**操作：** 展示 `MovieService.page()` 的列白名单、`:value`、`LEFT JOIN`、COUNT、`setFirstResult()`、`setMaxResults()`。

> Для запросов используется JPQL: он обращается к сущностям и их полям. Обычная фильтрация использует равенство, а не LIKE. Значение фильтра передаётся отдельным параметром. Названия колонок выбираются из разрешённого списка, поскольку имя поля сортировки нельзя безопасно заменить обычным параметром значения.

**中文：** JPQL 面向实体和字段；精确筛选使用等号；值参数化；排序字段从白名单选择，不能把用户字符串直接拼进列名位置。

> Для необязательных участников используются левые соединения. Поэтому фильм без режиссёра не пропадает из списка при сортировке. Для фильмов пагинация выполняется на сервере: отдельно вычисляется общее количество записей и загружается нужная страница. При одинаковых значениях дополнительная сортировка по идентификатору делает порядок стабильным.

**中文：** LEFT JOIN 保留没有可选人物的电影。电影分页在服务器计算总数并查询当前页；同值时追加 ID 排序，保证稳定。

**实现边界：** 辅助对象接口当前返回完整列表，其分页在客户端完成；不要说四类对象都用数据库分页。分页 COUNT 与列表查询是两条查询，当前 `read()` 不保证它们在并发写入时具有完全一致的快照。

## B9 五项特殊操作的后端实现 / Реализация пяти специальных операций

**操作：** 打开 `MovieService` 的五个方法。每个方法说明一句目的、查询方式和事务性质即可；老师追问再展开。

> Метод deleteByBoxOffice находит все фильмы с заданными сборами и удаляет их как управляемые сущности в одной транзакции. Метод average выполняет JPQL-запрос с агрегатом AVG. Для пустого результата среднее возвращается как null. Метод prefix экранирует служебные символы LIKE и добавляет знак процента только в конце подготовленного префикса.

**中文：** 删除先查全量匹配再逐实体 remove，处于同一事务。平均值用 JPQL AVG，空集合返回 null。前缀先转义 LIKE 元字符，再在末尾加通配符。

> Метод redistribute вычисляет доступную сумму наград, целую долю и остаток. Целевые фильмы заранее упорядочены по идентификатору. Метод award выбирает фильмы по условию «продолжительность строго больше порога» и увеличивает их награды. Перед приведением результата к int проверяется переполнение. Если одна запись приводит к ошибке, вся операция изменения должна откатиться.

**中文：** 转移计算总量、商和余数，目标按 ID 排序。加奖使用严格大于，先按宽类型计算，再检查 int 溢出。任一记录出错，整项写事务回滚。

**必须如实说明的原题歧义：** 原文禁止直接使用数据库函数和过程，却未进一步界定是否包含内置聚合函数。当前 `average()` 确实使用 `AVG`，不能念成“所有计算都在 Java 内存完成”或“完全不使用数据库函数”。老师若要求连 AVG 也禁用，这一处需要改为业务层读取数值后计算；本稿只解释当前实现，不声称已获得教师认可。

**可直接回答：**

> Хранимых бизнес-процедур в проекте нет. Перераспределение и начисление наград реализованы в Java-сервисе. Для среднего сейчас используется стандартный агрегат AVG в JPQL. Если запрет в задании распространяется и на встроенные агрегаты, эту часть нужно вычислять в Java.

**中文：** 没有自定义存储业务过程，改奖算法在 Java；平均值当前确实调用 JPQL AVG。如果禁令也包含内置聚合，这部分需改为 Java 计算。

## B10 密码、Session 和 CSRF / Пароли, сессии и CSRF

**操作：** 展示 `AuthService.hash()`、`credentials()`、`authenticate()`；`AuthResource.session()`；`AuthFilter.filter()`。不显示真实密码、令牌或服务器凭据。

> Пароли не сохраняются в открытом виде. Используется PBKDF2 с HMAC-SHA-256, индивидуальной случайной солью и шестьюстами тысячами итераций. При входе вычисляется производное значение для введённого пароля и сравнивается с сохранённым. Соль хранится вместе с хешем и не является секретным паролем.

**中文：** 密码不存明文；使用 PBKDF2-HMAC-SHA256、独立随机盐和 60 万次迭代。登录重新推导后比较。盐与哈希一起保存，盐不是密码。

> После входа сервер создаёт новую HTTP-сессию и CSRF-токен. Cookie позволяет связать последующие запросы с сессией. Для операций изменения фильтр дополнительно проверяет токен. Это разные механизмы: сессия подтверждает состояние входа, а токен помогает защитить запросы от подделки с другого сайта. При выходе сессия уничтожается.

**中文：** 登录后新建 Session 和 CSRF token；Cookie 关联会话，写请求额外校验 token。Session 确认登录状态，CSRF 防跨站请求伪造。退出销毁会话。

**实现边界：** 所有账号当前具有相同集合操作权限；创建者没有独占修改、删除权。普通标签共享 Cookie，在一页重新登录会使另一页旧 token 失效；演示双账号用独立会话。

## C1 为什么不直接在 Resource 写所有逻辑 / Почему логика вынесена в сервис?

> Ресурс отвечает за HTTP, а сервис — за правила предметной области. Такое разделение уменьшает связанность и позволяет тестировать бизнес-логику без запуска веб-интерфейса. Один и тот же сервис можно вызывать из разных входных компонентов.

**中文：** Resource 管 HTTP、Service 管业务，便于复用和脱离界面测试。

## C2 JPA 与 EclipseLink 的区别 / Чем JPA отличается от EclipseLink?

> JPA — это спецификация и API. EclipseLink — конкретная реализация. В коде я в основном использую EntityManager и аннотации JPA, а провайдер выполняет отображение и обращение к базе.

**中文：** JPA 是规范与接口，EclipseLink 是提供实际映射和数据库交互的实现。

## C3 Hibernate Validator 是不是 Hibernate ORM / Используется ли здесь Hibernate ORM?

> В тестовых зависимостях есть Hibernate Validator. Это реализация Bean Validation, а не Hibernate ORM. Для ORM в этом проекте используется EclipseLink.

**中文：** 测试依赖中的 Hibernate Validator 是校验实现，不代表项目用 Hibernate ORM；ORM 是 EclipseLink。

## C4 为什么工厂共享而 EntityManager 不共享 / Почему EntityManager создаётся отдельно?

> Фабрика рассчитана на повторное использование. EntityManager содержит изменяемый контекст персистентности и не предназначен для совместного использования несколькими потоками. Отдельный экземпляр ограничивает время жизни управляемых сущностей одной операцией.

**中文：** 工厂复用；EntityManager 有可变上下文，不适合多线程共享，每次操作独立管理实体。

## C5 为什么修改时没有调用 persist / Как сохраняются изменения существующего объекта?

> При изменении сервис загружает существующую сущность через EntityManager. Она уже управляемая, поэтому JPA отслеживает изменения её полей. Persist используется для нового объекта. При flush изменения управляемого объекта синхронизируются с базой.

**中文：** 已查出的实体处于受管理状态，JPA 跟踪字段变化；persist 用于新对象。

## C6 flush 后还能回滚吗 / Можно ли отменить изменения после flush?

> Да, если изменения относятся к той же транзакции и она ещё не была успешно зафиксирована. Flush отправляет изменения в базу, а commit завершает транзакцию. Это разные этапы.

**中文：** 可以，前提是同一事务且尚未成功提交。flush 发往数据库，commit 完成提交。

## C7 既然有悲观锁，为什么还比较版本 / Зачем проверять версию при наличии блокировки?

> Блокировка действует во время серверной транзакции. Пользователь может редактировать форму значительно дольше, уже после завершения запроса чтения. Версия позволяет обнаружить, что форма была открыта до чужого изменения. Эти механизмы защищают разные интервалы времени.

**中文：** 锁覆盖服务器事务，表单可能编辑很久；版本检查识别表单打开之后发生的变化，二者保护的时间范围不同。

## C8 @Version 为什么不够 / Почему нужна ручная проверка версии формы?

> Если сервер загрузил новую версию сущности и затем записал в неё значения из старой формы, JPA не знает, когда эта форма была открыта. Поэтому я отдельно сравниваю версию из запроса с текущей версией сущности. Аннотация Version обеспечивает проверку конкурентного изменения при записи через JPA.

**中文：** 服务端读了最新实体后写旧表单，JPA 不知道表单来自旧版本；请求版本比较负责补齐这一点。

## C9 version 与 revision 有何区别 / Чем версия объекта отличается от ревизии коллекции?

> Версия относится к отдельному объекту и помогает обнаруживать конфликты его изменения. Ревизия — общий сигнал о выполненной записи в приложении. Она сообщает клиенту, что список нужно обновить, но не указывает, какой именно объект изменился.

**中文：** version 管单对象冲突，revision 是应用写入变化信号，不直接说明哪个对象改变。

## C10 为什么不用 CascadeType.REMOVE 删除人物 / Почему нет каскада REMOVE от фильма к человеку?

> Человек может быть общим для нескольких фильмов. Удаление одного фильма не должно удалять этого человека и нарушать другие связи. Поэтому каскад выбран в направлении зависимостей: от удаляемого справочного объекта к использующим его фильмам. Он реализован бизнес-логикой и внешними ключами базы.

**中文：** 人物可能被多部电影共享，不能删一部电影就删除人物。当前按依赖方向由业务与数据库外键执行级联。

## C11 为什么查询里用 LEFT JOIN / Зачем используются левые соединения?

> Связанные участники необязательны. Внутреннее соединение исключило бы фильмы без соответствующего человека. Левое соединение сохраняет такие фильмы в результате.

**中文：** 关联人物可选，内连接会排除缺失关联的电影，左连接保留它们。

## C12 参数化查询能防止所有注入吗 / Достаточно ли параметров для сортировки?

> Значения передаются через параметры. Но имя сортируемого поля является частью структуры запроса. Поэтому для имён полей дополнительно используется белый список, а пользовательский текст не вставляется туда напрямую.

**中文：** 参数保护查询值；排序字段属于语法结构，还需白名单。

## C13 空字符串、null 和零 / Чем отличаются пустая строка, null и ноль?

> Null означает отсутствие значения. Пустая строка — существующее строковое значение нулевой длины. Ноль — числовое значение. Например, общие сборы могут быть null, но не могут быть равны нулю. Слоган не может быть null, но по заданию может быть пустой строкой.

**中文：** null 是无值、空字符串是长度零的字符串、0 是数字。总票房允许 null 不允许零；标语不允许 null 但允许空字符串。

## C14 重复护照为什么还需要数据库唯一约束 / Зачем UNIQUE после проверки в сервисе?

> Проверка в сервисе позволяет вернуть понятное сообщение. Уникальное ограничение базы гарантирует целостность независимо от способа записи данных. Предварительная проверка приложения сама по себе не заменяет ограничение базы.

**中文：** Service 查重用于友好提示；数据库 UNIQUE 独立保证完整性，预查询不能替代约束。

## C15 为什么 Long 在 JSON 是字符串 / Почему большое число передаётся строкой?

> Диапазон Java Long шире диапазона целых чисел, которые JavaScript точно представляет обычным Number. Десятичная строка сохраняет все цифры. На сервере значение снова преобразуется в Long с проверкой диапазона.

**中文：** Java Long 范围超过 JavaScript Number 的精确整数范围，字符串保留所有位数，服务器再检查并转换。

## C16 金额为什么用浮点类型 / Почему для сборов используется Double?

> В этой лабораторной работе типы полей заданы условием, поэтому я сохраняю Double и Float там, где они указаны. Для реальной денежной системы обычно требуется точная десятичная модель, например BigDecimal и NUMERIC, с явно заданными правилами округления.

**中文：** 本实验遵循题目指定类型；实际金额系统通常需要 BigDecimal/NUMERIC 与明确舍入规则。

## C17 增加奖项发生溢出怎么办 / Что происходит при переполнении количества наград?

> Сложение сначала выполняется в более широком типе long. Затем проверяется верхняя граница int. Если результат выходит за допустимый диапазон, выбрасывается исключение и вся операция изменения откатывается. Уже обработанные фильмы не должны остаться частично изменёнными.

**中文：** 先用 long 加法，检查 int 上界，溢出抛异常，整项事务回滚，不能部分更新。

## C18 转移是幂等的吗，加奖是幂等的吗 / Что произойдёт при повторном выполнении?

> Повторное начисление наград снова изменяет количество наград, поэтому оно не идемпотентно. После перераспределения у источников остаётся по одной награде. Если между вызовами ничего не менялось, повторный перенос передаст ноль наград. Однако нельзя утверждать, что повторный HTTP-запрос вообще не меняет состояние приложения: write также увеличивает общую ревизию.

**中文：** 加奖重复会再次增加，不幂等；无中间变化时再次转移为零。但 write 仍增加 revision，不能笼统说整个请求完全无状态变化。

## C19 你用什么模式，是否用了 Repository / Какие архитектурные решения использованы?

> В проекте используются слоистая организация, сервисный слой и внедрение зависимостей. Компонент Database централизует выполнение операций с ресурсами и транзакциями через передаваемый callback. Отдельного слоя Repository в текущей реализации нет: JPQL-запросы находятся в сервисе.

**中文：** 有分层、Service 与依赖注入，Database 回调封装资源与事务；没有单独 Repository，JPQL 在 Service。

## C20 技术限制与可改进之处 / Какие ограничения есть у решения?

> Общая блокировка упрощает согласованность, но ограничивает параллельную запись. Обновление клиентов использует опрос, поэтому имеет небольшую задержку. **中文：** 全局写锁降低并行性，轮询有延迟，没有用户角色和冲突自动合并。这些是当前教学项目的简化。
