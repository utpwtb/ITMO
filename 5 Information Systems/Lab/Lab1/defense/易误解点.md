## 001 列表自动刷新，不等于编辑表单的版本自动更新

记录日期：2026-10-12。依据：当前工作区源码。行号用于快速定位；源码变化后，以函数名和关键语句为准。

### 核心结论

后端比较的是**浏览器打开编辑表单时保存的期望版本**与**本次保存事务读取的实体版本**。比较发生在后端，不要求浏览器把编辑快照更新到最新版本。

列表、编辑表单和集合变化标记是不同的状态。轮询可以更新列表和 `state.revision`，但不会自动更新已经打开的编辑表单及其 `state.editing.version`。

### 几个版本相关的状态分别是什么

| 状态 | 示例 | 代表什么 | 什么时候更新 |
|---|---|---|---|
| 数据库实体的 `version` | 当前电影版本为 8 | 该对象当前的数据库版本 | JPA 在对应实体更新时维护；事务提交后修改生效 |
| 编辑快照 `state.editing.version` | 仍为 7 | 用户打开这张表单时，所读取对象的版本 | 调用 `edit()` 重新建立编辑状态时取得；轮询不会修改它 |
| 列表请求返回的 `row.version` | 新列表中为 8 | 最近一次列表查询得到的对象版本 | 重新请求列表时取得；不会自动传递到已打开的编辑状态 |
| 集合标记 `state.revision` | 从 100 变为 101 | 这个页面最近一次处理的应用变化标记 | 轮询发现变化并完成相关刷新后记录 |

其中 `revision` 是应用范围的变化标记，不能替代单个对象的 `version`。另一个电影、人物、坐标或地点变化，也可能导致 `revision` 改变。

### 用两个用户走一遍实际流程

假设用户 B 打开电影 #1 的表单时，名称为“旧名称”，对象版本为 7。

1. B 的 `edit()` 请求对象，填充输入框，并保存 `state.editing.version = 7`。
2. 用户 A 修改同一部电影并提交；该电影的版本变为 8，应用的 `revision` 也随成功写事务改变。
3. B 的轮询发现 `revision` 与上次不同，重新加载列表。列表现在可以包含版本 8 的对象数据。
4. B 已打开的编辑表单继续保留原内容及 B 自己尚未保存的输入，编辑快照版本仍为 7。界面提示“集合发生变化；输入已保留；服务器将在保存时检查版本”。
5. B 点击保存，前端读取输入框内容，同时提交编辑快照中的 `version = 7`。
6. 后端在保存事务中读取电影 #1，得到当前版本 8。比较 `7 != 8` 后抛出 `Problem(409, ...)`，拒绝这次修改。
7. 前端把错误显示在编辑窗口中。保存失败时不会关闭表单或清空输入；用户可以保留所需内容，再关闭并重新打开表单查看最新记录。

重点：第 6 步需要的新版本由**后端查询**获得；浏览器并不需要先把旧编辑版本改成 8，才能检测到冲突。

### 关键代码与含义

前端：建立编辑快照，随后保存时带上该版本。

```javascript
// 打开表单时：row 来自单独的对象查询。
state.editing = {kind, id, version: row.version};

// 提交表单时：version 来自编辑快照。
const {kind, id, version} = state.editing;
if (id) data.version = version;
```

以上是不同位置的源码节选，展示数据来源，不是连续的独立程序。

后端：两个版本都在服务端这一步参与比较。

```java
Object expected = input.get("version");
if (expected == null ||
        Long.parseLong(expected.toString()) !=
                t.getField("version").getLong(entity))
    throw new Problem(409,
            "Объект изменён другим пользователем. Откройте форму заново.");
```

`expected` 来自 HTTP 请求；`entity` 来自本次事务的数据库读取。反射表达式读取当前 Java 实体的版本字段，本身并不另发起一次数据库查询。

### 易误解点

| 容易误解的说法 | 正确理解 |
|---|---|
| “后端能比较出差异，所以浏览器的版本肯定自动变了。” | 后端比较请求中的旧版本与数据库当前实体版本；旧版本不需要自动变化 |
| “页面自动刷新了，编辑表单也一定刷新了。” | `refresh()` 重新绘制列表；已打开的输入框和编辑快照由 `edit()` 管理 |
| “列表中的对象已经是版本 8，保存必然提交版本 8。” | 提交版本来自 `state.editing`，而非刷新后的列表行 |
| “提示集合变化，就说明当前编辑的电影过期了。” | 提示来自应用 `revision`，也可能由其他对象引起；保存时才检查当前对象版本 |
| “只更新编辑版本到 8，保留输入，就兼顾了刷新和输入保护。” | 旧内容可能因此携带新版本，误导后端认为输入基于最新记录，使旧表单校验失去作用 |
| “直接用最新数据覆盖表单，总能解决问题。” | 这可能覆盖用户尚未保存的输入，需要明确的重新加载或合并操作 |
| “`@Version` 自动识别一切旧表单，不需要手动比较。” | 后端若先读取最新实体，再填入旧表单内容，JPA 未必知道表单原来基于哪个版本；请求版本比较补上这一层保护 |
| “只要两个用户修改不同字段，就不会冲突。” | 当前按整个对象版本检查，不做字段级合并；同一对象的版本变化会使旧编辑提交被拒绝 |

### 当前设计的意图与边界

列表自动刷新让用户观察集合变化；保留编辑表单避免覆盖未保存的输入；保存时版本比较避免旧内容直接覆盖最新记录。三项行为同时存在，并不矛盾。

当前实现没有自动合并两个人的修改，也没有在提示时直接确认哪个对象变化。更完善的交互可以显示旧值、服务器新值和用户草稿，允许用户选择重新加载或合并。不能只更新版本号，却假定旧草稿已经基于新数据。
