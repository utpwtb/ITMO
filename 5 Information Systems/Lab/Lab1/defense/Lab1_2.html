1. Шаблоны проектирования и архитектурные шаблоны / 设计模式与架构模式

概念与区别

设计模式（Design Pattern）是针对反复出现的软件设计问题的可复用解决思路。它不是一段可以直接运行的代码，而是角色、关系和协作方式的模板。

架构模式（Architectural Pattern）决定系统较高层次的结构：系统如何分层、组件如何通信、依赖如何组织，以及数据和控制流如何通过系统。

类别典型模式主要用途
创建型Factory Method、Abstract Factory、Builder、Singleton控制对象创建，降低对具体类的依赖。
结构型Adapter、Decorator、Facade、Composite组织对象关系、适配接口、扩展功能。
行为型Strategy、Observer、Command、Template Method组织算法、事件通知和对象协作。
架构模式分层架构、MVC、六边形架构、微服务、事件驱动组织整个应用或多个服务。

例子：模式如何组合？

一个图书管理系统可以采用分层架构（Controller → Service → Repository），用 Repository 模式隔离数据访问，用 Strategy 模式切换不同的罚款计算算法。它们解决不同层次的问题，可以同时使用。

优缺点

  • 优点：提供共同词汇；降低耦合；提高可维护性和可测试性；帮助团队复用成熟经验。
  • 缺点：不适合所有场景；过度设计会增加类、接口和跳转；照搬模式可能让简单问题变复杂。

不要混淆

  • 模式：解决问题的通用方案。
  • 框架：可复用代码与约定，通常由框架控制程序流程（控制反转）。
  • 库：应用主动调用的工具集合，通常由应用控制调用时机。

Понятие и различия

Паттерн проектирования (Design Pattern) — типовое решение часто встречающейся проблемы проектирования. Это не готовый исполняемый код, а шаблон ролей, связей и взаимодействий объектов.

Архитектурный паттерн задаёт структуру более высокого уровня: слои системы, взаимодействие компонентов, направление зависимостей и потоки данных.

КатегорияПримерыНазначение
ПорождающиеFactory Method, Abstract Factory, Builder, SingletonУправлять созданием объектов и уменьшать зависимость от конкретных классов.
СтруктурныеAdapter, Decorator, Facade, CompositeОрганизовать связи объектов, адаптировать интерфейсы, расширять функции.
ПоведенческиеStrategy, Observer, Command, Template MethodОрганизовать алгоритмы, уведомления и взаимодействия.

Как паттерны сочетаются?

Система управления библиотекой может использовать слоистую архитектуру (Controller → Service → Repository), паттерн Repository для изоляции доступа к данным и Strategy для смены алгоритма расчёта штрафа. Они решают задачи разных уровней и могут применяться вместе.

Плюсы и минусы

  • Плюсы: общий язык команды, снижение связанности, удобство сопровождения и тестирования, повторное использование опыта.
  • Минусы: не подходят автоматически к любой задаче; избыточное применение создаёт лишние классы и усложняет код.

Не путать

  • Паттерн — общее решение проблемы.
  • Фреймворк — повторно используемый код и правила; обычно он управляет потоком выполнения (инверсия управления).
  • Библиотека — набор инструментов, которые приложение вызывает само.

2. Платформа Jakarta EE. Виды компонентов / Jakarta EE 平台与组件类型

Jakarta EE 是什么？

Jakarta EE 是面向企业级 Java 应用的一套开放标准。每项技术通常由规范（Specification）、API、兼容性测试（TCK）和兼容实现组成。应用可以依赖标准 API，而不必绑定某个厂商的专有 API。

常见兼容运行环境包括 GlassFish、Payara、WildFly、Open Liberty 等。运行环境中的容器为组件提供生命周期管理、依赖注入、事务、安全、连接池等服务。

Profiles（配置档案）

  • Core Profile：较精简的核心企业应用能力，适合轻量服务和云原生场景。
  • Web Profile：在核心能力上增加常用 Web 应用技术。
  • Platform：更完整的企业级技术集合，包含更多消息、批处理、邮件等能力。

常见组件类别

类别例子职责
Web 组件Servlet、Jakarta REST 资源类、WebSocket endpoint、Faces 相关组件处理 HTTP 请求、REST API、WebSocket 和 Web 表现层。
业务组件CDI bean、Enterprise Beans（EJB）实现业务规则；EJB 还提供特定的事务、安全、异步或远程调用能力。
持久化模型JPA / Jakarta Persistence entity描述持久化数据及对象关系；通常由 Persistence Provider 管理其持久化行为。
横切组件Interceptor、事件监听器、过滤器日志、审计、权限检查、请求预处理等。
注意：“组件”在严格规范语境中有具体含义；实体类、CDI bean、Servlet 的生命周期和容器服务并不完全相同。答辩时可以先按职责分类，再说明具体规范。

容器的意义

开发者声明组件和依赖，容器负责创建对象、注入依赖、管理上下文、协调事务和提供基础设施。这样业务代码不必自己管理所有底层资源。

Что такое Jakarta EE?

Jakarta EE — набор открытых стандартов для корпоративных Java-приложений. Обычно технология включает спецификацию, API, тест совместимости (TCK) и совместимые реализации. Приложение может использовать стандартный API, не привязываясь к закрытому API одного поставщика.

Примеры совместимых сред: GlassFish, Payara, WildFly, Open Liberty. Контейнер предоставляет компонентам управление жизненным циклом, внедрение зависимостей, транзакции, безопасность, пулы соединений и другие службы.

Профили

  • Core Profile: более компактный набор базовых корпоративных возможностей, подходящий для лёгких сервисов и cloud-native-приложений.
  • Web Profile: базовые возможности плюс распространённые веб-технологии.
  • Platform: более полный набор корпоративных технологий, включая дополнительные возможности сообщений, пакетной обработки, почты и т. д.

Зачем нужен контейнер?

Разработчик объявляет компоненты и зависимости, а контейнер создаёт объекты, внедряет зависимости, управляет контекстами, координирует транзакции и предоставляет инфраструктуру. Бизнес-коду не нужно самостоятельно управлять всеми ресурсами.

3. Jakarta EE. Управляемые бины. CDI-бины / Managed Beans 与 CDI Beans

核心概念

Managed Bean（受容器管理的 Bean）泛指由容器创建并管理生命周期、依赖或上下文的对象。注意：历史上也存在名为 Jakarta Managed Beans 的独立轻量规范；它不能与 CDI 混为一谈。

CDI（Contexts and Dependency Injection）是 Jakarta EE 的上下文与依赖注入规范。CDI bean 由 CDI 容器发现、创建并管理，可以使用依赖注入、作用域、限定符、事件和拦截器等功能。

常见注解

注解作用
@Inject按类型和限定符注入依赖。
@ApplicationScoped应用级上下文；同一应用上下文中通常共享一个上下文实例。
@RequestScoped每个 HTTP 请求一个上下文实例。
@SessionScoped会话级上下文；对象通常需要可序列化。
@Dependent依赖对象的生命周期通常与注入它的对象/注入点相关。
@Qualifier当同一接口有多个实现时，明确选择哪一个。
@Produces声明由生产者方法或字段提供的对象。

CDI、普通 Java 对象、EJB 的区别

  • 普通 `new` 创建的对象不自动获得 CDI 注入和容器生命周期管理。
  • CDI bean 适合常见业务服务，支持注入、作用域、事件、装饰器和拦截器。
  • EJB 是企业 Bean 组件模型；当需要其特定能力（例如消息驱动 Bean、远程调用或某些容器管理服务）时仍有价值。新业务组件常可优先考虑 CDI。

示例

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
public class BookService {
    @Inject
    BookRepository repository;

    public Book find(Long id) {
        return repository.findById(id);
    }
}

容器创建 `BookService`，并把合适的 `BookRepository` 实例注入进去。类必须由容器管理，手动 `new BookService()` 不会自动触发 CDI 注入。

优缺点

  • 优点：松耦合、可测试、生命周期统一、业务类更简洁。
  • 缺点：需要理解作用域与代理；作用域选择错误可能导致状态泄漏、并发问题或序列化问题；注入歧义需要限定符解决。

Основные понятия

Managed bean — общее название объекта, создание и жизненный цикл которого контролирует контейнер. Исторически существовала и отдельная спецификация Jakarta Managed Beans; её не следует отождествлять с CDI.

CDI (Contexts and Dependency Injection) — спецификация контекстов и внедрения зависимостей Jakarta EE. CDI-контейнер обнаруживает, создаёт и управляет CDI-бинами. Доступны внедрение зависимостей, области видимости, квалификаторы, события и перехватчики.

Распространённые аннотации

АннотацияНазначение
@InjectВнедрение зависимости по типу и квалификаторам.
@ApplicationScopedКонтекст приложения; обычно общий контекстный экземпляр в пределах приложения.
@RequestScopedКонтекстный экземпляр на HTTP-запрос.
@SessionScopedКонтекст сессии; объект обычно должен поддерживать сериализацию.

CDI, обычный Java-объект и EJB

  • Объект, созданный через обычный `new`, автоматически не получает CDI-внедрение и управление жизненным циклом.
  • CDI bean подходит для обычных бизнес-сервисов; поддерживает внедрение, контексты, события, декораторы и перехватчики.
  • EJB — модель корпоративных компонентов. Она полезна, когда нужны специфические функции, например Message-Driven Bean, удалённые вызовы или определённые контейнерные службы. Для новых бизнес-компонентов часто достаточно CDI.

Пример

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
public class BookService {
    @Inject
    BookRepository repository;

    public Book find(Long id) {
        return repository.findById(id);
    }
}

Контейнер создаёт `BookService` и внедряет подходящий `BookRepository`. Если вручную вызвать `new BookService()`, CDI-внедрение автоматически не произойдёт.

Преимущества и недостатки

  • Плюсы: слабая связанность, тестируемость, единое управление жизненным циклом, более простой бизнес-код.
  • Минусы: нужно понимать области видимости и прокси; неверный scope может привести к утечке состояния, проблемам конкурентного доступа или сериализации; неоднозначность внедрения решается квалификаторами.

4. ORM. Hibernate 与 EclipseLink / ORM、Hibernate и EclipseLink

什么是 ORM？

ORM（Object-Relational Mapping，对象关系映射）把面向对象程序中的类和对象映射到关系数据库的表和记录。它处理对象属性与列、对象关联与外键之间的关系，并可自动生成 SQL、跟踪对象变化和协调持久化操作。

典型映射：`Book` 类 → `book` 表；`Book.id` → 主键列；`Book.author` → 关联或外键。ORM 并不意味着开发者永远不需要 SQL，也不能自动消除数据库设计和性能问题。

Hibernate 与 EclipseLink：共同点

  • 都是 Java ORM 解决方案，也都可作为 Jakarta Persistence（JPA）提供者。
  • 都能映射实体、处理关联、执行查询、参与事务，并提供缓存等能力。
  • 都支持标准的 `jakarta.persistence` API；在标准范围内编写代码通常更容易更换提供者。

区别概览

维度Hibernate ORMEclipseLink
定位广泛使用的 ORM 框架与 JPA 提供者；拥有丰富的 Hibernate 专有扩展。Jakarta Persistence 的重要参考实现之一；也是 EclipseLink 持久化项目的一部分。
原生 API除标准 `EntityManager` 外，还提供 Hibernate `Session` 等专有 API。除标准 API 外，也提供 EclipseLink 专有扩展和配置能力。
特色HQL、丰富的 ORM 扩展；部分项目会使用 Envers 等生态功能。支持 weaving（织入）等机制，并有 EclipseLink MOXy 等相关映射能力。
可移植性使用标准 API 较好；依赖 Hibernate 专有功能会增加迁移成本。使用标准 API 较好；依赖 EclipseLink 专有扩展同样会增加迁移成本。

ORM 的优点与代价

  • 优点：减少 CRUD 样板代码；对象模型更自然；关联和脏检查更方便；可通过缓存、批处理等优化。
  • 代价：抽象层会隐藏 SQL；复杂查询可能需要原生 SQL；懒加载可能触发 N+1 查询；错误的抓取策略、事务边界或缓存配置会导致性能问题。
答辩关键句：Hibernate/EclipseLink 是实现；Jakarta Persistence 是标准 API/规范。优先使用 `EntityManager`、JPQL 和标准注解；确有必要时才使用提供者专有 API。

Что такое ORM?

ORM (Object-Relational Mapping) сопоставляет классы и объекты объектно-ориентированной программы с таблицами и строками реляционной БД. ORM связывает свойства объектов с колонками, ассоциации — с внешними ключами, а также может генерировать SQL, отслеживать изменения объектов и координировать сохранение.

Пример: класс `Book` → таблица `book`; `Book.id` → первичный ключ; `Book.author` → связь или внешний ключ. ORM не означает, что SQL больше никогда не нужен, и не решает автоматически проблемы проектирования БД и производительности.

Общее у Hibernate и EclipseLink

  • Оба решения являются Java ORM и могут выступать провайдерами Jakarta Persistence (JPA).
  • Оба отображают сущности, связи, выполняют запросы, участвуют в транзакциях и предоставляют механизмы кэширования.
  • Оба поддерживают стандартный API `jakarta.persistence`; код на стандартном API обычно легче перенести к другому провайдеру.

Плюсы и цена ORM

  • Плюсы: меньше шаблонного CRUD-кода; естественная объектная модель; удобные связи и dirty checking; возможны оптимизации кэшем и пакетными операциями.
  • Минусы: абстракция скрывает SQL; для сложных запросов может понадобиться native SQL; lazy loading способен вызвать N+1 запросов; неверные стратегии загрузки, транзакции или кэширования ухудшают производительность.
Фраза для защиты: Hibernate/EclipseLink — реализации, а Jakarta Persistence — стандарт API и правил. По возможности используйте `EntityManager`, JPQL и стандартные аннотации; специфический API провайдера — только при необходимости.

5. Jakarta Persistence（JPA）/ 持久化标准

它是什么？

Jakarta Persistence 是 Java 对象持久化与 ORM 的标准规范。过去常称 JPA（Java Persistence API），因此资料和口头交流中仍经常说“JPA”。它规定 API、实体映射和查询语义，但本身不是数据库，也不是 Hibernate 这样的具体 ORM 实现。

重要 API

  • Entity、Id、GeneratedValue、Column：声明实体及字段映射。
  • ManyToOne、OneToMany、OneToOne、ManyToMany、JoinColumn：声明实体关系。
  • EntityManagerFactory：创建 `EntityManager`；通常是较重的对象，按持久化单元管理。
  • EntityManager：管理持久化上下文，查找、持久化、合并、删除实体并创建查询。
  • TypedQuery、JPQL、Criteria API：以实体模型为基础进行类型化查询。
  • persistence.xml：可用于配置持久化单元、实体和提供者相关设置。

实体状态（高频考点）

状态含义
New / Transient刚创建的普通对象，尚未纳入持久化上下文。
Managed由当前持久化上下文管理；属性变化可被脏检查发现。
Detached曾经受管理，但已脱离当前持久化上下文。
Removed已标记删除，通常在同步/提交时执行数据库删除。

工作过程

  1. 定义 `@Entity` 类和主键、字段、关联映射。
  2. 获得 `EntityManager`（在 Jakarta EE 环境可由容器注入；Java SE 可通过 `Persistence` 引导创建）。
  3. 在事务中调用 `persist`、`find`、`merge`、`remove` 或查询 API。
  4. 持久化上下文跟踪实体状态；`flush` 将待执行变更同步到数据库，事务 `commit` 决定是否提交。
易错点：flush() 不等于 commit()。Flush 是把上下文中的变更同步到数据库连接/事务中；Commit 才是提交事务。事务回滚仍可能撤销已 flush 的变更。

示例：实体类

import jakarta.persistence.*;

@Entity
@Table(name = "books")
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String title;

    protected Book() {} // 供持久化框架使用
}

优点与局限

  • 优点：标准化；实体映射与查询 API 相对可移植；减少手写 SQL 和重复映射代码。
  • 局限：需要理解实体状态、事务、懒加载和关联维护；标准并不保证所有数据库生成的 SQL 和性能相同；特殊 SQL 能力可能需要 native query 或提供者扩展。

Что это такое?

Jakarta Persistence — стандарт для сохранения Java-объектов и ORM. Раньше он назывался JPA (Java Persistence API), поэтому термин «JPA» по-прежнему широко используется. Спецификация определяет API, отображение сущностей и семантику запросов, но сама не является ни БД, ни конкретной ORM-реализацией вроде Hibernate.

Важные API

  • Entity, Id, GeneratedValue, Column — объявление сущности и отображения полей.
  • ManyToOne, OneToMany, OneToOne, ManyToMany, JoinColumn — связи между сущностями.
  • EntityManagerFactory — создаёт `EntityManager`; обычно это более тяжёлый объект уровня persistence unit.
  • EntityManager — управляет контекстом персистентности, ищет, сохраняет, объединяет и удаляет сущности, создаёт запросы.
  • TypedQuery, JPQL, Criteria API — типизированные запросы на основе модели сущностей.
  • persistence.xml — файл для настройки persistence unit, сущностей и параметров провайдера.

Состояния сущности — частый вопрос

СостояниеЗначение
New / TransientНовый обычный объект, ещё не включённый в контекст персистентности.
ManagedУправляется текущим контекстом; изменения полей могут быть обнаружены dirty checking.
DetachedРаньше управлялся, но больше не связан с текущим контекстом персистентности.
RemovedПомечен на удаление; SQL DELETE обычно выполняется при синхронизации или фиксации.

Как работает технология

  1. Определить класс `@Entity`, первичный ключ, поля и связи.
  2. Получить `EntityManager` (в Jakarta EE его может внедрить контейнер; в Java SE фабрику можно создать через `Persistence`).
  3. В транзакции вызвать `persist`, `find`, `merge`, `remove` или API запросов.
  4. Контекст отслеживает состояние сущностей; `flush` синхронизирует изменения с БД, а `commit` фиксирует транзакцию.
Типичная ошибка:flush() не равен commit(). Flush отправляет изменения из контекста в БД внутри текущей транзакции; commit фиксирует транзакцию. Откат всё ещё может отменить изменения, которые уже были flush-нуты.

Пример сущности

import jakarta.persistence.*;

@Entity
@Table(name = "books")
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String title;

    protected Book() {} // для ORM
}

Преимущества и ограничения

  • Плюсы: стандартизация; относительно переносимые отображение и запросы; меньше ручного SQL и повторяющегося кода.
  • Ограничения: нужно понимать состояния сущностей, транзакции, lazy loading и управление связями; стандарт не гарантирует одинаковый SQL и производительность на всех БД; для специфических запросов могут понадобиться native query или расширения провайдера.

6. Технология Jakarta Data / Jakarta Data 数据访问规范

定位：比 Persistence 更高一层

Jakarta Data 是标准化的数据访问 API，1.0 版于 2024 年发布，并面向 Jakarta EE 11 生态。目标是用 Repository（仓储）抽象简化常见查询、增删改、分页和排序，让应用代码更关注领域模型与业务。

它的目标是补充而不是取代 Jakarta Persistence 或 Jakarta NoSQL。Jakarta Persistence 侧重实体映射、持久化上下文和 ORM 行为；Jakarta Data 侧重统一的仓储接口和数据访问方式。

主要概念

  • @Repository：声明仓储接口。
  • BasicRepository、CrudRepository：提供常见基础操作的接口。
  • @Find、@Query：声明查询方法；具体查询语法和提供者支持需查看实现及规范版本。
  • @Insert、@Update、@Delete、@Save：声明数据生命周期操作。
  • 分页、排序、限制结果数量等能力减少手写通用代码。

概念示例

import jakarta.data.repository.BasicRepository;
import jakarta.data.repository.Repository;

@Repository
public interface BookRepository
        extends BasicRepository<Book, Long> {
    // 通用保存、删除、按 ID 查找等操作
}

接口的实际实现由 Jakarta Data Provider 提供；应用通常注入接口，而不是自己编写实现类。具体运行时是否提供兼容实现，需要确认。

与 Jakarta Persistence 的区别

比较项Jakarta PersistenceJakarta Data
核心问题对象如何映射、管理与持久化？应用如何用统一仓储 API 访问数据？
典型对象Entity、EntityManager、Persistence ContextRepository 接口、通用 CRUD、查询方法
抽象层次ORM / 持久化 API数据访问 / Repository 抽象
关系互补，不是替代关系；具体 provider 与持久化技术的集成方式取决于实现和规范支持。
版本细节：Jakarta Data 1.0 没有规定一种强制、统一的 Jakarta Persistence 集成方式。因此不要直接说“Jakarta Data 就是 JPA 的一层包装”；要强调它是标准化的仓储 API，具体集成依赖提供者。

优缺点

  • 优点：减少样板代码；接口表达清晰；有分页和查询抽象；目标是面向不同数据存储保持一致的编程模型。
  • 局限：规范较新，运行环境和提供者支持需要核实；不同数据库的能力并不完全相同；复杂查询和数据库专有功能可能仍需扩展或底层 API。

Позиционирование: уровень выше Persistence

Jakarta Data — стандартизованный API доступа к данным. Версия 1.0 выпущена в 2024 году для экосистемы Jakarta EE 11. Цель — упростить типичные запросы, CRUD, пагинацию и сортировку с помощью абстракции Repository, чтобы код был ближе к доменной модели и бизнес-задачам.

Спецификация дополняет, а не заменяет Jakarta Persistence или Jakarta NoSQL. Jakarta Persistence сосредоточена на отображении сущностей, контексте персистентности и поведении ORM; Jakarta Data — на единообразных репозиториях и доступе к данным.

Основные понятия

  • @Repository — объявляет интерфейс репозитория.
  • BasicRepository, CrudRepository — интерфейсы с базовыми операциями.
  • @Find, @Query — объявляют методы запросов; точный синтаксис и поддержка зависят от версии спецификации и провайдера.
  • @Insert, @Update, @Delete, @Save — обозначают операции жизненного цикла данных.
  • Пагинация, сортировка и ограничение количества результатов сокращают шаблонный код.

Концептуальный пример

import jakarta.data.repository.BasicRepository;
import jakarta.data.repository.Repository;

@Repository
public interface BookRepository
        extends BasicRepository<Book, Long> {
    // Базовые операции: сохранить, удалить, найти по ID
}

Реализацию интерфейса предоставляет Jakarta Data Provider; приложение обычно внедряет интерфейс и не пишет класс реализации вручную. Наличие совместимого провайдера в конкретной среде нужно проверить.

Отличие от Jakarta Persistence

КритерийJakarta PersistenceJakarta Data
Главный вопросКак отображать, управлять и сохранять объекты?Как обращаться к данным через единый API репозиториев?
Типичные сущности APIEntity, EntityManager, Persistence ContextИнтерфейс Repository, CRUD, методы запросов

СвязьТехнологии дополняют друг друга. Способ интеграции конкретного провайдера с технологией хранения зависит от реализации и поддержки спецификаций.
Важная деталь версии: Jakarta Data 1.0 не определяет единственный обязательный способ интеграции с Jakarta Persistence. Поэтому неверно утверждать, что «Jakarta Data — просто обёртка над JPA»: это стандартный API репозиториев, а конкретная интеграция зависит от провайдера.

Плюсы и ограничения

  • Плюсы: меньше шаблонного кода; выразительные интерфейсы; абстракции запросов и пагинации; единообразная модель для разных типов хранилищ.
  • Ограничения: спецификация сравнительно новая, нужно проверять поддержку средой и провайдером; возможности разных БД не одинаковы; для сложных запросов и специфических функций могут понадобиться расширения или нижележащий API.

7. Платформа Spring. Сходства и отличия с Java EE / Spring 与 Java EE、Jakarta EE

先区分名称

Java EE 是 Jakarta EE 的前身名称。Java EE 由 Oracle 移交给 Eclipse Foundation 后，后续平台称为 Jakarta EE。Jakarta EE 是一组标准规范；Spring Framework 则是一个独立的应用开发框架和生态系统。

共同点

  • 都用于构建企业级 Java 应用。
  • 都提供依赖注入、Web 开发、事务管理、验证、安全集成和数据访问集成等能力。
  • 都能与 Jakarta Persistence、Hibernate 等持久化技术协作。

核心区别

运行方式常见于兼容应用服务器/运行环境，也可使用轻量配置和现代部署方式。可运行于嵌入式服务器，也可部署到外部容器；具体取决于应用形态。

如何选择？

  • 重视标准化、应用服务器兼容和规范可移植性时，可考虑 Jakarta EE。
  • 重视 Spring 生态、快速组合模块、团队已有 Spring 经验时，Spring 常更方便。
  • 两者不是绝对对立：Spring 应用也可以使用 JPA、Bean Validation 等 Jakarta 标准。

Сначала различим названия

Java EE — прежнее название платформы, которая теперь называется Jakarta EE. После передачи Java EE от Oracle фонду Eclipse дальнейшая платформа развивается как Jakarta EE. Jakarta EE — набор стандартных спецификаций; Spring Framework — независимый фреймворк и экосистема разработки приложений.

Общее

  • Обе технологии предназначены для корпоративных Java-приложений.
  • Обе предоставляют внедрение зависимостей, веб-разработку, транзакции, валидацию, интеграцию безопасности и доступа к данным.
  • Обе могут работать с Jakarta Persistence, Hibernate и другими технологиями хранения данных.

Как выбирать?

  • Jakarta EE уместна, если важны стандартизация, совместимость с сервером приложений и переносимость стандартного API.
  • Spring часто удобнее благодаря экосистеме модулей, быстрой композиции и опыту команды.
  • Это не абсолютные конкуренты: приложение Spring тоже может использовать стандарты Jakarta, например JPA и Bean Validation.

8. Spring Boot / Spring Boot 框架

它是什么、解决什么问题？

Spring Boot 构建在 Spring Framework 之上，目标是减少新项目的配置成本，让应用更容易启动、测试和部署。它没有替代 Spring，而是通过约定优于配置、自动配置、starter 依赖和可执行应用打包来简化 Spring 应用开发。

关键机制

  • Auto-configuration（自动配置）：根据 classpath、已有 Bean 和配置属性，尝试配置合适的组件；通常可由用户配置覆盖。
  • Starters：把一组常用依赖打包成依赖入口，例如 Web、测试、数据访问等 starter。
  • Embedded server：常见 Web 应用可将服务器嵌入应用并以可执行 JAR 运行，而不必手工部署 WAR 到外部服务器。
  • Externalized configuration：通过配置文件、环境变量、命令行参数等管理环境差异。
  • Actuator：提供健康检查、指标、应用信息等运维端点（具体功能取决于配置和依赖）。

典型入口

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

@SpringBootApplication 通常组合了配置类、自动配置启用和组件扫描等功能。

优点与代价

  • 优点：启动快、默认配置多、依赖组合方便、易于容器化与部署、生态成熟。
  • 代价：自动配置可能让初学者不清楚“为什么这样运行”；依赖版本冲突、默认设置和启动行为仍需理解；不正确的配置也可能带来安全或性能问题。
一句话回答：Spring 是核心框架；Spring Boot 是简化 Spring 应用配置、启动和部署的工具集。

Что это и какую проблему решает?

Spring Boot построен поверх Spring Framework и уменьшает стоимость настройки нового проекта, упрощая запуск, тестирование и развёртывание. Он не заменяет Spring, а упрощает разработку за счёт принципа convention over configuration, автоконфигурации, starter-зависимостей и исполняемого пакета приложения.

Ключевые механизмы

  • Автоконфигурация: на основе classpath, уже существующих Bean и настроек пытается подобрать нужные компоненты; конфигурацию обычно можно переопределить.
  • Starters: группируют типичные зависимости в удобные точки подключения, например для Web, тестирования и доступа к данным.
  • Встроенный сервер: веб-приложение часто запускается как исполняемый JAR со встроенным сервером, без ручного развёртывания WAR во внешнем сервере.
  • Внешняя конфигурация: файлы настроек, переменные окружения, аргументы командной строки помогают различать окружения.
  • Actuator: предоставляет средства мониторинга — health checks, метрики, сведения о приложении; набор функций зависит от конфигурации и зависимостей.

Типичная точка входа

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

@SpringBootApplication обычно объединяет конфигурационный класс, включение автоконфигурации и сканирование компонентов.

Преимущества и цена

  • Плюсы: быстрый старт, разумные настройки по умолчанию, удобное подключение зависимостей, контейнеризация и развёртывание, зрелая экосистема.
  • Минусы: новичку бывает неясно, почему сработала определённая автоконфигурация; нужно понимать версии зависимостей, настройки по умолчанию и процесс запуска; ошибочная конфигурация может повлиять на безопасность и производительность.
Ответ одной фразой: Spring — основной фреймворк; Spring Boot — инструменты для упрощения конфигурации, запуска и развёртывания приложений Spring.

9. Spring Data / Spring Data 数据访问生态

定位与组成

Spring Data 是一组用于简化数据访问的 Spring 项目，不是单独的数据库，也不是某一个 ORM。它通过 Repository 抽象、查询方法、分页、排序和审计等能力，减少重复的数据访问代码。

  • Spring Data JPA：基于 JPA 的模块，常与 Hibernate 等 JPA provider 搭配。
  • Spring Data JDBC：面向 JDBC 和关系型数据访问，抽象与 ORM 不同。
  • Spring Data MongoDB、Redis 等：面向不同存储系统的独立模块。
  • Spring Data Commons：提供多个 Spring Data 模块共享的核心仓储抽象。

Spring Data JPA 示例

import org.springframework.data.jpa.repository.JpaRepository;

public interface BookRepository
        extends JpaRepository<Book, Long> {
    // Spring Data 可根据方法名生成查询
    List<Book> findByTitleContainingIgnoreCase(String title);
}

开发者声明接口；Spring Data 在运行时提供实现。`JpaRepository` 表示管理 `Book` 实体，主键类型是 `Long`。

与 Jakarta Data、JPA 的区别

Hibernate / EclipseLinkJPA 的具体 ORM 提供者，实现持久化行为。
Jakarta Data标准化 Repository / 数据访问 API；强调规范层面的统一接口。
Spring DataSpring 生态中的多个数据访问项目；提供不同存储模块和 Spring 风格的 Repository。

优缺点

  • 优点：减少 DAO 样板代码；方法名可表达简单查询；分页和排序方便；与 Spring DI、事务和测试体系整合紧密。
  • 缺点：方法名查询过长时可读性下降；复杂查询仍需要 JPQL、Criteria 或原生 SQL；接口和注解与 Spring 生态绑定，迁移到非 Spring 方案时需调整。
答辩陷阱：Spring Data JPA ≠ JPA。JPA 是标准；Spring Data JPA 是 Spring 项目；Hibernate 常作为底层 provider。三者可以同时出现在一个项目中。

Позиционирование и состав

Spring Data — семейство проектов Spring для упрощения доступа к данным, а не отдельная база данных и не одна ORM. Абстракция Repository, методы запросов, пагинация, сортировка и аудит сокращают повторяющийся код.

  • Spring Data JPA: модуль на основе JPA, часто используемый вместе с Hibernate или другим JPA-провайдером.
  • Spring Data JDBC: доступ к реляционным данным через JDBC; его модель отличается от ORM.
  • Spring Data MongoDB, Redis и др.: отдельные модули для разных хранилищ.
  • Spring Data Commons: общие абстракции репозиториев для модулей Spring Data.

Пример Spring Data JPA

import org.springframework.data.jpa.repository.JpaRepository;

public interface BookRepository
        extends JpaRepository<Book, Long> {
    // Spring Data строит запрос по имени метода
    List<Book> findByTitleContainingIgnoreCase(String title);
}

Разработчик объявляет интерфейс, а Spring Data предоставляет реализацию во время выполнения. `JpaRepository` означает работу с сущностью `Book` и ключом типа `Long`.

Преимущества и недостатки

  • Плюсы: меньше шаблонного DAO-кода; простые запросы выражаются именами методов; удобные пагинация и сортировка; тесная интеграция с DI, транзакциями и тестированием Spring.

11. 高频答辩问题 / Вопросы для устной защиты

点击问题展开答案。建议先用 2–4 句话回答，再根据追问补充例子。

中文问答

1. 设计模式和架构模式有什么区别？
设计模式解决类和对象层面的重复设计问题；架构模式决定系统更高层次的结构和组件协作方式。例如 Strategy 是设计模式，分层架构是架构模式。一个系统可以同时使用多种设计模式和一种或多种架构模式。
2. Jakarta EE 是框架吗？
更准确地说，它是一组企业 Java 标准规范及其平台生态。规范定义标准 API 和行为要求，兼容运行环境负责实现。开发者因此能在不同兼容实现之间获得一定的可移植性。
3. Managed Bean 和 CDI Bean 一样吗？
不完全一样。“managed bean”可以泛指由容器管理的对象；CDI bean 是 CDI 规范定义的 bean 模型。历史上的 Jakarta Managed Beans 又是一个独立规范，不能简单与 CDI 等同。
4. 为什么依赖注入比在类里直接 new 更好？
依赖由容器提供，类不必自己选择和创建具体实现，降低耦合并便于测试替换。缺点是对象创建和生命周期不再完全显式，因此需要理解容器配置、作用域和注入规则。
5. ORM 解决什么问题？
ORM 把对象模型映射到关系表，减少重复 SQL 和映射代码，并帮助管理实体关系及变化。但 ORM 不会消除 SQL、事务和性能问题；仍需关注查询计划、索引、抓取策略和 N+1 查询。
6. JPA 与 Hibernate 有什么区别？
JPA（现在的名称是 Jakarta Persistence）是标准 API/规范；Hibernate 是实现这一标准的 ORM provider，也提供自己的扩展 API。使用标准 API 有助于移植，使用专有扩展则可能增加对 Hibernate 的依赖。
7. Hibernate 和 EclipseLink 有什么相同点和不同点？
两者都可实现 Jakarta Persistence，支持实体映射、关联、查询和事务。它们的扩展 API、配置方式、SQL 生成、缓存和性能特征不同；应基于项目兼容性、团队经验、实际测试和所需特性选择。
8. EntityManager 和 EntityManagerFactory 的区别？
EntityManagerFactory 创建 EntityManager，通常是较重且可在应用范围复用的工厂；EntityManager 负责一个持久化上下文中的实体操作，通常不应被多个并发线程随意共享。
9. flush 和 commit 的区别？
flush 把持久化上下文中的待执行变更同步到数据库事务中；commit 提交事务。flush 不代表事务已经提交，后续回滚仍可能撤销这些更改。
10. Jakarta Data 会取代 Jakarta Persistence 吗？
不会。Jakarta Data 提供更高层的 Repository 数据访问抽象；Jakarta Persistence 定义实体映射、持久化上下文和 ORM API。两者目标不同，设计上是互补关系；具体集成要看 provider 的支持。
11. Spring 和 Jakarta EE 的本质区别是什么？
Jakarta EE 以标准规范和兼容实现为核心；Spring 是应用开发框架及生态。两者功能重叠但组织方式不同，也能结合使用，例如 Spring 应用使用 JPA 标准 API 和 Hibernate provider。
12. Spring Boot 是什么？
Spring Boot 是构建在 Spring Framework 之上的工具集，借助自动配置、starter 依赖、外部化配置和嵌入式服务器降低配置与部署成本。它不替代 Spring，而是简化 Spring 应用的开发流程。
13. Spring Data 与 Spring Data JPA 有什么区别？
Spring Data 是包含多个存储技术模块的项目家族；Spring Data JPA 是其中使用 JPA 的一个模块。Spring Data JPA 通常通过 Hibernate 等 JPA provider 执行底层持久化。
14. Jakarta Data 和 Spring Data 的区别？
Jakarta Data 是标准化的 Jakarta API，目标是跨实现提供一致的数据访问编程模型；Spring Data 是 Spring 生态中的项目家族，提供针对多种数据存储的模块。前者强调标准规范，后者强调 Spring 生态和具体模块能力。
15. 什么是 Repository 模式？
Repository 在业务逻辑和数据存储之间提供一个面向领域的接口，把查询和持久化细节封装起来。这样服务层不需要直接依赖 SQL 或具体数据访问实现，更易测试和维护。
16. 使用 Spring Data/Jakarta Data 后还需要理解 SQL 吗？
需要。抽象可以减少重复代码，但不会消除数据库索引、连接、事务隔离、查询计划和性能优化问题。复杂查询和数据库专有功能仍可能需要 SQL 或底层 API。

Вопросы и ответы по-русски

1. Чем отличаются паттерн проектирования и архитектурный паттерн?
Паттерн проектирования решает повторяющуюся задачу на уровне классов и объектов; архитектурный паттерн определяет более крупную структуру системы и взаимодействие компонентов. Например, Strategy — паттерн проектирования, а слоистая архитектура — архитектурный паттерн. Их можно применять одновременно.
2. Jakarta EE — это фреймворк?
Точнее, это набор корпоративных Java-спецификаций и экосистема платформы. Спецификации задают стандартные API и требования к поведению, а совместимые среды их реализуют. Это обеспечивает определённую переносимость приложений.
3. Managed Bean и CDI Bean — одно и то же?
Не совсем. «Managed bean» может быть общим термином для объекта, жизненным циклом которого управляет контейнер. CDI bean — модель бина, определённая CDI. Историческая спецификация Jakarta Managed Beans также была отдельной технологией, поэтому термины нельзя безоговорочно отождествлять.
4. Почему DI лучше, чем создавать зависимости через new?
Зависимости предоставляет контейнер, поэтому класс не обязан сам выбирать и создавать конкретные реализации. Это уменьшает связанность и упрощает тестирование. При этом нужно понимать конфигурацию контейнера, scope и правила внедрения.
5. Какую проблему решает ORM?
ORM отображает объектную модель на реляционные таблицы, сокращает повторяющийся SQL и код отображения, помогает управлять связями и изменениями сущностей. Но ORM не устраняет проблемы SQL, транзакций и производительности: нужны индексы, контроль запросов, стратегии загрузки и внимание к N+1.
6. Чем JPA отличается от Hibernate?
JPA, современное название — Jakarta Persistence, является стандартом API и спецификацией. Hibernate — ORM-провайдер, реализующий этот стандарт и предлагающий собственные расширения. Стандартный API повышает переносимость, а специфические функции связывают код с Hibernate.
7. Что общего и различного у Hibernate и EclipseLink?
Оба могут реализовывать Jakarta Persistence и поддерживают отображение сущностей, связи, запросы и транзакции. Отличаются расширениями, конфигурацией, генерацией SQL, кэшированием и характеристиками производительности. Выбор нужно делать по совместимости, опыту команды, нужным функциям и результатам тестов.
8. Чем EntityManager отличается от EntityManagerFactory?
EntityManagerFactory создаёт EntityManager и обычно является более тяжёлой фабрикой, которую можно повторно использовать на уровне приложения. EntityManager выполняет операции с сущностями в конкретном контексте персистентности; его не следует бездумно разделять между конкурентными потоками.
9. В чём разница между flush и commit?
Flush синхронизирует ожидающие изменения контекста персистентности с БД внутри текущей транзакции. Commit фиксирует транзакцию. После flush транзакция ещё не обязательно завершена, и изменения могут быть отменены откатом.
10. Заменит ли Jakarta Data Jakarta Persistence?
Нет. Jakarta Data даёт более высокоуровневую абстракцию доступа к данным через Repository; Jakarta Persistence определяет отображение сущностей, контекст персистентности и ORM API. Их цели различаются, они дополняют друг друга; интеграция зависит от провайдера.
11. В чём принципиальная разница Spring и Jakarta EE?
Jakarta EE опирается на спецификации и совместимые реализации; Spring — фреймворк и экосистема разработки приложений. Функциональность частично пересекается, но подходы отличаются. Их можно сочетать: например, приложение Spring использует стандартный JPA API и Hibernate-провайдер.
12. Что такое Spring Boot?
Spring Boot — инструменты поверх Spring Framework, которые упрощают конфигурацию и развёртывание за счёт автоконфигурации, starter-зависимостей, внешней конфигурации и встроенного сервера. Он не заменяет Spring, а упрощает работу с ним.
13. Чем Spring Data отличается от Spring Data JPA?
Spring Data — семейство модулей для разных хранилищ; Spring Data JPA — один из модулей, использующий JPA. Для реальной персистентности Spring Data JPA обычно обращается к JPA-провайдеру, например Hibernate.
14. Чем Jakarta Data отличается от Spring Data?
Jakarta Data — стандартизованный API Jakarta с целью обеспечить единообразную модель доступа к данным между реализациями. Spring Data — семейство проектов экосистемы Spring с модулями для различных хранилищ. Первый подход делает акцент на стандарте, второй — на интеграции и возможностях Spring.
15. Что такое паттерн Repository?
Repository предоставляет ориентированный на предметную область интерфейс между бизнес-логикой и хранилищем данных. Он скрывает детали запросов и сохранения, поэтому сервисный слой меньше зависит от SQL и конкретной реализации доступа к данным.
16. Нужно ли знать SQL, если используется Spring Data или Jakarta Data?
Да. Абстракции сокращают шаблонный код, но не отменяют необходимость понимать индексы, соединения, изоляцию транзакций, планы запросов и оптимизацию производительности. Для сложных запросов и специфических функций всё ещё могут понадобиться SQL или нижележащие API.
