01 · Design / Architecture

1. 设计模式与架构模式
Шаблоны проектирования и архитектурные шаблоны

1.1 设计模式是什么？ / Что такое шаблон проектирования?

设计模式是针对软件设计中反复出现的问题，总结出来的、可复用的解决思路。它不是现成的完整代码，也不是必须照搬的规则，而是描述类、对象之间如何分工和协作。

Шаблон проектирования — это проверенное типовое решение часто встречающейся проблемы проектирования. Это не готовый фрагмент кода и не обязательное правило, а описание взаимодействия классов и объектов.

1.2 常见设计模式分类 / Основные группы

分类 / Группа解决什么问题 / Задача例子 / Примеры优点与代价 / Плюсы и цена
创建型 / Порождающие如何创建对象而不把创建逻辑散落各处。Factory Method、Abstract Factory、Builder、Singleton降低创建逻辑与业务代码的耦合；可能增加类和抽象层。
结构型 / Структурные如何组织类与对象、组合复杂功能。Adapter、Decorator、Facade、Composite、Proxy方便组合和扩展；结构过度设计会让调用链变复杂。
行为型 / Поведенческие如何分配职责、组织对象之间的交互。Strategy、Observer、Command、Template Method、Iterator降低条件分支或对象间耦合；可能增加接口、回调和间接层。

Strategy（策略模式）

把可替换的算法封装成不同策略，例如信用卡、银行卡、电子钱包等支付方式。调用方依赖共同接口，不需要写一个巨大 if-else。

Разные алгоритмы (например, способы оплаты) реализуют общий интерфейс. Клиент выбирает стратегию без большого блока if-else.

Factory（工厂模式）

把对象创建过程集中起来。适合创建逻辑复杂或需要按配置选择实现的场景。

Создание объектов выносится в отдельный компонент. Полезно, когда создание сложно или реализация выбирается по конфигурации.

Adapter（适配器模式）

把一个接口转换成客户端需要的接口，例如把第三方支付 SDK 包装成系统统一的 PaymentService。

Адаптер преобразует несовместимый интерфейс в ожидаемый, например оборачивает сторонний SDK единым интерфейсом PaymentService.

Observer（观察者模式）

一个对象状态变化时通知多个订阅者，例如订单支付成功后通知库存、邮件和积分模块。

При изменении состояния издатель уведомляет подписчиков, например после оплаты заказа запускаются складской, почтовый и бонусный модули.

1.3 架构模式是什么？ / Что такое архитектурный шаблон?

架构模式在比类设计更高的层次上，规定系统的主要组成部分、职责边界以及它们的通信方式。它影响整个应用或多个子系统，而不只是几个类。

Архитектурный шаблон задаёт на более высоком уровне основные части системы, границы ответственности и способы взаимодействия. Он влияет на приложение или подсистемы, а не только на отдельные классы.

架构模式 / Шаблон结构与用途 / Структура и применение优势 / Преимущества局限 / Ограничения
分层架构 / Layered表示层 → 业务层 → 数据访问层；常见于企业应用。职责清晰、容易教学和测试、团队易分工。可能层层转发、变更传播慢；容易形成“所有逻辑都塞进 Service”。
MVCModel 管数据/业务状态，View 展示，Controller 处理输入并协调。分离界面和逻辑，便于替换 UI、测试控制逻辑。小项目也可能过度拆分；Model 的含义因框架而不同。
六边形 / Ports and Adapters核心业务通过端口定义边界，数据库、HTTP、消息队列等由适配器接入。业务逻辑不依赖具体技术，便于替换外部组件和测试。接口和抽象较多，简单 CRUD 项目可能显得繁琐。
微服务 / Microservices按业务边界拆成可独立部署的服务，通过 API 或消息通信。可独立部署、扩缩容、按服务选技术。分布式事务、网络故障、监控、部署和数据一致性更复杂。
事件驱动 / Event-driven组件发布和消费事件，通常通过消息代理异步通信。降低直接依赖、便于异步处理和扩展。追踪调用链、处理重复消息、顺序和最终一致性更难。

1.4 二者的区别与联系 / Различия и связь

比较维度设计模式架构模式
层次 / Уровень类、对象、模块内部。系统、子系统、服务之间。
关注点 / Фокус某个设计问题如何解决。系统整体如何组织和通信。
例子 / ПримерStrategy、Factory、Adapter、Observer。Layered、MVC、Microservices、Hexagonal。
联系 / Связь架构通常由多个设计模式共同实现。例如分层架构中可以使用 Repository、Factory、Strategy；MVC 是常见的应用架构模式，而 Controller 内部也可能使用策略模式。

答辩句：设计模式解决局部、反复出现的设计问题；架构模式决定系统的高层结构。它们不是竞争关系，架构模式可以通过多个设计模式来实现。

Ответ: Шаблон проектирования решает локальную повторяющуюся задачу, а архитектурный шаблон определяет общую структуру системы. Они дополняют друг друга: архитектура может реализовываться с помощью нескольких шаблонов проектирования.

02 · Enterprise Java Platform

2. Jakarta EE 平台与组件
Платформа Jakarta EE. Виды компонентов

2.1 Jakarta EE 是什么？ / Что такое Jakarta EE?

Jakarta EE 是面向企业级 Java 应用的一组开放标准规范。它定义了许多 API，例如 Servlet、RESTful Web Services、CDI、事务、安全、持久化、消息等。规范说明 API 应当如何工作；应用服务器或兼容运行时负责提供实现和容器服务。

Jakarta EE — набор открытых спецификаций для корпоративных Java-приложений. Он определяет API для Servlet, REST, CDI, транзакций, безопасности, хранения данных, сообщений и других задач. Спецификация описывает контракт, а совместимый сервер или runtime предоставляет реализацию и сервисы контейнера.

注意：Jakarta EE 不是单个框架，也不等于某一款服务器。它是规范集合；例如 WildFly、Payara、Open Liberty 等是不同的实现/运行环境。

Важно: Jakarta EE — не один фреймворк и не конкретный сервер. Это набор спецификаций; WildFly, Payara и Open Liberty — примеры разных сред реализации.

2.2 平台、规范、实现、容器 / Платформа, спецификация, реализация, контейнер

术语含义例子
平台 / Platform将多个规范组合成可互相协作的一套企业应用能力。Jakarta EE Platform
规范 / Specification定义 API、行为和兼容性要求。Jakarta REST、Jakarta Persistence、CDI
API程序员直接使用的类型、注解、接口和方法。EntityManager、@Inject
实现 / Implementation真正实现某个规范的库或运行时。Hibernate 实现 Jakarta Persistence；服务器集成 CDI 等实现
容器 / Container管理组件生命周期，并提供依赖注入、事务、安全、资源池等服务。Web 容器、CDI 容器、企业 Bean 容器

2.3 主要组件类型 / Основные виды компонентов

教材中的分类会随版本和语境略有不同。答辩时可以先按功能说明，再举规范组件的例子。现代 Jakarta EE 中，组件通常是运行在服务器端、由容器管理并使用平台服务的功能单元。

Классификация может немного различаться в зависимости от версии и учебника. На защите удобно сначала объяснить назначение, а затем привести примеры. В современной Jakarta EE компонент обычно является серверной функциональной единицей, управляемой контейнером и использующей его сервисы.

类型 / Вид职责 / Назначение例子 / Примеры
Web 组件 / Веб-компоненты处理 HTTP 请求、Web 页面、实时 Web 通信。Servlet、Jakarta REST 资源类、Faces 页面/组件、WebSocket endpoint。
业务组件 / Бизнес-компоненты实现业务规则、用例和应用服务。CDI bean；需要专门企业服务时可使用 Enterprise Beans（EJB）。
持久化模型 / Модель хранения描述可持久化的数据及其关系；通常不等同于处理请求的 Web 组件。JPA entity、entity listener。
消息驱动组件 / Компоненты сообщений异步消费消息，不必由 HTTP 请求直接触发。Message-driven bean（MDB，使用相应消息规范时）。
客户端/连接器类组件（视场景）客户端访问或连接企业信息系统。应用客户端、资源适配器等；具体支持取决于平台规范和配置。

2.4 什么是容器服务？ / Что дают сервисы контейнера?

  • 生命周期：创建对象、注入依赖、调用初始化/销毁回调。
  • 依赖注入（DI）：组件不必自己查找并创建所有依赖。
  • 事务：在配置或注解约定下开启、提交、回滚事务。
  • 安全：身份认证、角色授权等服务。
  • 资源管理：数据源、连接池、线程/并发、消息资源等（取决于规范与运行时）。

Контейнер управляет жизненным циклом, внедряет зависимости, может обеспечивать транзакции и безопасность, а также управляет ресурсами — например, источниками данных и пулами соединений.

优点：标准化、组件间更容易互操作、容器可统一提供企业服务。代价：需要理解规范和运行时配置；不同版本及不同服务器支持情况要匹配。

Плюсы: стандартизация, совместимость компонентов и единые корпоративные сервисы. Минусы: нужно понимать спецификации и конфигурацию runtime; версии и поддержка сервера должны совпадать.

03 · CDI / Dependency Injection

3. Jakarta EE Managed Beans 与 CDI Beans
Управляемые бины и CDI-бины

3.1 Bean 是什么？ / Что такое бин?

Bean 通常指由容器或框架创建、管理生命周期并可能注入依赖的对象。它仍然是 Java 对象，但其创建、作用域和依赖关系不完全由业务代码手动控制。

Бин — это объект Java, жизненным циклом которого управляет контейнер или фреймворк и в который могут внедряться зависимости. Это обычный Java-объект, но его создание и область действия контролируются не только прикладным кодом.

3.2 Managed Bean 与 CDI Bean 的区别 / Различия

术语陷阱：“managed bean”既可能泛指被容器管理的对象，也可能特指旧版 Java EE/Jakarta EE Managed Beans 规范或旧式 JSF @ManagedBean。现代 Jakarta EE 开发通常优先使用 CDI bean。

Терминологическая ловушка: «managed bean» может означать любой объект под управлением контейнера или конкретно старую спецификацию Managed Beans / старый JSF @ManagedBean. В современной Jakarta EE обычно предпочитают CDI-бин.

比较点传统 Managed Bean（旧术语/旧机制）CDI Bean（现代主流）
核心目标以较简单的方式让 Java 类受容器管理；早期也用于 JSF 页面支持。统一、类型安全的依赖注入和上下文生命周期管理。
依赖注入能力较有限，取决于具体机制。支持 @Inject、qualifier、producer 等。
作用域 / Scope取决于所用的旧机制；历史 JSF 有自己的作用域注解。例如 @RequestScoped、@SessionScoped、@ApplicationScoped、@Dependent。
高级能力较有限。还可支持拦截器、装饰器、事件、替代实现等。
现代建议维护旧项目时可能遇到；新项目不要把它和 CDI 混为一谈。优先考虑 CDI；是否能用取决于运行时是否提供相应 CDI 能力。

3.3 CDI 的核心概念 / Основные понятия CDI

  • DI（Dependency Injection，依赖注入）：容器把依赖交给对象，而不是对象自己 new 所有依赖。
  • Scope（作用域）：决定 bean 在什么上下文中保持可用，以及实例大致如何复用。
  • Qualifier（限定符）：当多个实现都满足同一类型时，明确选择哪一个。
  • Producer（生产者）：用方法或字段提供由容器管理的对象，适用于不能直接按默认规则创建的对象。
  • Interceptor / Decorator：横切关注点或对业务行为做可组合的增强。
  • Events（事件）：发布者与观察者可以不直接持有对方的引用。

3.4 示例 / Пример

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.inject.Inject;

@ApplicationScoped
public class BookService {
    @Inject
    BookRepository repository;

    public Book findBook(Long id) {
        return repository.findById(id)
            .orElseThrow();
    }
}

这里 @ApplicationScoped 表示应用级上下文中的 CDI bean；@Inject 请求容器注入 BookRepository。实际项目中，Repository 的实现可能由 Jakarta Data、Spring Data 或自定义代码提供，取决于采用的技术栈。

Здесь @ApplicationScoped задаёт область действия CDI-бина, а @Inject просит контейнер внедрить BookRepository. Реализация репозитория может предоставляться Jakarta Data, Spring Data или собственным кодом — в зависимости от стека.

答辩句：CDI 是 Jakarta EE 中的上下文与依赖注入机制。CDI bean 不只是“有注解的类”，关键在于容器识别它、管理它的上下文/生命周期，并为它提供依赖注入等服务。

Ответ: CDI — это механизм контекстов и внедрения зависимостей в Jakarta EE. CDI-бин — не просто класс с аннотацией: контейнер распознаёт его, управляет контекстом и жизненным циклом и предоставляет DI и другие сервисы.

04 · Object-relational mapping

4. ORM、Hibernate 与 EclipseLink
Концепция ORM. Hibernate и EclipseLink

4.1 ORM 是什么？ / Что такое ORM?

ORM（Object-Relational Mapping，对象关系映射）是一种把面向对象程序中的类、对象、属性和关联映射到关系数据库的表、行、列和外键的技术。它让程序可以主要使用 Java 对象操作数据，由 ORM 框架生成或执行相应 SQL。

ORM (Object-Relational Mapping) — технология отображения классов, объектов, полей и связей объектной модели на таблицы, строки, столбцы и внешние ключи реляционной БД. Приложение работает преимущественно с объектами, а ORM формирует и выполняет SQL.

读取时，ORM 将结果集映射为实体对象；写入时，根据实体状态和映射关系生成 INSERT/UPDATE/DELETE；事务决定一组数据库操作如何提交或回滚。

При чтении ORM преобразует результаты запросов в объекты. При записи на основе состояния сущностей и метаданных формируются INSERT/UPDATE/DELETE. Транзакция определяет, какие операции будут зафиксированы или отменены вместе.

4.3 ORM 的优缺点 / Плюсы и минусы ORM

优势 / Преимущества

  • 减少重复 JDBC/SQL 映射代码。
  • 用对象关系表达领域模型。
  • 提供实体状态管理、级联、查询抽象、缓存等能力。
  • 提高常规 CRUD 的开发效率。

Меньше шаблонного JDBC-кода; объектная модель; управление состоянием, связями и кэшем; быстрее разрабатывать типовые CRUD-операции.

代价 / Недостатки

  • 复杂查询可能仍需 SQL 或数据库专用能力。
  • 懒加载可能引发 N+1 查询或会话关闭异常。
  • 抽象层可能隐藏 SQL 性能问题。
  • 复杂映射、缓存和事务行为需要学习成本。

Сложные запросы всё ещё требуют SQL; lazy loading может вызвать N+1 или ошибку после закрытия сессии; абстракция скрывает проблемы производительности; сложное отображение и кэширование требуют опыта.

4.4 Hibernate 与 EclipseLink：共同点和区别 / Сходства и различия

两者都是 ORM 框架，也都可以作为 Jakarta Persistence 的实现。若应用只使用标准 Jakarta Persistence API，切换 provider 的可能性会更高；如果依赖 Hibernate/EclipseLink 的专有 API、扩展注解或特定行为，迁移成本会上升。

Оба продукта — ORM-фреймворки и реализации Jakarta Persistence. Если приложение использует только стандартный API, перенос между провайдерами обычно проще. Зависимость от собственных API, расширений и специфического поведения увеличивает стоимость миграции.

比较项Hibernate ORMEclipseLink
定位广泛使用的 ORM，提供 Jakarta Persistence 实现及自己的原生 API。Eclipse Foundation 维护的持久化框架，提供 Jakarta Persistence 实现，并支持额外的映射能力。
标准 APIEntityManager、JPQL、Criteria API 等；同时有 Session、HQL 等 Hibernate API。EntityManager、JPQL、Criteria API 等；也有 EclipseLink 专有扩展 API。
特色成熟生态、丰富文档与集成、Hibernate 特定查询/缓存/审计等扩展。标准持久化能力，以及对象关系映射之外的 XML/JSON 映射生态（如 MOXy）和专有扩展。
优势社区和第三方集成广泛，很多 Java 项目与教程默认使用它。标准化背景强，适合需要其映射扩展或已有 EclipseLink 技术栈的项目。
注意事项专有功能会降低 provider 可替换性；仍需关注 SQL、抓取策略和缓存。同样需要理解 provider 特有配置、映射行为及版本兼容性。
怎么选根据团队经验、框架集成、性能测试和项目需要选择。根据既有系统、标准/扩展需求、运行环境和实际测试选择。

不要这样回答：“Hibernate 是 ORM，EclipseLink 是 JPA。”更准确的是：ORM 是一种技术类别；Jakarta Persistence 是标准；Hibernate 和 EclipseLink 都是可实现该标准的 ORM provider。

Не говорите: «Hibernate — ORM, а EclipseLink — JPA». Точнее: ORM — подход, Jakarta Persistence — спецификация, а Hibernate и EclipseLink — ORM-провайдеры, реализующие эту спецификацию.

05 · Standard persistence API

5. Jakarta Persistence（以前称 JPA）
Технология Jakarta Persistence

5.1 它是什么？ / Что это такое?

Jakarta Persistence 是 Java 环境中的持久化和 ORM 标准。JPA 是它的历史名称（Java Persistence API）。它定义实体映射、实体管理、查询、关系、锁、缓存相关的标准行为，但它本身不是一个数据库，也不是 ORM 实现。

Jakarta Persistence — стандарт API для хранения данных и ORM в Java. JPA — его историческое название (Java Persistence API). Спецификация определяет сущности, отображение, управление состоянием, запросы и связи, но сама не является ни базой данных, ни ORM-реализацией.

5.2 关键 API / Основные API

API / 注解作用 / Назначение
@Entity标记一个类为持久化实体。
@Id、@GeneratedValue定义实体标识以及可选的主键生成策略。
@ManyToOne、@OneToMany、@OneToOne、@ManyToMany描述实体之间的关联关系。
EntityManagerFactory创建 EntityManager；通常创建成本较高，按持久化单元管理。
EntityManager核心接口：管理持久化上下文，查找、持久化、合并、删除实体和执行查询。
TypedQuery / Query执行 JPQL 或原生 SQL 等查询。
CriteriaBuilder / Criteria API以程序化方式构造类型安全程度较高的动态查询。
JPQL面向实体及其属性的查询语言，不是直接以数据库表名和列名为中心。

5.3 实体生命周期与 EntityManager / Жизненный цикл сущности

状态 / Состояние含义 / Значение
New / Transient（新建）刚创建的 Java 对象，还没有被当前持久化上下文管理。
Managed（受管理）实体由当前 persistence context 管理；对其受跟踪属性的更改可在同步时写入数据库。
Detached（游离）曾经受管理，但现在不再属于当前 persistence context。
Removed（待删除）已标记删除，通常在 flush/事务提交时执行数据库删除。
 
// 省略事务与依赖注入配置，仅展示核心 API
Book book = new Book();
book.setTitle("Database Systems");

entityManager.persist(book);          // 新对象进入 managed 状态
Book found = entityManager.find(Book.class, 1L); // 按主键查找
Book managedCopy = entityManager.merge(detachedBook); // 合并 detached 对象状态
entityManager.remove(found);          // 删除一个 managed 实体

常见追问：persist 和 merge 有什么区别？persist 用于让新实体进入持久化上下文；merge 把传入实体的状态复制/合并到一个受管理实例，并返回该受管理实例。不要默认认为 merge 返回的对象与传入对象是同一个引用。

Частый вопрос: чем отличаются persist и merge? persist делает новую сущность управляемой. merge переносит состояние переданного объекта в управляемый экземпляр и возвращает этот экземпляр; не следует считать, что возвращённая ссылка обязательно совпадает с исходной.

应用代码调用标准 API；运行时由配置选定的 provider 负责把标准调用转成具体 SQL 和数据库操作。在 Jakarta EE 容器中，数据源和事务可以由容器管理；在 Java SE 或 Spring 应用中，也可以通过相应配置使用 Jakarta Persistence provider。

Приложение вызывает стандартный API, а выбранный провайдер преобразует вызовы в SQL и операции БД. В Jakarta EE контейнер может управлять источником данных и транзакциями; в Java SE или Spring Persistence-провайдер также можно подключить через соответствующую конфигурацию.

5.5 优点、缺点与适用场景 / Плюсы, минусы и применение

  • 优点：统一标准、减少对某个 provider 的直接依赖、对象关系映射、支持查询和实体状态管理。
  • 缺点：抽象不能消除 SQL 与数据库差异；复杂查询、批处理和性能调优仍需理解 SQL；惰性加载和事务边界需要谨慎处理。
  • 适用：领域对象与关系表有较自然映射、需要事务和关联管理的企业应用。

Плюсы: единый стандарт, объектное отображение, управление связями и состоянием. Минусы: не устраняет различия SQL и БД; сложные запросы и оптимизация требуют знания SQL; нужно правильно управлять lazy loading и транзакциями. Подходит для корпоративных приложений с объектной доменной моделью и реляционной БД.

06 · Repository abstraction standard

6. Jakarta Data
Технология Jakarta Data

6.1 为什么需要 Jakarta Data？ / Зачем нужна Jakarta Data?

即使有了 ORM，开发者仍可能要写很多重复的数据访问代码，例如按 ID 查询、保存、删除、排序、分页和自定义查询。Jakarta Data 在更高层提供 Repository 抽象：开发者声明仓库接口和方法，兼容实现根据规范提供实际行为。

Даже при наличии ORM приходится писать повторяющийся код доступа к данным: поиск по ID, сохранение, удаление, сортировку, пагинацию и запросы. Jakarta Data добавляет более высокий уровень абстракции Repository: разработчик объявляет интерфейс и методы, а совместимая реализация предоставляет поведение.

6.2 核心概念 / Основные понятия

  • Repository：面向某类实体或数据源的数据访问接口。
  • 预定义仓库接口：如 CrudRepository、BasicRepository，提供常见 CRUD 或基础访问操作。
  • 派生查询：通过符合规范的方法名表达查询意图，由实现解析方法。
  • 查询注解/查询语言：对复杂查询可以显式声明查询，而不是仅靠方法名。
  • 分页与排序：支持用统一 API 表达常见结果窗口、排序和分页需求；细节仍取决于规范版本和 provider 能力。
  • 持久化无关性：目标是让数据访问 API 尽量不绑定某一种存储技术，但并不保证不同数据库之间完全无修改迁移。

6.3 示例 / Пример

import jakarta.data.repository.CrudRepository;
import jakarta.data.repository.Repository;
import java.util.List;

@Repository
public interface BookRepository
        extends CrudRepository<Book, Long> {
    List<Book> findByTitle(String title);
}

接口表达“我需要哪些数据操作”，通常不需要手动写出每个基础 CRUD 方法的实现。具体方法名规则、返回类型、查询注解和支持范围应以所用 Jakarta Data 版本及 provider 文档为准。

Интерфейс описывает необходимые операции; базовую реализацию CRUD обычно не нужно писать вручную. Правила имён методов, возвращаемые типы, аннотации запросов и доступные возможности нужно сверять с версией Jakarta Data и документацией провайдера.

6.4 Jakarta Data 与 Jakarta Persistence 的区别 / Отличие от Persistence

维度Jakarta PersistenceJakarta Data
抽象层次更接近实体管理、映射、持久化上下文和查询执行。更高层的数据访问/Repository 编程模型。
核心 APIEntityManager、实体映射、JPQL、Criteria API。Repository、CrudRepository、派生查询、分页/排序等。
是否互相替代不替代。Jakarta Data 的目标是简化访问并与持久化技术协作，而不是复制或取代 Persistence / NoSQL 规范。
控制力与简洁度控制力较细，开发者需更直接地管理查询与持久化行为。样板代码更少，但需要遵守 Repository 方法约定；遇到复杂需求时仍可能要使用底层 API。

版本提醒：Jakarta Data 1.0 随 Jakarta EE 11 发布；截至本手册日期，Jakarta Data 1.1 仍处于开发草案阶段。因此答辩时要区分已经发布的规范与草案中的新功能。

О версии: Jakarta Data 1.0 вошла в Jakarta EE 11; на дату этого конспекта Jakarta Data 1.1 всё ещё находится в разработке. На защите различайте опубликованную спецификацию и функции проекта спецификации.

6.5 优缺点 / Плюсы и минусы

优点：减少重复代码、接口更清晰、方法名查询便于常规检索、提升数据访问层可读性。局限：规范和实现生态相对较新；各 provider 支持范围可能不同；复杂查询和数据库特性仍需专门处理。

Плюсы: меньше шаблонного кода, более ясный интерфейс репозитория, удобные типовые запросы. Ограничения: экосистема моложе; поддержка провайдеров может различаться; сложные запросы и особенности БД всё равно требуют отдельной работы.

7. Spring 平台与 Jakarta EE 的相似点和区别
Платформа Spring. Сходства и отличия с Java EE

7.1 Spring 是什么？ / Что такое Spring?

Spring Framework 是用于构建 Java 应用的模块化框架。核心能力包括 IoC/DI（控制反转/依赖注入）、AOP（面向切面编程）、事务抽象、Web MVC、数据访问集成等。Spring 生态还包括 Spring Boot、Spring Data、Spring Security、Spring Batch 等独立项目。

Spring Framework — модульный фреймворк для Java-приложений. Основные возможности: IoC/DI, AOP, абстракция транзакций, Spring MVC и интеграция с доступом к данным. В экосистему также входят отдельные проекты: Spring Boot, Spring Data, Spring Security, Spring Batch и другие.

7.2 Jakarta EE 与 Spring：不是简单的二选一 / Это не просто взаимоисключающие варианты

维度Jakarta EESpring Framework
本质由多项标准规范组成的平台，强调标准 API 与兼容实现。应用开发框架及其生态，提供自己的编程模型和大量集成能力。
依赖注入以 CDI 等 Jakarta 规范为主，常见注解如 @Inject。Spring IoC 容器；常见 @Autowired、构造器注入，也支持标准 @Inject。
Web 层Servlet、Jakarta REST、Faces、WebSocket 等标准。Spring MVC、WebFlux 等框架选择。
事务Jakarta Transactions/JTA 等标准服务；容器可管理事务。Spring 事务抽象，支持多种事务管理器，也可集成 JTA/JPA。
运行方式传统方式部署到兼容应用服务器，也可按具体规范/运行时在较轻环境中运行。可部署到外部容器，也常通过 Spring Boot 打包为带嵌入式服务器的可执行应用。
可移植性使用标准 API 有助于在兼容实现间移植，但仍需考虑版本、扩展和服务器差异。Spring 应用通常依赖 Spring API；其优势是统一开发模型和生态集成。
典型优势标准化、厂商间规范契约、企业服务覆盖全面。开发体验灵活、生态广、配置和集成选择丰富。
典型成本规范、运行时和部署配置可能较复杂；不同服务器的产品差异仍存在。需要管理 Spring 生态依赖和版本；过度依赖特定抽象可能增加迁移成本。

7.3 它们能一起用吗？ / Можно ли использовать вместе?

可以。Spring 能集成 Servlet、Jakarta Persistence、Bean Validation、事务等 Jakarta 技术。Spring 不是 Jakarta EE 规范本身，但二者不是完全隔离的世界。要特别注意版本兼容：现代 Spring 版本使用 jakarta.* 命名空间，而旧应用可能使用 javax.*。

Да. Spring может интегрироваться с Servlet, Jakarta Persistence, Bean Validation, транзакциями и другими технологиями Jakarta. Spring не является спецификацией Jakarta EE, но эти экосистемы не изолированы друг от друга. Важно проверять совместимость версий: современные версии Spring используют пространство имён jakarta.*, старые приложения могут использовать javax.*.

答辩句：Jakarta EE 更强调由标准规范定义 API 和兼容性；Spring 更强调框架提供的统一开发模型和生态集成。Spring 可以使用 Jakarta 标准技术，所以不能简单说二者完全对立。

Ответ: Jakarta EE делает акцент на стандартизированных API и совместимых реализациях, а Spring — на единой модели разработки и интеграции экосистемы. Spring может использовать технологии Jakarta, поэтому эти подходы не являются полностью противоположными.

08 · Application bootstrap

8. Spring Boot

8.1 它是什么？ / Что это такое?

Spring Boot 建立在 Spring Framework 之上，目标是减少创建、配置、运行 Spring 应用时的样板工作。它的核心特征包括自动配置、Starter 依赖、外部化配置、嵌入式服务器选项、可执行归档，以及 Actuator 等生产环境管理能力。

Spring Boot построен поверх Spring Framework и уменьшает объём шаблонной работы при создании, настройке и запуске приложения. Основные возможности: автоконфигурация, Starter-зависимости, внешняя конфигурация, встроенный сервер, исполняемый архив и средства эксплуатации вроде Actuator.

8.2 三个重要机制 / Три ключевых механизма

自动配置 / Auto-configuration

根据 classpath 中的依赖、已有 bean 和配置条件，尝试提供合理的默认配置。开发者可以定义自己的 bean 或显式排除某些自动配置。

По зависимостям в classpath, существующим бинам и условиям Boot пытается применить подходящие настройки по умолчанию. Их можно заменить собственными бинами или отключить отдельную автоконфигурацию.

Starter

一组经过协调的依赖描述符。例如 Web、JPA、测试等 Starter 帮助一次引入常用依赖，并减少版本冲突。

Набор согласованных зависимостей. Например, Web-, JPA- и тестовые Starter позволяют подключить типичный стек и уменьшают риск конфликтов версий.

嵌入式服务器 / Embedded server

常见 Web 应用可以把服务器作为依赖打包，运行可执行 JAR，而不必总是先安装并单独管理外部服务器。

Типичное веб-приложение может включать сервер как зависимость и запускаться из исполняемого JAR без обязательной отдельной установки внешнего сервера.

外部化配置 / Externalized config

可通过配置文件、环境变量、命令行参数等在不同环境中调整设置，而不把环境差异写死在代码里。

Настройки можно задавать через файлы конфигурации, переменные окружения и аргументы командной строки, не зашивая различия окружений в код.

8.3 最小示例 / Минимальный пример

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class Application {
    public static void main(String[] args) {
        SpringApplication.run(Application.class, args);
    }
}

@SpringBootApplication 是组合注解，包含配置类、自动配置和组件扫描等核心功能。它并不意味着应用没有配置，而是让常见配置拥有合理默认值，并允许按需覆盖。

@SpringBootApplication — составная аннотация, объединяющая конфигурацию, автоконфигурацию и сканирование компонентов. Это не означает отсутствие конфигурации: Boot задаёт разумные значения по умолчанию и позволяет переопределять их.

8.4 Spring Boot 的优缺点 / Плюсы и минусы

优点 / Плюсы缺点 / Минусы
启动项目快；默认配置降低入门成本；依赖版本更容易统一；便于打包、部署和监控。自动配置有时像“黑盒”；需要排查条件报告、依赖和版本；默认值不一定适合高负载或特殊部署；升级时要关注兼容性。

常见误区：Spring Boot 不是 Spring 的替代品，而是建立在 Spring Framework 之上的快速配置与启动方案；Spring Boot 也不是数据库层或 ORM。

Типичная ошибка: Spring Boot не заменяет Spring Framework, а упрощает настройку и запуск приложений на его основе. Spring Boot также не является ORM или слоем базы данных.

09 · Spring data access

9. Spring Data

9.1 它是什么？ / Что это такое?

Spring Data 是 Spring 生态中的一组数据访问项目，目标是减少数据访问层的重复代码，并提供相对统一的 Repository 编程模型。它不是单一 ORM，也不只支持关系数据库：有 Spring Data JPA、JDBC、MongoDB、Redis、Cassandra、Elasticsearch 等模块。

Spring Data — набор проектов экосистемы Spring для упрощения доступа к данным и уменьшения шаблонного кода через модель Repository. Это не один ORM и не только реляционные БД: существуют модули JPA, JDBC, MongoDB, Redis, Cassandra, Elasticsearch и другие.

9.2 Repository 抽象 / Абстракция Repository

开发者声明 Repository 接口，Spring Data 根据接口继承、方法名、查询注解和所用模块生成实现或代理。基础 CRUD 不必每次手写；复杂查询可以用 @Query 或相应模块的能力。

Разработчик объявляет интерфейс Repository, а Spring Data создаёт реализацию или прокси на основе базового интерфейса, имени метода, аннотаций запросов и конкретного модуля. CRUD обычно не нужно писать вручную; сложные запросы можно задавать через @Query или API модуля.

9.3 Spring Data JPA 示例 / Пример Spring Data JPA

import org.springframework.data.jpa.repository.JpaRepository;
import java.util.List;

public interface BookRepository
        extends JpaRepository<Book, Long> {
    List<Book> findByTitleContainingIgnoreCase(String keyword);
}

这里 JpaRepository 是 Spring Data JPA 的接口，不是 Jakarta Persistence 的接口。底层通常仍通过 Jakarta Persistence API 与 JPA provider（例如 Hibernate）交互。

Здесь JpaRepository — интерфейс Spring Data JPA, а не Jakarta Persistence. Внизу он обычно взаимодействует с JPA-провайдером (например, Hibernate) через API Jakarta Persistence.

9.4 Spring Data 与 Jakarta Data 的区别 / Spring Data и Jakarta Data

维度Spring DataJakarta Data
归属Spring 项目集合，由 Spring 生态维护。Jakarta EE 标准规范体系的一部分。
设计目标针对多种数据存储提供成熟、模块化的 Repository 抽象。定义标准化、尽量持久化技术无关的数据访问 API。
模块/生态覆盖面广、模块细分多、与 Spring Boot 集成紧密。目标是跨 Jakarta 数据技术提供统一编程模型；生态和实现成熟度取决于规范版本。
典型 APICrudRepository、JpaRepository、MongoRepository、@Query。CrudRepository、BasicRepository、@Repository、规范定义的查询方法。
兼容性属于 Spring 编程模型；不同 Spring Data 模块有自己的功能差异。标准化意图更强，但仍需看 provider 支持和底层数据源能力。
成熟度取舍通常有更成熟的模块生态和丰富的具体功能。标准化价值突出，但较新版本和实现支持需谨慎核实。

这张图是非常重要的答辩内容：Spring Data JPA 不等于 JPA；JPA 不等于 Hibernate。Spring Data JPA 简化仓库操作，Jakarta Persistence 定义标准 API，Hibernate 负责具体 ORM 实现，JDBC 与数据库完成底层交互。

Это ключевая схема для защиты: Spring Data JPA — не то же самое, что JPA; JPA — не то же самое, что Hibernate. Spring Data JPA упрощает репозитории, Jakarta Persistence определяет стандартный API, Hibernate реализует ORM, а JDBC взаимодействует с БД.

11 · Oral exam practice

11. 高频答辩问题与中俄双语参考答案
Частые вопросы и ответы для устной защиты

建议练习方式：先遮住答案，用俄语说出关键词；然后展开核对。每个答案是口试的基础版本，可以根据老师追问继续补充。

Q1. Что такое шаблон проектирования? / 什么是设计模式？

设计模式是对软件设计中常见问题的可复用解决方案，描述对象和类如何协作，而不是一段可直接复制的完整代码。

Шаблон проектирования — повторно используемое решение типовой проблемы проектирования, описывающее взаимодействие объектов и классов, а не готовый фрагмент кода.

Q2. Чем архитектурный шаблон отличается от шаблона проектирования?

架构模式关注系统整体结构和组件通信；设计模式关注较小范围的类与对象协作。例如微服务是架构模式，Strategy 是设计模式。

Архитектурный шаблон определяет структуру системы и взаимодействие компонентов; шаблон проектирования описывает сотрудничество классов и объектов. Например, микросервисы — архитектура, Strategy — шаблон проектирования.

Q3. Что такое Jakarta EE?

Jakarta EE 是一组面向企业级 Java 应用的标准规范，提供 Web、依赖注入、事务、安全、持久化和消息等 API。兼容运行时提供这些规范的实现及容器服务。

Jakarta EE — набор стандартных спецификаций для корпоративных Java-приложений. Он предоставляет API для Web, DI, транзакций, безопасности, хранения данных и сообщений. Совместимый runtime реализует спецификации и предоставляет сервисы контейнера.

Q4. Какие бывают компоненты Jakarta EE?

常见有 Web 组件，例如 Servlet、REST 资源和 WebSocket endpoint；业务组件，例如 CDI bean 和 Enterprise Beans；持久化实体则主要用于描述数据模型。组件可使用容器提供的依赖注入、事务和安全服务。

К типичным компонентам относятся веб-компоненты (Servlet, REST-ресурсы, WebSocket endpoint) и бизнес-компоненты (CDI-бин, Enterprise Bean). Сущности описывают модель данных. Компоненты могут использовать DI, транзакции и безопасность контейнера.

Q5. Что такое CDI?

CDI 是上下文与依赖注入规范，负责识别 bean、管理作用域与生命周期、注入依赖，还提供限定符、生产者、事件和拦截器等机制。

CDI — спецификация контекстов и внедрения зависимостей. Она распознаёт бины, управляет областями действия и жизненным циклом, внедряет зависимости и поддерживает qualifiers, producers, события и интерсепторы.

Q6. Что такое ORM и зачем он нужен?

ORM 把 Java 对象映射到关系数据库的表和关系，减少手写 JDBC 映射代码。它提高 CRUD 开发效率，但不消除 SQL、事务和性能调优的必要性。

ORM отображает Java-объекты на таблицы и связи реляционной БД, уменьшая объём ручного JDBC-кода. Он ускоряет CRUD-разработку, но не отменяет необходимость понимать SQL, транзакции и оптимизацию.

Q7. Чем отличаются Hibernate и EclipseLink?

二者都是 ORM 框架和 Jakarta Persistence provider，都支持标准 EntityManager、实体映射和 JPQL；它们的社区、扩展 API、集成方式和附加功能不同。应按需求和测试选择。

Оба являются ORM-фреймворками и провайдерами Jakarta Persistence, поддерживают EntityManager, отображение сущностей и JPQL. Они различаются экосистемой, расширениями, интеграциями и дополнительными возможностями. Выбор зависит от требований и тестов.

Q8. Что такое Jakarta Persistence?

它是 Java 持久化和 ORM 的标准 API，定义实体、EntityManager、JPQL、Criteria API 等。它是规范，不是具体 ORM 实现；Hibernate 和 EclipseLink 可以实现它。

Это стандартный API хранения данных и ORM для Java. Он определяет сущности, EntityManager, JPQL и Criteria API. Это спецификация, а не конкретный ORM; её могут реализовывать Hibernate и EclipseLink.

Q9. Чем отличаются persist и merge?

persist 用于让新实体成为受管理实体；merge 将传入对象的状态合并到受管理实例并返回该实例，尤其要注意返回对象不一定是原对象。

persist делает новую сущность управляемой. merge переносит состояние переданного объекта в управляемый экземпляр и возвращает его; возвращаемый объект не обязательно является исходным.

Q10. Что такое Jakarta Data?

Jakarta Data 是简化数据访问的标准 API，通过 Repository、预定义接口和查询方法减少样板代码。它与 Jakarta Persistence 协作，而不是取代后者。

Jakarta Data — стандартный API для упрощения доступа к данным через Repository, готовые интерфейсы и методы запросов. Он дополняет Jakarta Persistence, а не заменяет её.

Q11. В чём разница между Jakarta EE и Spring?

Jakarta EE 是规范平台，强调标准化 API 和兼容实现；Spring 是应用框架及其生态，提供 IoC/DI、AOP、Web 和事务等能力。Spring 也可以集成 Jakarta 标准技术。

Jakarta EE — платформа спецификаций со стандартизированными API и совместимыми реализациями. Spring — фреймворк и экосистема с IoC/DI, AOP, Web и транзакциями. Spring также может интегрироваться с технологиями Jakarta.

Q12. Что такое Spring Boot?

Spring Boot 建立在 Spring Framework 上，通过自动配置、Starter、外部化配置和嵌入式服务器选项简化应用的创建、启动和部署。

Spring Boot построен поверх Spring Framework и упрощает создание, запуск и развёртывание приложения с помощью автоконфигурации, Starter-зависимостей, внешней конфигурации и встроенного сервера.

Q13. Чем Spring Boot отличается от Spring Framework?

Spring Framework 提供核心能力，例如依赖注入、AOP 和 Web 框架；Spring Boot 在其基础上提供自动配置、依赖组合和更简单的运行/部署方式。

Spring Framework предоставляет базовые возможности, например DI, AOP и веб-фреймворки. Spring Boot добавляет автоконфигурацию, наборы зависимостей и упрощённый запуск и развёртывание.

Q14. Что такое Spring Data?

Spring Data 是一组简化数据访问的项目，通过 Repository 抽象、方法名查询和查询注解减少重复代码，支持关系数据库以及多种 NoSQL 数据存储。

Spring Data — набор проектов для упрощения доступа к данным. Абстракция Repository, запросы по имени метода и аннотации уменьшают шаблонный код; поддерживаются реляционные и различные NoSQL-хранилища.

Q15. Чем Spring Data JPA отличается от Jakarta Persistence?

Spring Data JPA 是 Spring 的 Repository 层抽象，通常建立在 Jakarta Persistence 之上；Jakarta Persistence 是标准持久化 API。底层 provider（例如 Hibernate）负责 ORM 的具体实现。

Spring Data JPA — абстракция Repository в экосистеме Spring, обычно работающая поверх Jakarta Persistence. Jakarta Persistence — стандартный API хранения данных, а провайдер (например, Hibernate) выполняет ORM.

Q16. Какие плюсы и минусы у ORM?

优点是减少样板代码、使用对象模型、简化关联和常见 CRUD；缺点是可能隐藏 SQL 性能问题，复杂查询和懒加载需要额外理解，也可能产生 N+1 查询。

Плюсы — меньше шаблонного кода, объектная модель, удобные связи и CRUD. Минусы — возможные скрытые проблемы SQL, сложные запросы, нюансы lazy loading и проблема N+1.

Q17. Почему нельзя сказать, что Jakarta Data заменяет Jakarta Persistence?

因为两者抽象层不同。Jakarta Persistence 管理实体映射和持久化上下文；Jakarta Data 通过 Repository 简化常见数据访问。Jakarta Data 的目标是协作和补充，而不是复制底层持久化功能。

Потому что уровни абстракции различаются. Jakarta Persistence управляет отображением сущностей и контекстом хранения, а Jakarta Data упрощает типовой доступ через Repository. Jakarta Data дополняет Persistence, а не дублирует её низкоуровневые функции.

Q18. Что такое внедрение зависимостей и зачем оно нужно?

依赖注入是把对象需要的依赖从外部提供给它，而不是让对象自己创建依赖。它降低耦合，便于替换实现和单元测试。缺点是需要理解容器和依赖装配过程。

Внедрение зависимостей означает, что необходимые объекту зависимости предоставляет внешний контейнер, а не сам объект создаёт их. Это снижает связанность и упрощает замену реализаций и тестирование, но требует понимания контейнера и конфигурации.

12.3 最容易扣分的说法 / Типичные ошибки

  • 不要说 Hibernate = JPA。正确：Hibernate 可以实现 Jakarta Persistence。
  • 不要说 Spring Boot = Spring。正确：Boot 建立在 Spring Framework 之上。
  • 不要说 Jakarta Data = Jakarta Persistence。正确：Data 是更高层的访问抽象，Persistence 管理实体映射和持久化。
  • 不要说 Spring Data JPA 是 ORM。更准确：它提供 Repository 抽象，通常通过 JPA 与 ORM provider 交互。
  • 不要绝对化比较性能。Hibernate 和 EclipseLink 的表现取决于查询、映射、缓存、数据库、配置和测试场景。
  • 不要把所有有注解的 Java 类都称为 CDI bean。容器是否识别并按 CDI 规则管理它，才是关键。

Не смешивайте Hibernate и JPA, Spring и Spring Boot, Jakarta Data и Jakarta Persistence. Не называйте Spring Data JPA ORM-провайдером. Не делайте абсолютных выводов о производительности без измерений. Не каждый Java-класс с аннотацией автоматически является CDI-бином.
