设计模式与架构模式 Паттерны проектирования и архитектурные паттерны

先分清：一个帮助安排类和对象，另一个帮助安排整个系统。
Сначала различайте: одни помогают организовать классы и объекты, другие — систему целиком.

先用直观的话理解Сначала простое объяснение

模式是对常见问题的一种可复用解决思路，不是一段复制后就能运行的代码。设计模式主要讨论类和对象怎样分工、创建和协作；架构模式主要讨论系统分成哪些部分，以及这些部分怎样联系。
Паттерн — повторно применимый подход к типичной проблеме, а не готовый исполняемый код. Паттерны проектирования в основном описывают создание, обязанности и взаимодействие классов и объектов; архитектурные — части системы и связи между ними.

看一个贯穿实验的例子Один пример из лабораторной

电影系统可以分为：页面 → 请求入口 MovieResource → 业务逻辑 MovieService → 数据访问 Database。这样划分职责是分层架构。若评分规则经常变化，可以把每种规则放到独立的策略对象中，让服务选择策略；这是 Strategy 设计模式。
Систему фильмов можно разделить так: страница → вход запросов MovieResource → бизнес-логика MovieService → доступ к данным Database. Это распределение обязанностей иллюстрирует слоистую архитектуру. Если правила оценки часто меняются, каждое правило можно вынести в отдельный объект-стратегию; это паттерн Strategy.
架构决定“大部分怎样组织”，设计模式帮助实现“某一部分怎样工作”。同一个系统可以同时采用两者。
Архитектура задаёт организацию крупных частей, а паттерны проектирования помогают реализовать работу отдельных частей. В одной системе применимы оба подхода.

把它理解为企业 Java 应用的一组共同规则；运行环境负责实现这些规则。

Jakarta EE 到底是什么Что такое Jakarta EE

开发 Web 系统时，经常需要接收请求、管理服务对象、访问数据库、执行事务和校验数据。Jakarta EE 为这些常见工作定义标准 API 和行为。它建立在 Java SE 之上，不是一个单独的服务器程序。
В веб-системе нужны приём запросов, управление сервисными объектами, доступ к БД, транзакции и проверка данных. Jakarta EE определяет стандартные API и поведение для этих задач. Платформа построена поверх Java SE и не является одной конкретной серверной программой.
规范告诉开发者“可以依赖哪些接口与行为”；Payara、WildFly、GlassFish 等相应兼容产品提供运行支持。就像规则与执行规则的程序，二者不能混为一谈。
Спецификация определяет доступные интерфейсы и поведение; соответствующие совместимые продукты, например Payara, WildFly и GlassFish, предоставляют среду выполнения. Правила и программа, выполняющая эти правила, — разные вещи.

API、容器和版本怎么区分Как различать API, контейнер и версии

API 是你在代码中调用的接口与注解；容器是管理组件运行的环境。仅加入 API 依赖，只能解决编译所需的类型，不代表已经具备所有运行服务。Full Platform、Web Profile、Core Profile 提供的标准能力范围不同。
API — интерфейсы и аннотации в коде; контейнер — среда управления компонентами. Зависимость с API даёт типы для компиляции, но сама не обеспечивает все сервисы выполнения. Full Platform, Web Profile и Core Profile отличаются набором гарантированных возможностей.
Java EE 是 Jakarta EE 的前身。Jakarta EE 9 起，相关企业 API 从 javax.* 迁到 jakarta.*；Java SE 中的 javax.sql 等包仍保留。你的实验使用 Java 17 与 Jakarta EE 10 API。标准化有利于移植与协作，但仍需关注服务器版本、配置和提供者差异。
Java EE — предшественник Jakarta EE. Начиная с EE 9 соответствующие корпоративные API перешли с javax.* на jakarta.*; пакеты Java SE, например javax.sql, сохранились. В лабораторной используются Java 17 и Jakarta EE 10 API. Стандартизация помогает переносимости и совместной работе, но версии серверов, настройки и различия провайдеров по-прежнему важны.

受管 Bean、CDI 与 EJB Управляемые бины, CDI и EJB

这一题围绕两个问题：对象由谁管理？它能得到哪些容器服务？
Два главных вопроса: кто управляет объектом и какие сервисы контейнера он получает?

先理解什么是受管 BeanСначала: что такое управляемый бин

普通 Java 对象由你 new 出来；受管 Bean 则由相应容器创建或接管，并按规则管理依赖和生命周期。在本题的日常表述中，CDI Bean 是由 CDI 机制管理的 Bean。不要把 JavaBean 的 getter/setter 约定，与容器管理对象混为一谈。
Обычный объект Java можно создать через new. Управляемый бин создаётся или принимается под управление соответствующим контейнером, который управляет зависимостями и жизненным циклом. 不要把 EJB 与 JPA 的 @Entity 混淆：前者是业务组件，后者是持久化数据模型。你的 Movie 实验使用 CDI 服务，不是 EJB 服务。
Не путайте EJB с @Entity из JPA: первое — бизнес-компонент, второе — персистентная модель данных. В вашей лабораторной Movie используются сервисы CDI, а не EJB.

从“我想查询学生”开始Начнём с «я хочу найти студента»

业务代码可能要按 ID 查学生、按姓名搜索、保存资料。若每个业务方法都直接处理连接、SQL 和结果转换，就会重复。Repository 把这些数据访问需求组织成一个业务层可调用的抽象；背后的实现负责真正访问数据。
Бизнес-код ищет студента по ID, выполняет поиск по имени и сохраняет сведения. Если каждый метод сам обрабатывает соединение, SQL и преобразование результатов, возникает повторение. Repository организует эти потребности в абстракцию для бизнес-слоя; реализация выполняет реальный доступ к данным.

Вы близки к верному пониманию, но слово «все» неточно. Repository обычно предоставляет нужные операции над сущностью или набором объектов предметной области. Он может быть только для чтения или включать запись и удаление; это не обязательно Java-интерфейс и не обязательно все возможные операции.

Jakarta Data 帮我们做了什么Что делает Jakarta Data

Jakarta Data 是标准化 Repository 编程方式的数据访问规范。你声明接口和数据操作，兼容提供者生成或提供实现。BasicRepository 包含 save、findById、delete 等基础操作；CrudRepository 在其上增加 insert、update。
Jakarta Data — спецификация доступа к данным, стандартизирующая Repository. Вы объявляете интерфейс и операции, совместимый провайдер предоставляет реализацию. BasicRepository содержит базовые операции save, findById, delete; CrudRepository добавляет insert и update.
JAVA
import jakarta.data.repository.*;
import java.util.List;

@Repository
public interface Students extends BasicRepository<Student, Long> {
    @Find
    List<Student> named(@By("name") String value);
}
Student 是实体类型，Long 是主键类型。这里 @Find 与 @By("name") 指定按 name 属性查询；named 这个方法名本身不决定查询字段。需要兼容的实体模型与 Jakarta Data 提供者。
Student — тип сущности, Long — тип ключа. @Find и @By("name") задают поиск по свойству name; само имя named не определяет поле. Нужны поддерживаемая модель сущностей и провайдер Jakarta Data.

Это разные уровни. Jakarta Data может сочетаться с реляционной персистентностью или обращаться к поддерживаемым нереляционным хранилищам; обязательной зависимости от JPA нет. Data 1.0 также не гарантирует, что результат находится в общем JPA-подобном контексте с автоматическим dirty checking.

回到你的关键追问：不写 SQL，框架凭什么知道要查哪个字段？
Вернёмся к вашему вопросу: откуда фреймворк знает поле запроса без написанного SQL?

先区分 Spring Data 与 Spring Data JPAСначала различайте Spring Data и Spring Data JPA

Spring Data 是多个数据访问项目组成的家族，包含 JPA、JDBC、MongoDB、Redis 等模块。Spring Data JPA 是其中使用 Jakarta Persistence 的模块：你声明 Repository，框架提供实现，底层再通过 JPA 与 ORM 提供者访问关系数据库。
Spring Data — семейство проектов доступа к данным с модулями JPA, JDBC, MongoDB, Redis и другими. Spring Data JPA использует Jakarta Persistence: вы объявляете Repository, фреймворк предоставляет реализацию, а доступ к реляционной БД выполняется через JPA и ORM-провайдер.
JAVA
import java.util.List;
import org.springframework.data.jpa.repository.JpaRepository;

interface StudentRepository extends JpaRepository<Student, Long> {
    List<Student> findByNameAndAgeGreaterThan(String name, int age);
}
假设 Student 是映射正确的 JPA 实体，Repository 已被 Spring Data 发现。Student 指定实体类型，Long 指定 ID 类型；常用 findById、save、deleteById 等操作从父接口获得。
Предполагается корректная JPA-сущность Student и обнаружение репозитория Spring Data. Student задаёт тип сущности, Long — тип ID; стандартные операции findById, save, deleteById и другие наследуются от родительского интерфейса.

你的追问：是通过 xxByxx 识别字段吗？Ваш вопрос: поле определяется через xxByxx?

对 Spring Data 的查询派生来说，方向是对的，但必须符合规定的语法，不是任意 xxByxx 都能使用。把例子拆开：find | By | Name | And | Age | GreaterThan。它表示“查找姓名匹配，并且年龄大于参数值的学生”。
Для выведения запросов Spring Data идея верна, но нужна установленная грамматика: не любой xxByxx допустим. Разберём пример: find | By | Name | And | Age | GreaterThan. Это означает поиск студентов с указанным именем и возрастом больше переданного значения.
TEXT
repository.findByNameAndAgeGreaterThan("Anna", 18);

WHERE student_name = ? AND age > ?
下方是帮助理解的 SQL 条件示意，参数分别绑定 Anna 与 18，并不保证生成的 SQL 文本完全相同。字段来自实体元数据，参数提供用于比较的值。
Ниже показано условие SQL для понимания: параметры связываются с Anna и 18. Фактический текст SQL может отличаться. Поля определяются по модели сущности, параметры дают сравниваемые значения.
方法名描述“哪个属性、怎样比较”；调用参数给出“与哪个值比较”。Spring Data 创建实现或代理，不是 Java 接口自己突然能执行数据库操作。
Имя метода задаёт свойство и сравнение, аргументы — значения сравнения. Реализацию или прокси создаёт Spring Data; интерфейс Java сам по себе не выполняет операции БД.

属性名和列名不同怎么办？复杂查询怎么办？Что делать с разными именами свойства и столбца или сложным запросом?

假设 Student.name 使用 @Column(name="student_name") 映射到数据库。查询方法仍写 findByName，因为解析的是 Java 实体属性 name；ORM 再依据映射使用 student_name 列。不能把它直接改成 findByStudent_name 来表示列名。
Допустим, Student.name отображается на столбец через @Column(name="student_name"). Метод остаётся findByName: разбирается Java-свойство name, а ORM использует столбец student_name по отображению. Подставлять имя столбца как findByStudent_name нельзя.
复杂查询可以用 Spring Data JPA 的 @Query 显式写 JPQL，或使用自定义实现。例如 @Query("select s from Student s where s.age > :age")。JPQL 使用实体与属性；原生 SQL 使用表与列。Jakarta Data 也有自己的查询注解，它们不是同一组 Java 注解。
Сложный запрос можно явно задать JPQL через @Query из Spring Data JPA или реализовать вручную. Например, @Query("select s from Student s where s.age > :age"). JPQL использует сущности и свойства, SQL — таблицы и столбцы. У Jakarta Data свои аннотации запросов; это разные Java-аннотации.
