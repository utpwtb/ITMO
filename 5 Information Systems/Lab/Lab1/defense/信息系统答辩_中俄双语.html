设计模式与架构模式 Шаблоны проектирования и архитектурные шаблоны

先说明模式解决什么重复出现的问题，再解释它影响的范围、代价，以及在实际系统中的位置。模式是有适用条件的设计经验，不是必须套用的代码模板。
Сначала объясните, какую повторяющуюся проблему решает шаблон, затем — масштаб его влияния, издержки и место в реальной системе. Шаблон — опыт проектирования с условиями применимости, а не обязательная заготовка кода.

1. 概念：关注点、粒度与决策代价1. Понятия: предмет решения, масштаб и цена изменений

一个完整的模式通常说明：使用情境、反复出现的问题、解决方案中的参与者及其协作，以及方案的结果与代价。它描述可复用的结构和思想；具体类名、数据库、框架和代码可以不同。评价模式要问“为什么需要这层间接性”，而不是只背 UML 图。
Полное описание шаблона обычно включает контекст, повторяющуюся проблему, участников решения и их взаимодействие, а также последствия и издержки. Повторно используется структура и идея; имена классов, база данных, фреймворк и код могут отличаться. При оценке нужно спросить, зачем нужен дополнительный уровень косвенности, а не только воспроизводить UML.
设计模式通常组织类与对象的创建、组合和交互；架构模式或架构风格通常组织子系统、职责边界、依赖方向、通信和部署。两者的边界不是绝对的：MVC 有时叫设计模式，有时叫架构模式。答辩时说明你讨论的是 UI 的结构还是整个系统的结构，比争论名称更有价值。
Шаблоны проектирования обычно организуют создание, композицию и взаимодействие классов и объектов. Архитектурные шаблоны или стили обычно задают подсистемы, границы ответственности, направление зависимостей, коммуникацию и развёртывание. Граница условна: MVC называют и шаблоном проектирования, и архитектурным шаблоном. На защите полезнее уточнить, идёт ли речь о структуре интерфейса или всей системы, чем спорить о названии.

3. Strategy：把变化的算法从业务流程中移出3. Strategy: вынести изменяемый алгоритм из бизнес-процесса

假设电影可以按不同规则计算推荐分数。不断在服务中增加 if/switch 会把所有规则耦合在一起。Strategy 把每种规则放到同一个接口的不同实现中，服务持有接口引用；选择策略可以通过普通构造器、CDI 或 Spring 注入完成。
Пусть для фильма нужно вычислять рекомендательный балл по разным правилам. Рост if/switch в сервисе связывает все правила в одном месте. Strategy выносит каждое правило в реализацию общего интерфейса, а сервис хранит ссылку на интерфейс. Выбрать стратегию можно обычным конструктором, через CDI или Spring.
Strategy 主要依赖对象组合，可在运行时更换协作者；Template Method 主要依赖继承，由父类控制流程并调用可覆盖步骤。策略更容易独立测试和组合；模板方法能集中维护固定流程，但子类与父类实现耦合更紧。只有一个稳定算法时，不必为了模式制造多个空接口。
Strategy опирается на композицию и позволяет менять сотрудничающий объект во время выполнения. Template Method опирается на наследование: родитель управляет процессом и вызывает переопределяемые шаги. Стратегии проще тестировать и комбинировать; шаблонный метод централизует стабильный процесс, но теснее связывает подкласс с реализацией родителя. Ради одного стабильного алгоритма не нужны искусственные интерфейсы.

interface ScorePolicy {

}

final class OscarPolicy implements ScorePolicy {
    public int score(int oscars) {
        return oscars * 10;
    }
}

final class RecommendationService {
    private final ScorePolicy policy;

    RecommendationService(ScorePolicy policy) {
        this.policy = policy;
    }

    int recommend(int oscars) {
        return policy.score(oscars);

5. IoC、DI、DIP：三个相关但不同的概念5. IoC, DI, DIP: связанные, но разные понятия

  • IoC（控制反转）：程序的某些控制权交给框架或容器，例如容器决定何时调用请求处理方法、何时创建对象。它是宽泛原则。
    IoC — инверсия управления: часть управления передаётся фреймворку или контейнеру, например выбор момента вызова обработчика или создания объекта. Это общий принцип.
  • DI（依赖注入）：对象所需的协作者从外部传入，而不是由对象自行查找或固定 new。构造器、字段、初始化方法都可以是注入点。DI 是实现 IoC 的一种具体方式。
    DI — внедрение зависимостей: нужные объекты передаются извне, а не находятся или жёстко создаются самим получателем. Точками внедрения бывают конструктор, поле и метод инициализации. DI — конкретный способ реализации IoC.
  • DIP（依赖倒置原则）：高层业务与低层细节依赖合适的抽象，让细节适应业务边界。DI 可以帮助实现 DIP，但仅用 @Inject 注入一个具体数据库类，并不会自动形成良好的依赖倒置。
    DIP — принцип инверсии зависимостей: бизнес высокого уровня и низкоуровневые детали зависят от подходящих абстракций, а детали подстраиваются под бизнес-границы. DI помогает реализовать DIP, но @Inject для конкретного класса базы данных сам по себе не создаёт качественную архитектуру.
  • Service Locator 由使用者主动向注册表请求依赖；DI 由外部提供依赖。前者使查找入口成为显式依赖，却可能隐藏真正需要的服务；后者让构造器参数表达依赖，但容器配置和解析规则也需要理解。
    При Service Locator клиент сам запрашивает зависимость у реестра; при DI зависимость передаётся извне. Первый делает точку поиска явной зависимостью, но может скрывать реальные потребности объекта. Второй выражает их параметрами конструктора, однако требует понимания конфигурации и правил разрешения контейнера.

9. 选择模式时的答辩逻辑9. Как обосновывать выбор шаблона на защите

  • 先说变化点：例如排序规则变化、数据库访问需要集中、多个入口需要复用同一个业务用例。然后说不使用该方案会产生什么具体重复或耦合。
    Сначала назовите изменяемую часть: правила сортировки, необходимость централизовать доступ к БД или повторно использовать сценарий через разные входы. Затем объясните конкретное дублирование или связанность без решения.
  • 再说选择与代价：Strategy 便于增加算法，但增加接口与实现；Repository 统一访问语义，但不能自动优化查询；微服务独立发布，但增加分布式系统成本。
    Затем объясните выбор и цену: Strategy упрощает добавление алгоритмов, но добавляет интерфейсы; Repository унифицирует доступ, но не оптимизирует запросы автоматически; микросервисы дают независимые релизы, но повышают издержки распределённой системы.
  • 最后落到证据：指出一个真实类、一次调用、一条依赖方向或一个测试替换点。避免把“使用 Spring/Jakarta EE”直接等同于某个架构，也避免为了展示模式而引入没有变化需求的抽象。
    В завершение покажите доказательство: реальный класс, вызов, направление зависимости или точку подмены в тесте. Не приравнивайте использование Spring/Jakarta EE к определённой архитектуре и не вводите абстракции без потребности в изменениях.

设计模式是对类与对象之间常见设计问题的可复用方案，例如 Strategy 用组合来替换算法，Facade 简化子系统入口。架构模式影响更大的结构，例如分层架构规定表示、业务和数据访问职责，微服务规定可独立部署的业务服务。两者是不同粒度的设计知识，可以同时使用。比如一个分层的 Movie 应用可以在业务层用 Strategy，在数据层用 Repository。选择时需要说明问题、收益和代价，不能认为模式越多越好，也不能把 CDI 或 Spring 这样的框架直接等同于一种架构。
Шаблон проектирования — повторно используемое решение типичной задачи взаимодействия классов и объектов: например, Strategy заменяет алгоритмы через композицию, а Facade упрощает вход в подсистему. Архитектурный шаблон определяет более крупную структуру: слоистая архитектура разделяет представление, бизнес-логику и доступ к данным, а микросервисы выделяют независимо развёртываемые бизнес-сервисы. Это знания разного масштаба, которые можно сочетать. Например, слоистое приложение Movie может использовать Strategy в бизнес-слое и Repository в слое данных. Выбор нужно обосновывать проблемой, преимуществами и издержками. Большее число шаблонов не означает лучшее решение, а CDI или Spring сами по себе не задают единственную архитектуру.

Jakarta EE 平台与组件类型 Платформа Jakarta EE и виды компонентов

Jakarta EE 是企业 Java 的规范平台，应用服务器提供规范的实现与运行环境。理解“规范—API—实现—容器—应用组件”五个层次，就能避免把 Jakarta EE、Payara、CDI 和 EclipseLink 混为一谈。
Jakarta EE — платформа спецификаций enterprise Java; сервер приложений предоставляет их реализацию и среду выполнения. Разделяйте спецификацию, API, реализацию, контейнер и компонент приложения — тогда Jakarta EE, Payara, CDI и EclipseLink не будут смешиваться.

1. 平台是什么：一组相互配合的标准契约1. Что такое платформа: согласованный набор стандартных контрактов

Jakarta EE 在 Java SE 的语言、JVM、集合、并发和 JDBC 等能力之上，标准化企业应用常用功能：HTTP 与 REST、依赖注入、持久化、事务、校验、安全和消息。平台规范规定不同技术如何一起工作；单项规范规定某一技术的 API、行为和实现要求。它不是单独一个服务器程序。
Jakarta EE поверх языка, JVM, коллекций, многопоточности и JDBC из Java SE стандартизует HTTP/REST, внедрение зависимостей, персистентность, транзакции, валидацию, безопасность и сообщения. Платформенная спецификация задаёт совместную работу технологий, а отдельная — API, поведение и требования конкретной технологии. Это не одна серверная программа.
API 给开发者类型和注解；实现执行这些契约；TCK 用于检查实现是否符合相应规范。符合某一版本和 Profile 的产品提供对应的标准功能，但对供应商扩展、运维配置及性能不能假定完全相同。仅能编译并不证明部署环境具有这些服务。
API предоставляет разработчику типы и аннотации; реализация исполняет контракт; TCK проверяет соответствие реализации спецификации. Продукт определённой версии и профиля предоставляет соответствующие стандартные возможности, но расширения поставщика, настройки эксплуатации и производительность могут различаться. Успешная компиляция не доказывает наличие сервисов в среде развёртывания.

2. Java EE → Jakarta EE：版本与命名空间2. Java EE → Jakarta EE: версии и пространства имён

Jakarta EE 继承了 Java EE 的企业 Java 规范体系。Jakarta EE 8 仍使用 javax.* 企业 API 包；Jakarta EE 9 把相关企业规范 API 迁移到 jakarta.*。这造成相关代码的源码与二进制兼容性断点，迁移还涉及依赖、实现与部署描述文件，不能只全局替换一条 import。
Jakarta EE продолжает систему спецификаций enterprise Java от Java EE. Jakarta EE 8 ещё использует javax.* для enterprise API; Jakarta EE 9 переносит соответствующие API в jakarta.*. Это разрыв совместимости исходного и двоичного кода. Миграция затрагивает зависимости, реализации и дескрипторы, а не только одну замену import.
不能把所有 javax 都替换成 jakarta。属于 Java SE 的 javax.sql.DataSource、javax.naming 等仍保留原命名空间。JDBC 的 Connection 属于 java.sql。应根据 API 归属判断，而不是根据前缀猜测。
Нельзя заменять все javax на jakarta. Входящие в Java SE javax.sql.DataSource, javax.naming и другие сохраняют свои имена. JDBC Connection находится в java.sql. Решение определяется принадлежностью API, а не только префиксом.
本实验 pom.xml 使用 Java 17 编译目标、jakarta.jakartaee-api 10.0.0 与 EclipseLink 4.0.5，因此本手册的实验解释以 Jakarta EE 10 为基线。EE 10 的平台最低要求是 Java SE 11；“我的项目用 Java 17”不等于“EE 10 只支持 Java 17”。
В pom.xml лабораторной указаны целевая Java 17, jakarta.jakartaee-api 10.0.0 и EclipseLink 4.0.5, поэтому объяснение проекта опирается на Jakarta EE 10. Минимум платформы EE 10 — Java SE 11. Использование Java 17 в проекте не означает, что EE 10 поддерживает только Java 17.

7. 容器如何参与执行7. Как контейнер участвует в выполнении

容器并非只是存放对象的 Map。它根据部署元数据识别组件，构建依赖图，在规定的时机创建实例、注入依赖、执行生命周期回调，并通过代理或调用链加入拦截器、事务及安全检查。具体服务取决于组件类型、Profile 和声明方式。
Контейнер — не просто Map с объектами. По метаданным развёртывания он распознаёт компоненты, строит граф зависимостей, создаёт экземпляры, внедряет зависимости и вызывает lifecycle callbacks. Через прокси или цепочки вызова он добавляет перехватчики, транзакции и проверки безопасности. Набор сервисов зависит от типа компонента, профиля и деклараций.
自己 new 一个服务得到的是普通 Java 对象，不会因为其类上有注解就自动成为当前容器管理的实例。类似地，通过对象内部的普通 this 调用，不能假定总能经过外部代理。解释声明式服务时，应说清是谁创建实例、调用是否经过容器、事务边界在哪里。
Созданный вручную через new сервис — обычный Java-объект; аннотации класса сами по себе не делают именно этот экземпляр управляемым текущим контейнером. Обычный внутренний вызов через this также не следует автоматически считать проходящим через внешний прокси. Для декларативных сервисов объясняйте, кто создал объект, проходит ли вызов через контейнер и где граница транзакции.

9. 用最小示例解释组件协作9. Объяснение взаимодействия на минимальном примере

当前实验的真实路径与此类似：MovieResource 是 @RequestScoped 的 REST 资源；MovieService 和 Database 是 @ApplicationScoped 的 CDI Bean；Movie 是持久化实体。Database 在 @PostConstruct 中创建工厂、在 @PreDestroy 中关闭工厂，并在 write() 中显式管理 RESOURCE_LOCAL 事务。不要在答辩中把这份源码描述成 EJB 的自动容器事务。
Реальная лабораторная устроена сходным образом: MovieResource — REST-ресурс @RequestScoped; MovieService и Database — CDI beans @ApplicationScoped; Movie — сущность хранения. Database создаёт фабрику в @PostConstruct, закрывает её в @PreDestroy и явно управляет RESOURCE_LOCAL-транзакцией в write(). Не описывайте этот код как автоматические контейнерные транзакции EJB.

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.context.RequestScoped;
import jakarta.inject.Inject;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;

@ApplicationScoped
class GreetingService {
    public String message() {
        return "Movie service is ready";
    }
}

@Path("/status")
@RequestScoped
public class StatusResource {
    @Inject
    GreetingService service;

    @GET
    public String status() {
        return service.message();
    }
}
教学示例：REST 把 GET 请求匹配到 status()；CDI 提供 service 并管理作用域。部署时还需要 REST 应用配置或运行时约定。这里没有数据库操作，也没有声明事务，不能把 @Inject 解释成自动开启事务。
Учебный пример: REST сопоставляет GET-запрос с status(); CDI предоставляет service и управляет областями. При развёртывании нужна конфигурация REST-приложения или соглашение среды выполнения. Здесь нет работы с БД и декларации транзакции; @Inject не означает автоматическое начало транзакции.

10. 优点、成本与适用性10. Преимущества, стоимость и применимость

  • 优点：统一 API 与集成语义减少基础设施代码；标准与兼容性要求帮助降低对单一供应商的依赖；容器集中处理对象生命周期和企业服务。
    Плюсы: единые API и правила интеграции уменьшают инфраструктурный код; стандарты и совместимость снижают зависимость от поставщика; контейнер централизует жизненный цикл и enterprise-сервисы.
  • 成本：需要理解多个规范、版本组合、部署与容器行为；供应商扩展可能降低可移植性；错误的作用域或事务配置可能在运行时才显现。运行时开销取决于具体实现和启用功能，不能简单说所有 Jakarta EE 都“重量级”。
    Издержки: нужно понимать несколько спецификаций, совместимость версий, развёртывание и контейнерное поведение; расширения поставщика снижают переносимость; ошибки областей и транзакций могут проявиться во время выполнения. Расходы зависят от реализации и используемых функций: нельзя объявлять весь Jakarta EE «тяжеловесным».
  • 常见误区：Jakarta EE 不是数据库，不是 EclipseLink 的别名，也不是只能使用 EJB 的旧式开发方式。它可以承载分层单体，也可以用于较小服务；架构选择与技术规范是不同维度。
    Частые ошибки: Jakarta EE — не база данных, не другое имя EclipseLink и не только историческая разработка через EJB. На нём можно строить слоистый монолит и небольшие сервисы; архитектурное решение и технологическая спецификация относятся к разным измерениям.

2. CDI 的核心模型：定义、实例、上下文与引用2. Модель CDI: определение, экземпляр, контекст и ссылка

Bean 是容器知道的组件定义；contextual instance 是该定义在某个上下文中的实例；context 决定它的存活和共享边界；injection point 声明需要的类型与限定符。注入得到的引用可能是客户端代理，而不是实例的直接地址。
Bean — известное контейнеру определение компонента; contextual instance — его экземпляр в контексте; context задаёт границы жизни и совместного использования; injection point объявляет требуемый тип и qualifiers. Внедрённая ссылка может быть клиентским прокси, а не прямой ссылкой на экземпляр.
容器在部署时发现 Bean，检查定义和依赖，解析注入点。没有符合条件的 Bean 是 unsatisfied dependency；有多个无法消歧的候选是 ambiguous dependency。通常应在部署时暴露这些问题，而不是等待某个请求才随机选择实现。
При развёртывании контейнер обнаруживает beans, проверяет определения и зависимости и разрешает точки внедрения. Отсутствие подходящего bean — unsatisfied dependency; несколько неразрешённых кандидатов — ambiguous dependency. Обычно ошибки должны выявляться при развёртывании, а не приводить к случайному выбору при запросе.
对于普通托管 Bean 类，容器使用标注 @Inject 的构造器；没有这样的构造器时，使用无参构造器。最多只能有一个 @Inject 构造器。不能把 Spring 的“单构造器可以省略 @Autowired”规则直接迁移为 CDI 的通用规则；正常作用域还另有代理限制。
Для обычного managed bean контейнер использует конструктор с @Inject, а при его отсутствии — конструктор без параметров. Конструктор с @Inject может быть только один. Учебный фрагмент: CatalogReport с @Dependent показывает внедрение через конструктор; для развёртывания нужна разрешимая реализация MovieCatalog. В unit-тест можно вручную передать подмену. @Dependent выбран, чтобы не представлять класс только с параметризованным конструктором как переносимый normal-scoped bean.

4. 限定符解决“哪个实现”，@Named 解决名字4. Qualifier выбирает реализацию, @Named задаёт имя

CDI 主要根据 bean type 与 qualifier 做类型安全解析。例如同时有数据库版与内存版 MovieCatalog，可以定义 @DatabaseCatalog 作为 @Qualifier，并同时标在实现与注入点上。限定符可表达业务语义；不要依赖类名猜测容器会选哪个对象。
CDI выполняет типобезопасное разрешение по bean type и qualifier. Если есть реализация MovieCatalog для БД и для памяти, можно определить @DatabaseCatalog с @Qualifier и поставить его на реализацию и точку внедрения. Qualifier выражает смысл выбора; не следует угадывать выбор контейнера по имени класса.
@Named 主要为 EL 等使用字符串名字的场景提供名称。通常的注入优先使用自定义限定符。没有显式业务限定符时，常见 Bean 和注入点使用 @Default；@Any 表示 Bean 具备的通用限定符。@Named 并不是 CDI Bean 必须具有的注解。
@Named прежде всего даёт имя для EL и других сценариев со строковой идентификацией. Для обычного внедрения предпочтительнее собственный qualifier. Без явно заданного прикладного qualifier обычно действует @Default; @Any — общий qualifier beans. @Named не является обязательной аннотацией CDI bean.

6. 正常作用域为什么通常使用客户端代理6. Зачем normal scope обычно нужен клиентский прокси

例如一个应用级服务需要访问请求级 Bean。容器可注入一个稳定的客户端代理；每次调用时，代理根据当前活动上下文定位对应实例。因此长寿命 Bean 不必永久抓住某次请求的实际对象。没有活动上下文时，访问会失败，而不是凭空出现“当前请求”。
Например, application-scoped сервису нужен request-scoped bean. Контейнер может внедрить стабильный клиентский прокси, который при вызове находит экземпляр текущего активного контекста. Долгоживущий bean не удерживает навсегда объект одного запроса. Если контекст не активен, обращение завершается ошибкой: «текущий запрос» не возникает сам.
CDI 4.0 的可移植正常作用域代码必须注意可代理性，例如 final 类、某些非静态 final 方法以及缺少非 private 无参构造器的类会形成限制。某些实现可通过构建期变换放宽限制，但不能把这些扩展当作所有容器都保证的规范行为。构造器注入合法与是否能创建正常作用域代理是两个检查点。
В переносимом коде CDI 4.0 нужно учитывать проксируемость normal scope: ограничения создают final-классы, некоторые нестатические final-методы и отсутствие неприва́тного конструктора без параметров. Отдельные реализации ослабляют ограничения преобразованием при сборке, но это не универсальная гарантия спецификации. Допустимость конструктора для внедрения и возможность создать прокси normal scope — разные проверки.

7. 生命周期、生产者与销毁7. Жизненный цикл, producers и уничтожение

典型顺序是实例化 → 字段/初始化方法注入 → @PostConstruct → 业务调用 → @PreDestroy。@PostConstruct 适合依赖已经注入后的初始化；构造器中不能假定字段注入已经完成。@PreDestroy 用于相应生命周期结束前释放该 Bean 拥有的资源，不保证进程崩溃时一定执行。
Типичный порядок: создание → внедрение полей/методов → @PostConstruct → бизнес-вызовы → @PreDestroy. В @PostConstruct зависимости уже внедрены; в конструкторе нельзя рассчитывать на завершённое внедрение полей. @PreDestroy освобождает принадлежащие bean ресурсы перед штатным завершением жизни и не гарантируется при аварийном падении процесса.
@Produces 方法或字段让不直接以普通 Bean 类构造的对象参与 CDI，例如根据配置创建第三方库对象；@Disposes 方法可负责对应产品的释放。生产者定义的作用域属于所生产的 Bean，不自动等于声明生产者的那个 Bean 的作用域。不要同时让多个组件误以为自己拥有同一资源的关闭责任。
Метод или поле @Produces позволяет включить в CDI объект, который не создаётся как обычный managed bean, например объект сторонней библиотеки из конфигурации. @Disposes может освобождать продукт. Scope producer относится к произведённому bean и не обязан совпадать со scope содержащего producer bean. Нельзя допускать несколько владельцев, одновременно считающих себя ответственными за закрытие одного ресурса.
实验 Database 使用 @PostConstruct 初始化 EntityManagerFactory，用 @PreDestroy 关闭它；每次 read()/write() 都创建并关闭自己的 EntityManager。这里共享的是工厂与服务，而不是把一个 EntityManager 放进应用作用域反复使用。
В лабораторной Database инициализирует EntityManagerFactory через @PostConstruct и закрывает через @PreDestroy; каждый read()/write() создаёт и закрывает свой EntityManager. Совместно используются фабрика и сервис, а не один EntityManager на всё приложение.

8. 拦截器、装饰器和事件：CDI 不只是注入8. Перехватчики, декораторы и события: CDI не сводится к внедрению

  • 拦截器通过绑定把日志、审计或事务等横切逻辑应用到调用上。jakarta.transaction.Transactional 的事务能力来自 Jakarta Transactions 与相应拦截器集成，而不是任意 @Inject 调用都会开启事务。
    Перехватчики по bindings добавляют сквозную логику: журналирование, аудит, транзакции. Возможности jakarta.transaction.Transactional приходят из Jakarta Transactions и интеграции перехватчиков; не любой вызов внедрённого объекта начинает транзакцию.
  • CDI Decorator 围绕业务接口增加有业务语义的行为，使用 delegate 参与调用链，属于 CDI Full。它与常见的“日志拦截器”关注点不同，但它们都体现组合与间接调用思想。
    CDI Decorator добавляет поведение с бизнес-смыслом вокруг интерфейса и участвует в цепочке через delegate; относится к CDI Full. Его назначение отличается от типичного логирующего interceptor, хотя оба используют композицию и косвенный вызов.
  • Event<T>.fire() 与 @Observes 支持进程内的类型化发布/观察；还可使用异步事件。发送者与接收者无需直接依赖彼此的实现，但仍共同依赖事件契约。CDI 事件不是持久化消息队列，不自动提供跨进程传递或崩溃后重放保证。
    Event<T>.fire() и @Observes поддерживают типизированную публикацию и наблюдение внутри процесса; доступны и асинхронные события. Отправитель и получатель не зависят непосредственно от реализаций друг друга, но разделяют контракт события. События CDI — не долговечная очередь: они автоматически не дают межпроцессную доставку или воспроизведение после падения.

9. 发现机制与 CDI Lite / Full9. Обнаружение beans и CDI Lite / Full

CDI 4.0 将核心分为 Lite 和 Full。Lite 包含类型安全注入、依赖解析、基本上下文、生产者、事件和拦截器绑定等核心能力，并提供适合构建期处理的扩展模型。Full 在 Lite 之上加入完整能力，包括 Decorator、portable extensions，以及 session/conversation 等。不能把 Lite 理解成只支持 @Inject，也不能假定它提供 Full 的所有功能。
CDI 4.0 разделяет ядро на Lite и Full. Lite включает типобезопасное внедрение, разрешение зависимостей, базовые контексты, producers, события и interceptor bindings, а также модель расширений для обработки при сборке. Full добавляет полные возможности, включая Decorator, portable extensions и session/conversation contexts. Lite — не только @Inject, но и не весь Full.
在 annotated 发现模式下，需要 Bean defining annotation，例如正常作用域注解、@Dependent 或合适 stereotype。@Inject 标在一个字段上并不会自动使其声明类被发现；@Named 单独使用也不等价于作用域注解。本实验 beans.xml 明确使用 version=4.0、bean-discovery-mode=annotated，而 MovieResource、MovieService、Database 都有作用域注解。
При discovery=annotated нужна bean-defining annotation, например normal scope, @Dependent или подходящий stereotype. @Inject на поле не делает автоматически обнаруживаемым содержащий класс; одна @Named также не равна scope-аннотации. В лабораторной beans.xml явно задаёт version=4.0 и bean-discovery-mode=annotated, а MovieResource, MovieService и Database имеют scope-аннотации.

Смысл beans.xml лабораторной. В WAR он обычно находится в WEB-INF/beans.xml, в библиотеке — META-INF/beans.xml. Обязательность файла зависит от способа обнаружения и среды; неверно требовать пустой beans.xml для любого CDI-проекта.

ORM：Hibernate 与 EclipseLink ORM: Hibernate и EclipseLink

ORM 是对象与关系数据之间的映射思想；Hibernate ORM 和 EclipseLink 是执行这种映射的实现。它们都能实现 Jakarta Persistence，但扩展 API 和内部机制不同。
ORM — подход к отображению объектов на реляционные данные; Hibernate ORM и EclipseLink — реализации этого подхода. Обе библиотеки могут реализовывать Jakarta Persistence, но имеют разные расширения API и внутренние механизмы.

1. ORM 解决什么问题1. Какую проблему решает ORM

Java 使用对象、引用、集合和继承；关系数据库使用表、行、列、外键和连接。两种模型存在阻抗不匹配。例如 Movie 引用 Person，而数据库通常通过 movie.director_id 引用 person.id。ORM 根据映射元数据在两种表示之间转换。它不仅把查询结果装入对象，也处理对象标识、关系、继承策略、类型转换、加载策略和变化写回。
Java использует объекты, ссылки, коллекции и наследование; реляционная БД — таблицы, строки, столбцы, внешние ключи и соединения. Между моделями существует объектно-реляционное несоответствие. Например, Movie ссылается на Person, а БД обычно связывает movie.director_id с person.id. ORM преобразует представления на основании метаданных отображения: не только собирает объекты из результатов, но и управляет идентичностью, связями, наследованием, преобразованием типов, загрузкой и записью изменений.
Java 对象的内存身份用引用表示，持久化身份通常由实体类型和主键共同决定。两个不同对象仍可能代表同一数据库记录；同一持久化上下文则要求相同实体身份对应唯一托管实例。这是 ORM 比简单 Bean 复制工具更复杂的原因之一。
Идентичность Java-объекта в памяти задаётся ссылкой, а персистентная идентичность обычно определяется типом сущности и ключом. Разные объекты могут представлять одну запись; в одном контексте персистентности каждой идентичности должен соответствовать единственный управляемый экземпляр. Поэтому ORM сложнее простого средства копирования Bean-полей.

2. 从业务代码到数据库的完整链路2. Полный путь от бизнес-кода до БД

典型链路：Service → EntityManager（标准 API）→ Hibernate/EclipseLink（提供者）→ JDBC 驱动 → 数据库。提供者解释映射和 JPQL、生成 SQL、绑定参数并构造对象。数据库实际执行 SQL、检查约束、使用索引并提供事务隔离。ORM 没有消除 SQL，也没有替代 JDBC。
Типичная цепочка: Service → EntityManager (стандартный API) → Hibernate/EclipseLink (провайдер) → JDBC-драйвер → БД. Провайдер интерпретирует отображения и JPQL, формирует SQL, связывает параметры и создаёт объекты. БД выполняет SQL, проверяет ограничения, использует индексы и обеспечивает изоляцию транзакций. ORM не устраняет SQL и не заменяет JDBC.
对象属性访问可能引发查询，persist 也不一定立刻执行 INSERT。分析性能要查看实际 SQL、执行计划、往返次数和事务边界，而不是只数 Java 方法调用。ORM 的收益是减少重复工作，代价是必须理解它隐藏的执行过程。
Обращение к свойству может вызвать запрос, а persist не обязательно сразу выполняет INSERT. Производительность анализируют по фактическому SQL, планам, сетевым обращениям и границам транзакций, а не по числу Java-вызовов. ORM сокращает повторяющуюся работу, но требует понимания скрытого процесса выполнения.
层次要分清：ORM 是思想，Jakarta Persistence 是规范，Hibernate/EclipseLink 是实现，JDBC 是关系数据库访问 API，PostgreSQL 是数据库。它们不是同一层的替代品。
Различайте уровни: ORM — подход, Jakarta Persistence — спецификация, Hibernate/EclipseLink — реализации, JDBC — API доступа к реляционной БД, PostgreSQL — сама БД. Это не альтернативы одного уровня.

unwrap 是标准扩展入口，但返回值类型属于提供者。可以使用扩展，不过最好将依赖隔离在持久化层。若整个业务层直接使用 Session，改用 EclipseLink 时就需要重写相关逻辑。
unwrap — стандартная точка доступа к расширениям, но возвращаемый тип принадлежит провайдеру. Расширения допустимы, однако зависимость лучше изолировать в слое персистентности. Если весь бизнес-слой работает с Session напрямую, переход на EclipseLink потребует переписать соответствующую логику.

public final class HibernateAccess {
    public static Session nativeSession(EntityManager em) {

7. 一级与二级缓存7. Кэш первого и второго уровней

一级缓存通常指单个持久化上下文中的实体身份与状态管理，不只是查询加速器。同一上下文内重复 find 同一实体时可返回已有托管实例；EntityManager 一般不应被并发线程共享。
Кэш первого уровня обычно означает управление идентичностью и состоянием внутри одного контекста, а не только ускорение запросов. Повторный find той же сущности может вернуть уже управляемый экземпляр; EntityManager обычно нельзя разделять между параллельными потоками.
二级缓存由多个上下文共享，通常与 EntityManagerFactory 生命周期相关。它可能减少读取，但增加内存占用和失效管理难度。实体二级缓存与查询结果缓存不是同一机制；启用范围与默认行为取决于提供者配置。
Кэш второго уровня разделяется между контекстами и обычно связан с жизненным циклом EntityManagerFactory. Он может сократить чтение, но увеличивает память и сложность инвалидирования. Кэш сущностей и кэш результатов запросов — разные механизмы; включение и значения по умолчанию зависят от провайдера.
本实验设置 eclipselink.cache.shared.default=false，关闭默认共享缓存。这不会取消当前 EntityManager 的上下文，也不意味着 PostgreSQL 或操作系统没有自己的缓存。
В лабораторной eclipselink.cache.shared.default=false отключает общий кэш по умолчанию. Это не устраняет контекст текущего EntityManager и не отключает собственные кэши PostgreSQL или ОС.

8. LAZY、EAGER、N+1 与 weaving8. LAZY, EAGER, N+1 и weaving

N+1 场景：先查 N 部电影，再逐个访问导演，引发 N 次额外查询。可按用例采用 fetch join、实体图、批量读取或 DTO 投影。把所有关系都改 EAGER 可能扩大对象图、增加查询和内存，并不是通用解法。
Пример N+1: загружаются N фильмов, затем обращение к режиссёру каждого вызывает ещё N запросов. Под сценарий применяют fetch join, entity graph, пакетную загрузку или DTO-проекции. Замена всех связей на EAGER может увеличить граф, число запросов и память, поэтому не является универсальным решением.
Persistence 3.1 中 EAGER 是必须提前加载的要求，LAZY 是允许提供者提前加载的提示。EAGER 不保证一条 JOIN SQL；to-one 默认 EAGER，to-many 默认 LAZY。离开有效上下文后访问尚未加载的关系也不是可靠的通用做法。
В Persistence 3.1 EAGER требует ранней загрузки, а LAZY является подсказкой, допускающей раннюю загрузку провайдером. EAGER не гарантирует один SQL с JOIN; to-one по умолчанию EAGER, to-many — LAZY. Обращение к незагруженной связи вне действующего контекста также не является надёжным универсальным приёмом.
实验 weaving=false 影响 EclipseLink 依赖织入的能力，尤其是部分 to-one 延迟加载和增强式变化跟踪。不能断言所有 LAZY 都失效，也不能仅凭注解断言没有额外 SQL；必须查看实际日志。
weaving=false в лабораторной влияет на возможности EclipseLink, зависящие от weaving, особенно часть ленивой загрузки to-one и усиленное отслеживание изменений. Нельзя заключать, что вся LAZY-загрузка отключена, или по одной аннотации обещать отсутствие дополнительных SQL: нужны реальные логи.

9. 如何论证选择和迁移9. Как обосновать выбор и миграцию

ORM 适合围绕领域对象表达常见业务，降低 CRUD 和映射重复；复杂报表、大批量更新与数据库特性仍可配合原生 SQL。应按可读性、团队能力、真实负载和维护成本选择，而不是追求“纯 ORM”。
ORM подходит для выражения обычной бизнес-логики через доменные объекты и уменьшает повторение CRUD и отображений. Для отчётов, массовых обновлений и особенностей БД можно использовать native SQL. Выбор определяется читаемостью, навыками команды, нагрузкой и сопровождением, а не стремлением к «чистой ORM».
迁移提供者时先匹配 Persistence 版本，再调整依赖、提供者配置、增强或 weaving、命名策略、主键生成、查询提示、缓存和锁。标准注解能减少改动，但仍要检查 SQL、功能正确性和性能。
При миграции сначала согласуют версию Persistence, затем меняют зависимости, провайдера, enhancement/weaving, naming strategy, генерацию ключей, query hints, кэш и блокировки. Стандартные аннотации уменьшают изменения, но SQL, корректность и производительность всё равно проверяют.

Jakarta Persistence：实体、上下文与事务 Jakarta Persistence: сущности, контекст и транзакции

Jakarta Persistence 标准化 Java 关系持久化和 ORM 的映射与 API。关键不是背注解，而是解释“哪个上下文管理哪个实体，以及什么时候将变化写入并提交”。
Jakarta Persistence стандартизует отображения и API реляционной персистентности и ORM в Java. Главное — объяснить, какой контекст управляет сущностью и когда изменения записываются и фиксируются.

1. 规范、提供者与本实验版本1. Спецификация, провайдер и версии лабораторной

规范定义实体要求、映射、生命周期、EntityManager、JPQL、Criteria、锁及事务集成。提供者把标准操作转成数据库操作。只添加 jakarta.persistence-api 时只有类型和注解，没有完整 ORM 运行时。Java SE 可自行启动提供者，Jakarta EE 也可由容器完成集成。
Спецификация задаёт требования к сущностям, отображения, жизненный цикл, EntityManager, JPQL, Criteria, блокировки и интеграцию транзакций. Провайдер преобразует операции в действия БД. Зависимость jakarta.persistence-api даёт типы и аннотации, но не полноценный runtime ORM. В Java SE провайдер запускают самостоятельно, а в Jakarta EE интеграцией может заниматься контейнер.
本实验 Jakarta EE 10 对应 Persistence 3.1，EclipseLink 4.0 系列实现该规范。persistence.xml 使用 3.0 XML 格式，不表示运行时只能提供 3.0 API。描述符格式版本、规范 API 版本和提供者版本必须分别辨认。

2. 教学实体：映射与乐观锁2. Учебная сущность: отображение и optimistic locking

@Entity 声明实体，@Id 定义持久化标识，@GeneratedValue 请求主键生成，@Version 是乐观锁版本。Persistence 3.1 实体需要 public 或 protected 无参构造器；实体类和持久化方法不能是 final。关系字段可用 @ManyToOne 等映射，枚举、日期与自定义类型要选择合适的转换方式。
@Entity объявляет сущность, @Id задаёт идентичность, @GeneratedValue запрашивает генерацию ключа, @Version хранит версию для optimistic locking. В Persistence 3.1 нужен public или protected конструктор без параметров; класс сущности и персистентные методы не должны быть final. Связи отображают через @ManyToOne и другие аннотации; для enum, дат и пользовательских типов выбирают подходящее преобразование.
@Column(nullable=false) 是映射信息，不等同于 Java 入参校验；应用可以使用 Jakarta Validation，已有数据库表还应有真实的 NOT NULL、UNIQUE 和 CHECK 等约束。@Entity 也不代表对象由 CDI 管理；实体生命周期由持久化上下文管理。
@Column(nullable=false) — метаданные отображения, а не эквивалент проверки Java-параметров. Приложение может использовать Jakarta Validation, а существующая таблица БД должна иметь реальные NOT NULL, UNIQUE, CHECK и другие ограничения. @Entity также не означает управление объектом через CDI: жизненным циклом сущности управляет контекст персистентности.

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.Version;

@Entity
@Table(name = "movie")
public class Movie {
    @Id @GeneratedValue
    private Long id;

    @Column(nullable = false)
    private String name;

    @Version
    private long version;

    protected Movie() {}
    public Movie(String name) { this.name = name; }
    public void rename(String name) { this.name = name; }

Отдельный учебный Movie.java, а не полная копия сущности лабораторной. @Id находится на поле, поэтому используется доступ к полям; setter для каждого поля ради персистентности не требуется.

5. 上下文、dirty checking、flush 与 commit5. Контекст, dirty checking, flush и commit

持久化上下文维护实体身份和状态。对托管实体改属性时，一般不需要显式 update；提供者在有效事务同步时处理变化。dirty checking 是常用实现术语，规范要求的是托管状态同步的语义。若对象已游离或根本没有写事务，就不能套用“改 setter 自动保存”的简化说法。
Контекст поддерживает идентичность и состояние сущностей. После изменения управляемой сущности обычно не нужен явный update: провайдер обрабатывает изменения при синхронизации действующей транзакции. Dirty checking — распространённый термин реализации; спецификация задаёт семантику синхронизации. Для отсоединённого объекта или без транзакции записи правило «setter автоматически сохраняет» неприменимо.
flush 将上下文变化同步到数据库，可能执行 INSERT/UPDATE/DELETE，但没有结束事务，之后仍可能 rollback。commit 才固定事务结果，并会处理未同步的变化。flush 成功不等于业务已提交，也不代表其他事务在任何隔离级别下都立即可见。
flush синхронизирует изменения контекста с БД и может выполнить INSERT/UPDATE/DELETE, но не завершает транзакцию: после него возможен rollback. commit фиксирует результат и обрабатывает несинхронизированные изменения. Успешный flush не означает фиксацию бизнеса или немедленную видимость для других транзакций при любом уровне изоляции.
默认 AUTO 模式下，查询前可能进行相关同步。SQL 不一定等到 commit：查询、显式 flush、某些主键生成策略都可能提前访问数据库。失败也可能直到 flush 或 commit 才暴露，因此不能只给 persist 一行包异常处理就认为覆盖了全部写入错误。
В режиме AUTO перед запросом может происходить необходимая синхронизация. SQL не обязательно ждёт commit: запрос, явный flush или некоторые стратегии ключей обращаются к БД раньше. Ошибка может проявиться лишь при flush или commit, поэтому обработка исключения только вокруг строки persist не покрывает все ошибки записи.

6. 本地事务与 JTA：对应不同管理方式6. Локальные транзакции и JTA: разные модели управления

RESOURCE_LOCAL 通常控制一个数据库资源的事务，使用 EntityTransaction。JTA 通过事务管理器协调参与资源，在 EE 中常由 @Transactional 或 EJB 容器划定边界；是否采用 XA、多资源的具体保证取决于资源和配置。不能在 JTA 的 EntityManager 上机械使用 getTransaction。
RESOURCE_LOCAL обычно управляет транзакцией одного ресурса БД через EntityTransaction. JTA координирует ресурсы через transaction manager; в EE границы часто задаются @Transactional или EJB-контейнером. XA и конкретные гарантии нескольких ресурсов зависят от конфигурации. Нельзя механически применять getTransaction к JTA EntityManager.
容器管理的 EntityManager 由容器控制生命周期，应用通常不自行 close。实验部署在应用服务器上，却明确使用 RESOURCE_LOCAL，因此解释本实验时要看实际配置与代码，不能从服务器这一事实推断 JTA。
Жизненным циклом container-managed EntityManager управляет контейнер; приложение обычно не вызывает close. Лабораторная развёрнута на сервере приложений, но явно использует RESOURCE_LOCAL: объяснение определяется кодом и конфигурацией, а не самим наличием сервера.
JAVA
import jakarta.persistence.EntityManager;
import jakarta.persistence.EntityManagerFactory;
import jakarta.persistence.EntityTransaction;

public final class MovieCommands {
    public static void rename(EntityManagerFactory emf,
                              Long id, String newName) {
        EntityManager em = emf.createEntityManager();
        EntityTransaction tx = em.getTransaction();
        try {
            tx.begin();
            Movie movie = em.find(Movie.class, id);
            if (movie == null) {
                throw new IllegalArgumentException("Movie not found");
            }
            movie.rename(newName);
            em.flush();
            tx.commit();
        } catch (RuntimeException ex) {
            if (tx.isActive()) tx.rollback();
            throw ex;
        } finally {
            em.close();
        }
    }
}
教学文件 MovieCommands.java，与前面 Movie.java 配套，假定 emf 对应 RESOURCE_LOCAL。显式 flush 用于展示同步点，通常可以由 commit 完成同步；工厂由调用者复用和关闭。
Учебный MovieCommands.java используется с Movie.java выше; emf предполагается для RESOURCE_LOCAL. Явный flush показывает синхронизацию, которую обычно может выполнить commit; фабрику переиспользует и закрывает вызывающая сторона.

7. JPQL、Criteria 与原生 SQL7. JPQL, Criteria и native SQL

用户输入应绑定为参数，不要拼接查询字符串。参数化提高安全性，但不能修复不合理的查询结构。JPQL 批量 UPDATE/DELETE 直接影响数据库，不逐个同步已托管实体；之后应按需要 clear 或 refresh，避免使用陈旧对象。
Пользовательские значения связывают параметрами, а не конкатенацией. Параметризация улучшает безопасность, но не исправляет неудачный запрос. Массовые UPDATE/DELETE JPQL воздействуют на БД и не синхронизируют каждую управляемую сущность; затем при необходимости выполняют clear или refresh, избегая устаревших объектов.
分页必须有确定性排序，例如 name 后再按唯一 id 排序。集合 fetch join 与分页同时使用时，数据库行和实体数量不一定一一对应，应特别检查提供者行为与 SQL，避免把表面的一页查询变成大量内存处理。
Пагинации нужен детерминированный порядок, например name и затем уникальный id. При сочетании collection fetch join и пагинации строки БД и сущности не обязательно соответствуют один к одному: нужно проверить поведение провайдера и SQL, чтобы одна видимая страница не требовала большой обработки в памяти.

8. 关系拥有方、cascade 与 orphanRemoval8. Владелец связи, cascade и orphanRemoval

双向关系中 owning side 决定关系如何写回；inverse side 用 mappedBy 指向拥有方的 Java 属性名，而不是列名。例如 Person.movies 上的 mappedBy="director" 指向 Movie.director，常见外键位于 Movie 一侧。业务辅助方法应维护两侧引用一致；只修改 inverse 集合不等于可靠修改数据库外键。
В двунаправленной связи owning side определяет запись связи; inverse side указывает через mappedBy Java-атрибут владельца, а не столбец. Например, mappedBy="director" у Person.movies ссылается на Movie.director; внешний ключ обычно на стороне Movie. Вспомогательные методы должны согласованно менять обе ссылки: изменение только inverse-коллекции не гарантирует изменение внешнего ключа.
cascade 把 persist、merge、remove 等对象操作传播到关联对象，不是加载策略，也不等于数据库 ON DELETE CASCADE。默认不自动级联所有操作。对被多部电影共享的导演配置 REMOVE，可能误删仍被使用的 Person。
cascade распространяет persist, merge, remove и другие объектные операции; это не стратегия загрузки и не ON DELETE CASCADE в БД. По умолчанию все операции не каскадируются. REMOVE для режиссёра, общего у нескольких фильмов, может удалить ещё используемый Person.
orphanRemoval 适合父对象私有拥有的子实体：从支持该功能的关系中移除子实体会安排删除。它与删除父实体时传播 remove 的触发时机不同；并不是任意关联对象都属于可删除的孤儿。外键约束仍应由数据库保证。
orphanRemoval подходит для дочерних сущностей, исключительно принадлежащих родителю: исключение из поддерживающей это связи планирует удаление. Это другой момент, чем каскадный remove при удалении родителя. Не любой связанный объект является удаляемой «сиротой»; ссылочную целостность всё равно должна гарантировать БД.

9. 乐观锁、悲观锁与业务一致性9. Optimistic locking, pessimistic locking и согласованность

@Version 检查更新版本：两个事务读到同一版本时，先提交者可成功，后者在检查失败后得到乐观锁异常，应回滚并提示冲突或重新执行业务。它适合冲突较少的场景，不依赖长期持有行锁，也不自动保护所有跨行业务条件。
@Version проверяет версию обновления: если две транзакции прочитали одну версию, первая может завершиться, а вторая при неудачной проверке получит optimistic lock exception. Нужны rollback и сообщение о конфликте либо повтор бизнеса. Подход подходит при редких конфликтах, не требует долгого удержания row lock и автоматически не защищает все межстрочные условия.
悲观锁先通过数据库锁协调并发，适合必须锁定资源后操作的场景，代价是等待、死锁风险和吞吐下降。两种锁都不替代 UNIQUE 约束；对于先查不存在再插入的竞态，数据库必须最终保证唯一性。
Pessimistic locking координирует конкуренцию блокировками БД и подходит, когда ресурс нужно предварительно заблокировать. Цена — ожидание, deadlock и снижение пропускной способности. Ни один вид не заменяет UNIQUE: в гонке «проверить отсутствие, затем вставить» окончательную уникальность гарантирует БД.
事务通常围绕完整业务用例划定，例如修改电影和相关统计，而不是每条 DAO 调用单独提交。数据库隔离级别、应用锁、版本字段和约束分别解决不同问题，需要一起设计；ORM 本身不能代替业务一致性分析。
Транзакцию обычно задают для полного сценария, например изменения фильма и связанных итогов, а не отдельного commit для каждого DAO-вызова. Уровень изоляции, прикладные блокировки, версия и ограничения решают разные задачи и проектируются совместно; ORM не заменяет анализ бизнес-согласованности.

Jakarta Data：标准化 Repository 抽象 Jakarta Data: стандартизованная абстракция Repository

Jakarta Data 用声明式 Repository 简化访问数据。它比持久化底层 API 更接近业务方法，但不替代实体映射、数据库与事务设计。本节严格以 Data 1.0 为基线。
Jakarta Data упрощает доступ к данным через декларативные Repository. Это ближе к бизнес-методам, чем низкоуровневый API персистентности, но не заменяет отображения, БД и транзакции. Раздел последовательно использует Data 1.0.

1. 定位与版本边界1. Назначение и версии

Jakarta Data 1.0 为 Jakarta EE 11 发布，最低要求 Java 17。开发者声明 Repository 接口，提供者为方法生成或提供实现；在 CDI 环境中可通过 @Inject 获取。统一 API 不等于任意数据库之间无需修改就能切换。
Jakarta Data 1.0 выпущена для Jakarta EE 11 и требует минимум Java 17. Разработчик объявляет Repository-интерфейс, провайдер генерирует или предоставляет реализацию; в CDI-среде её получают через @Inject. Общий API не означает замену любой БД другой без изменений.

Лабораторная использует EE 10: jakarta.jakartaee-api:10.0.0 не содержит Data 1.0. Даже наличие CDI не позволяет просто написать @Repository и ожидать реализацию. 2. 与 Persistence、ORM 和 NoSQL 的关系2. Связь с Persistence, ORM и NoSQL

Jakarta Persistence 负责关系持久化：实体映射、上下文和查询。Data 负责 Repository 方法的声明与调用，可使用 Persistence 实体模型、NoSQL 模型或提供者自定义模型。Data 不提供替代 @Entity、@Id 和 @Column 的通用映射注解，映射规则由支持的实体模型决定。
Jakarta Persistence отвечает за реляционные отображения, контекст и запросы. Data определяет объявление и вызов Repository-методов и может использовать модель сущностей Persistence, NoSQL или собственную модель провайдера. Data не задаёт универсальные аннотации взамен @Entity, @Id и @Column: отображения определяются поддерживаемой моделью.
Data 1.0 的 Repository 是无状态的；第一版没有标准化与 Persistence 的详细集成，也没有定义对外暴露 JPA 式有状态上下文的语义。不能保证取出对象后改 setter 就自动写回，也不能断言所有实现都调用 EntityManager。

统一入口不会赋予底层数据库原本不存在的能力。键值库、文档库和关系库在筛选、连接、一致性与事务上仍不同；可移植的是受支持的 API 使用方式，不是任意查询能力或已有数据格式。
Общий вход не добавляет БД отсутствующих возможностей. Key-value, документные и реляционные БД различаются фильтрацией, соединениями, согласованностью и транзакциями. Переносимы поддерживаемые способы использования API, а не любые запросы или существующий формат данных.

6. insert、update、save 的准确区别6. Точное различие insert, update и save

在具有 ACID 事务的数据库场景中，insert 表达创建新记录；相同标识符已存在时报告 EntityExistsException。update 表达修改已存在记录，匹配标识符，并在有版本字段时检查版本；缺少记录或版本不一致会报告 OptimisticLockingFailureException。
В БД с ACID-транзакциями insert создаёт новую запись, а существующий идентификатор вызывает EntityExistsException. update изменяет существующую запись по идентификатору и при наличии версии проверяет её; отсутствие записи или несовпадение версии вызывает OptimisticLockingFailureException.
Data 1.0 的 save 按数据库中是否已有相同标识符选择更新或插入，不是“id 非空就一定 update”。规范不保证它只用一条原子 SQL UPSERT，也不允许忽视并发唯一性与事务。BASE 或追加写入存储的 insert/update 保证可能不同，需要说明环境。
save в Data 1.0 выбирает update либо insert по существованию идентификатора в БД, а не по правилу «ненулевой id всегда update». Стандарт не гарантирует один атомарный SQL UPSERT и не отменяет конкурентную уникальность и транзакции. Для BASE- и append-хранилищ гарантии insert/update могут отличаться.
应继续使用返回实例，例如 movie = movies.save(movie)，它包含生成 id、更新版本等；输入实例不保证原地更新或保持托管。Jakarta Data.save、Spring Data JPA.save 和 EntityManager.merge 属于不同 API，方法名相似不等于契约相同。
Нужно использовать результат, например movie = movies.save(movie), с новым id, версией и другими значениями; исходный экземпляр не обязан обновляться на месте или оставаться управляемым. Jakarta Data.save, Spring Data JPA.save и EntityManager.merge — разные API: похожее имя не означает одинаковый контракт.

7. 排序、分页与规模7. Сортировка, пагинация и масштаб

Data 1.0 提供 PageRequest、Page、CursoredPage、Sort、Order、Limit。偏移分页方便按页跳转，但大偏移可能扫描并跳过大量记录。游标分页按已有排序位置继续，适合连续浏览，但需相应数据库与提供者支持。
Data 1.0 предоставляет PageRequest, Page, CursoredPage, Sort, Order, Limit. Offset-пагинация удобна для перехода к номеру страницы, но большое смещение может потребовать просмотра и пропуска множества записей. Cursor-пагинация продолжает с известной позиции и подходит для последовательного просмотра при поддержке БД и провайдера.
要使用确定性排序，例如 name 后再按唯一 id 排序，避免同名记录顺序不稳定。并发插入删除仍会影响页面，分页本身不是多次请求共享的数据库快照。每页大小也应受控，防止一次将所有实体和关联对象载入内存。
Нужен детерминированный порядок, например name и затем уникальный id, чтобы совпадающие имена не давали нестабильный порядок. Конкурентные вставки и удаления продолжают влиять на страницы; пагинация не является общим snapshot для нескольких запросов. Размер страницы ограничивают, чтобы не загрузить все сущности и связи в память.

8. 生成方式、CDI 与事务8. Реализация, CDI и транзакции

实现可以由编译期注解处理器生成，也可由运行时机制提供，具体由提供者决定。不能将 Spring 常见的运行时代理说成所有 Jakarta Data 实现的要求，也不能声称所有查询错误都必定在编译期发现；错误可在构建、部署或调用时暴露。
Реализация может генерироваться compile-time annotation processor либо предоставляться runtime-механизмом — это решает провайдер. Распространённый runtime-прокси Spring не обязателен для всех Data-реализаций; не все ошибки запросов гарантированно находятся при компиляции: они возможны при сборке, развёртывании и вызове.
若 Jakarta Transactions 可用、线程已有全局事务且数据源能加入事务，Repository 必须参与它，不能擅自提交或回滚调用方的事务。多个仓库操作要共同成功时，应在业务层设计事务边界。受支持环境中可在仓库接口或方法标注 @Transactional。
Если доступны Jakarta Transactions, у потока есть глобальная транзакция и источник может присоединиться, Repository обязан участвовать в ней и не вправе самостоятельно фиксировать или откатывать транзакцию вызывающей стороны. Для атомарности нескольких операций границу задают в бизнес-слое. В поддерживаемой среде @Transactional допускается на интерфейсе или методе Repository.
只添加注解 API，不会自动产生容器和事务管理器；底层存储没有多记录事务时，统一接口也不能凭空提供相同 ACID 保证。无论采用何种声明式仓库，都要区分访问抽象与存储实际保证。
Добавление API-аннотации не создаёт контейнер и transaction manager. Если хранилище не имеет многозаписных транзакций, интерфейс не добавит одинаковые гарантии ACID. При любом декларативном репозитории нужно различать абстракцию доступа и реальные гарантии хранения.

9. 优点、限制和适用判断9. Плюсы, ограничения и решение о применении

  • 优点：常见 CRUD 与筛选不必重复实现；接口更接近领域；标准化减少对单个仓库框架 API 的绑定，CDI、参数与分页形成一致模型。
    Плюсы: меньше повторных реализаций CRUD и фильтров; интерфейс ближе к предметной области; стандарт уменьшает зависимость от API одного repository-фреймворка, унифицируя CDI, параметры и пагинацию.
  • 限制：需要具体提供者支持；复杂查询、加载、缓存和专有数据库功能可能需要扩展；标准接口不保证相同 SQL、相同性能、任意数据库迁移或已有数据格式兼容。
    Ограничения: нужен провайдер; сложные запросы, загрузка, кэш и функции БД могут потребовать расширений; API не гарантирует одинаковые SQL, скорость, миграцию между любыми БД или совместимость имеющихся данных.
  • 手写 DAO 适合明确表达特殊执行流程，Repository 节省常见操作实现。采用 Data 应看环境兼容性、查询需求、维护成本与团队经验，不应只因为名字比 Persistence 更新。
    Ручной DAO явно выражает особый процесс, Repository экономит реализацию обычных операций. Data выбирают по совместимости среды, запросным требованиям, сопровождению и опыту команды, а не из-за более нового названия по сравнению с Persistence.

Spring 平台：与 Java EE / Jakarta EE 的关系 Платформа Spring: связь с Java EE / Jakarta EE

Spring Framework 是以 IoC / DI 为核心的应用框架；Jakarta EE 是由多个规范组成的企业 Java 平台。两者都能提供 Web、事务和数据访问能力，也可以组合使用。
Spring Framework — прикладной фреймворк с ядром IoC / DI; Jakarta EE — платформа корпоративной Java, состоящая из набора спецификаций. Оба подхода поддерживают веб-приложения, транзакции и доступ к данным и могут использоваться совместно.

1. 先区分 Spring 家族与 Spring Framework1. Сначала разделим семейство Spring и Spring Framework

广义的 Spring 指 Spring Framework、Spring Boot、Spring Data、Spring Security 等项目组成的生态。狭义的 Spring Framework 提供容器、AOP、事务、JDBC / ORM 集成、Spring MVC / WebFlux 和测试支持。Boot 简化应用配置与启动；Data 简化持久化访问；它们承担不同职责，不能把三个名称当作同义词。
В широком смысле Spring — экосистема проектов: Spring Framework, Spring Boot, Spring Data, Spring Security и других. В узком смысле Spring Framework предоставляет контейнер, AOP, транзакции, интеграцию JDBC / ORM, Spring MVC / WebFlux и средства тестирования. Boot упрощает конфигурацию и запуск приложения, Data — доступ к сохраняемым данным. Это разные обязанности, поэтому три названия не являются синонимами.
Jakarta EE 定义组件之间及组件与容器之间的契约，由兼容运行时实现；Spring 提供自己的编程与配置模型，同时集成 Jakarta Servlet、Persistence、Validation、Transactions 等 API。使用 Spring MVC 通常仍需要 Servlet 容器；使用 Spring Data JPA 仍需要 Persistence 提供者。Spring 不是数据库、应用服务器或 ORM 提供者。
Jakarta EE определяет контракты между компонентами, а также между компонентами и контейнером; их реализует совместимая среда исполнения. Spring предлагает собственную модель программирования и конфигурации и одновременно интегрирует API Jakarta Servlet, Persistence, Validation, Transactions и другие. Для Spring MVC обычно по-прежнему нужен Servlet-контейнер, а для Spring Data JPA — провайдер Persistence. Spring сам по себе не является базой данных, сервером приложений или ORM-провайдером.

2. IoC 与 DI：谁创建、装配和管理对象2. IoC и DI: кто создаёт, связывает и управляет объектами

IoC（控制反转）把部分控制权交给框架。DI（依赖注入）是 IoC 的一种实现方式：MovieService 声明自己需要 MovieRepository，容器选择实现并通过构造器、setter 或字段注入。业务类不再自行 new 某个数据库实现，更容易替换依赖、单独测试和发现依赖关系。
IoC, инверсия управления, передаёт часть управления фреймворку. DI, внедрение зависимостей, — один из способов реализации IoC: MovieService объявляет потребность в MovieRepository, а контейнер выбирает реализацию и передаёт её через конструктор, setter или поле. Бизнес-класс больше не создаёт конкретную реализацию базы данных через new; зависимости легче заменять, отдельно тестировать и анализировать.
构造器适合必需依赖，能让依赖保持 final，也能在普通单元测试中直接传入替身。setter 适合可选或确实需要后续配置的依赖；字段注入简短，但隐藏了构造要求，并增加脱离容器测试的难度。DI 不意味着所有对象都必须由容器创建：DTO、值对象、JPA 实体通常仍由业务代码或持久化提供者创建。
Конструктор удобен для обязательных зависимостей: поле можно сделать final, а в обычном модульном тесте передать подмену напрямую. Setter подходит для необязательных зависимостей или последующей настройки. Внедрение в поле короче, но скрывает требования к созданию объекта и усложняет тестирование вне контейнера. DI не требует создавать через контейнер каждый объект: DTO, объекты-значения и JPA-сущности обычно создаёт прикладной код или провайдер сохранения данных.

3. BeanFactory、ApplicationContext 与 Bean 生命周期3. BeanFactory, ApplicationContext и жизненный цикл бина

Spring bean 是由 Spring 容器实例化、装配或管理的对象。BeanFactory 提供基本的 bean 获取与依赖装配能力；ApplicationContext 扩展它，加入事件、国际化资源、面向应用的上下文及与 AOP 等机制的集成。实际应用通常使用 ApplicationContext；容器根据 bean 定义管理对象，并非扫描到任何类就自动把它变成 bean。
Spring bean — объект, который создаётся, связывается или управляется контейнером Spring. BeanFactory предоставляет базовые средства получения бинов и связывания зависимостей. ApplicationContext расширяет его событиями, ресурсами интернационализации, прикладными контекстами и интеграцией, например, с AOP. В приложениях обычно используют ApplicationContext. Контейнер управляет объектами по определениям бинов; произвольный обнаруженный класс не становится бином автоматически.
典型生命周期可概括为：读取定义 → 实例化 → 注入依赖 → 初始化回调与后处理 → 对外使用（可能经过代理）→ 容器关闭时销毁回调。现代 Spring 可识别 jakarta.annotation.PostConstruct / PreDestroy；BeanPostProcessor 可扩展处理过程。prototype 的创建和初始化受管理，但容器通常不负责其完整销毁过程；资源释放需要调用方处理。
Типичный жизненный цикл можно представить так: чтение определения → создание экземпляра → внедрение зависимостей → инициализация и постобработка → использование, возможно через прокси → уничтожение при закрытии контейнера. Современный Spring поддерживает jakarta.annotation.PostConstruct / PreDestroy; BeanPostProcessor позволяет расширять обработку. Контейнер создаёт и инициализирует prototype-бин, но обычно не управляет его полным уничтожением: освобождать ресурсы должен вызывающий код.

6. AOP 与事务：必须理解代理边界6. AOP и транзакции: важно понимать границу прокси

Spring AOP 常用代理在目标方法前后加入横切逻辑，例如事务、缓存或安全检查。调用方拿到的引用可能是 JDK 接口代理或类代理，具体类型取决于配置。普通 Spring 中应启用相应基础设施；Boot 在满足条件时常替你完成配置。只写 @Transactional 并不意味着任意 new 出来的对象都会获得事务。
Spring AOP обычно использует прокси, добавляющий сквозную логику до и после целевого метода: транзакции, кеширование, проверки безопасности. Ссылка, полученная вызывающим кодом, может указывать на JDK-прокси интерфейса или прокси класса — это зависит от настройки. В обычном Spring соответствующую инфраструктуру нужно включить; Boot часто настраивает её при выполнении условий. Одна аннотация @Transactional не делает транзакционным объект, произвольно созданный через new.
在默认代理模式下，外部调用通过代理才应用事务拦截。同一对象中的 this.inner() 不会重新经过代理，因此 inner() 的 @Transactional 不会单独启动或改变事务；若外层已有事务，代码仍运行在外层事务中。常见修复是把独立事务职责移到另一个 bean，或使用 TransactionTemplate；不能把这个规则泛化到所有框架和所有织入模式。
В стандартном режиме прокси транзакционный перехват применяется к внешнему вызову через прокси. Вызов this.inner() внутри того же объекта не проходит через него повторно, поэтому @Transactional на inner() отдельно не начинает и не изменяет транзакцию. Если внешняя транзакция уже есть, код продолжает выполняться в ней. Обычно отдельную транзакционную операцию переносят в другой бин либо используют TransactionTemplate. Это правило нельзя переносить на все фреймворки и режимы внедрения аспектов.
org.springframework.transaction.annotation.Transactional 提供传播行为、隔离级别、超时、只读提示和回滚规则；Spring 也支持 jakarta.transaction.Transactional，但两者属性并不完全相同。常规默认规则是运行时异常和 Error 导致回滚，受检异常默认不回滚，具体规则可以配置。readOnly 是给基础设施的优化提示，不能代替数据库权限或只读事务的实际约束。
org.springframework.transaction.annotation.Transactional задаёт распространение транзакции, изоляцию, тайм-аут, признак readOnly и правила отката. Spring поддерживает также jakarta.transaction.Transactional, но наборы атрибутов различаются. Обычное правило по умолчанию: runtime-исключения и Error вызывают откат, проверяемые исключения — нет; правила можно настроить. readOnly — подсказка инфраструктуре для оптимизации, а не замена правам базы данных или её реальным ограничениям на запись.

  • 选择 Spring 的理由：模块灵活、配置与测试工具统一、生态集成丰富，适合自行控制应用启动和依赖组合。代价是需要理解代理、条件配置和多项目版本关系；大量约定可能隐藏运行机制。
    Причины выбрать Spring: гибкие модули, единые средства настройки и тестирования, множество интеграций, контроль над запуском и составом зависимостей. Цена — согласование возможностей и версий целевого сервера, а также различий развёртывания, загрузки классов и настройки ресурсов. Spring Boot：配置、启动与运行 Spring Boot: конфигурация, запуск и эксплуатация

Spring Boot 在 Spring Framework 之上提供有主张的默认配置、依赖管理、启动与运维支持。它减少重复配置，但没有替代 Spring 容器、业务设计或数据库知识。
Spring Boot добавляет к Spring Framework согласованные настройки по умолчанию, управление зависимостями, запуск и эксплуатационные средства. Он сокращает повторяющуюся конфигурацию, но не заменяет контейнер Spring, проектирование бизнес-логики или знание базы данных.

1. Boot 具体解决什么问题1. Какую задачу решает Boot

如果直接使用 Spring，开发者需要选择一组兼容依赖、创建上下文、连接 Web / 数据库基础设施、安排应用启动及打包方式。Boot 提供常用组合与默认约定，让应用更快达到可运行状态；实际 bean 仍由 Spring 的 ApplicationContext 管理。Boot 应用也可以是命令行、批处理或消息消费者，不必提供 HTTP 接口。
При непосредственном использовании Spring разработчик выбирает совместимые зависимости, создаёт контекст, связывает веб-инфраструктуру и базу данных, организует запуск и упаковку. Boot предлагает распространённые сочетания и соглашения по умолчанию, быстрее приводя приложение в рабочее состояние. Самими бинами по-прежнему управляет ApplicationContext Spring. Boot-приложение может быть консольной программой, пакетным заданием или потребителем сообщений и не обязано предоставлять HTTP-интерфейс.
Boot 的约定优于配置，含义是“常见情况有默认方案”，而不是“不需要配置”。数据库连接、业务校验、事务边界、授权、容量规划与查询优化仍然需要设计。依赖变化也可能改变自动配置结果，所以答辩时应能解释某个 bean 是从哪里来的。
«Соглашения вместо конфигурации» означает наличие готового решения для типичного случая, а не полное отсутствие настройки. Подключение базы, бизнес-валидацию, границы транзакций, авторизацию, планирование нагрузки и оптимизацию запросов всё равно проектируют. Изменение зависимостей может изменить результат автоконфигурации, поэтому на защите полезно уметь объяснить происхождение конкретного бина.

3. 自动配置不是魔法：条件匹配与回退3. Автоконфигурация: проверка условий и отступление перед явной настройкой

典型条件包括 @ConditionalOnClass（类存在）、@ConditionalOnMissingBean（缺少某类 bean）、@ConditionalOnProperty（属性符合条件）。例如存在数据访问依赖、配置满足要求且没有自定义 DataSource 时，相关自动配置可创建数据源。是否真的创建成功仍取决于驱动、连接参数等条件；加入 JPA starter 不会自动提供可用的生产数据库。
Типичные условия: @ConditionalOnClass — наличие класса, @ConditionalOnMissingBean — отсутствие подходящего бина, @ConditionalOnProperty — подходящее значение свойства. Например, при наличии зависимостей доступа к данным, нужной конфигурации и отсутствии собственного DataSource соответствующая автоконфигурация может создать источник данных. Успех всё равно зависит от драйвера и параметров соединения. Подключение JPA starter не создаёт готовую промышленную базу данных.
许多自动配置在发现用户提供的 bean 后会退让（back off）。这属于各自动配置定义的条件行为，不能笼统地说“任何同名 bean 都会被静默覆盖”。排查时先看依赖树、配置值和条件报告，可使用 --debug；确实不需要某项自动配置时再通过 exclude 等方式排除，而不是随意复制内部配置类。
Многие автоконфигурации отступают, обнаружив пользовательский бин: back off. Это результат условий конкретной автоконфигурации, а не общее правило о бесшумной замене любого одноимённого бина. Для диагностики проверяют дерево зависимостей, свойства и отчёт условий, например через --debug. Ненужную автоконфигурацию исключают через exclude и аналогичные средства, а не произвольно копируют внутренние классы настройки.

4. @SpringBootApplication 与启动过程4. @SpringBootApplication и последовательность запуска

@SpringBootApplication 组合 @SpringBootConfiguration、@EnableAutoConfiguration 与 @ComponentScan。第一个让主类成为配置源，第二个启用条件自动配置，第三个扫描主类所在包及其子包中的组件。把主类放在应用根包通常更清晰；在默认包中定义主类可能导致扫描范围过大。实体扫描和 Repository 发现还有各自规则，不能把所有发现过程理解成同一个注解扫描。
@SpringBootApplication объединяет @SpringBootConfiguration, @EnableAutoConfiguration и @ComponentScan. Первая делает главный класс источником конфигурации, вторая включает условную автоконфигурацию, третья сканирует компоненты в пакете главного класса и его подпакетах. Главный класс обычно размещают в корневом пакете приложения. Пакет по умолчанию может чрезмерно расширить сканирование. У обнаружения сущностей и репозиториев есть собственные правила; все виды обнаружения не сводятся к одному сканированию аннотаций.
SpringApplication.run 准备环境与配置，选择并创建合适的 ApplicationContext，加载配置、刷新上下文，随后运行启动回调。Web 应用在相应配置下启动内嵌 HTTP 服务器；非 Web 应用无需服务器。“有 main 方法”说明能自行启动，并不意味着绕过了 Spring 容器。
SpringApplication.run подготавливает окружение и конфигурацию, выбирает и создаёт подходящий ApplicationContext, загружает настройки, обновляет контекст и затем выполняет стартовые обратные вызовы. Веб-приложение при соответствующей настройке запускает встроенный HTTP-сервер; невеб-приложению сервер не нужен. Наличие main означает самостоятельный запуск, но не обход контейнера Spring.
JAVA
package example.movie;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class MovieApplication {
    public static void main(String[] args) {
        SpringApplication.run(MovieApplication.class, args);
    }
}
Boot 3 风格的最小启动类；仍需构建文件中的依赖。功能组件通常放在 example.movie 的子包内，业务接口与数据库配置需要另外实现。
Минимальный стартовый класс в стиле Boot 3; зависимости в файле сборки всё равно нужны. Прикладные компоненты обычно размещают в подпакетах example.movie; бизнес-интерфейсы и настройку базы реализуют отдельно.

5. 外部配置与 profile：同一代码适应不同环境5. Внешняя конфигурация и profile: один код для разных сред

Boot 可读取 application.properties / YAML、环境变量、命令行参数等来源，并按规定的优先级合并。@Value 适合注入简单值；@ConfigurationProperties 适合把一组相关属性绑定到配置对象，可配合校验。配置错误应在启动时尽早暴露，而不是直到第一次业务调用才发现数据库地址缺失。
Boot читает application.properties / YAML, переменные окружения, аргументы командной строки и другие источники, объединяя их по определённому приоритету. @Value удобна для простого значения, @ConfigurationProperties — для связывания группы свойств с объектом настройки, в том числе с валидацией. Ошибки конфигурации лучше обнаруживать при запуске, а не при первом бизнес-вызове из-за отсутствующего адреса базы.
Profile 用来选择一组配置或组件，例如 dev、test、prod。它是条件选择机制，不是密码加密与秘密管理系统。敏感值可从外部受控来源提供；不能认为把密码放进 application-prod.properties 就使其安全。示例属性及 starter 名称按 Boot 3 展示，迁移其他发行线时应查相应文档。
Profile выбирает набор настроек или компонентов, например dev, test, prod. Это механизм условного выбора, а не шифрования паролей или управления секретами. Чувствительные значения передают из внешнего контролируемого источника. Пароль не становится защищённым только потому, что находится в application-prod.properties. Примеры свойств и названий starter приведены для Boot 3; при переходе на другую линию выпуска проверяют её документацию.

7. Actuator 与测试：能运行之后还要可观测7. Actuator и тестирование: работающее приложение должно быть наблюдаемым

Actuator 提供 health、metrics、conditions 等运维端点，便于检查健康、指标与自动配置原因。端点存在、允许访问、通过 HTTP / JMX 暴露以及通过身份验证是不同层面的设置。应按需求选择暴露范围和授权；不能为了排错直接认定所有端点都适合公开。健康检查成功也不等于所有业务行为正确。
Actuator предоставляет эксплуатационные endpoint, например health, metrics, conditions, для проверки здоровья, метрик и причин автоконфигурации. Наличие endpoint, разрешение доступа, публикация по HTTP / JMX и аутентификация — разные настройки. Публикацию и авторизацию выбирают по потребности; наличие диагностической задачи не делает все endpoint подходящими для общего доступа. Успешная проверка здоровья не доказывает корректность всей бизнес-логики.
普通业务逻辑可以用不启动容器的单元测试；@SpringBootTest 用于需要 Boot 上下文的集成测试，默认并不启动真实 HTTP 服务器；RANDOM_PORT 可启动实际服务器。@WebMvcTest、@DataJpaTest 等切片测试只加载相关部分，速度通常更快，但不能替代完整集成验证。使用真实 HTTP 服务时，客户端测试事务不会自动回滚服务器线程里已经提交的事务。
Обычную бизнес-логику можно проверять модульными тестами без контейнера. @SpringBootTest подходит для интеграционных тестов с контекстом Boot и по умолчанию не запускает настоящий HTTP-сервер; RANDOM_PORT позволяет запустить его. Срезы @WebMvcTest, @DataJpaTest загружают только относящиеся к задаче части и обычно быстрее, но не заменяют полноценную интеграционную проверку. При настоящем HTTP-сервере транзакция клиентского теста не откатывает автоматически уже зафиксированные транзакции серверного потока.

8. 优点、局限与和实验的对照8. Преимущества, ограничения и сопоставление с лабораторной

  • 优点：减少启动与集成样板，提供协调依赖与一致配置，便于形成可独立发布的应用；接入监控与测试工具的路径比较统一。对常见需求效率高，但“配置少”不等于架构更正确。
    Преимущества: меньше шаблонного кода запуска и интеграции, согласованные зависимости и единая настройка, удобная независимая поставка приложения и понятный путь к мониторингу и тестированию. Типовые задачи решаются быстрее, но меньше конфигурации не означает более правильную архитектуру.
  • 局限：默认行为需要理解；依赖升级可能影响条件匹配和兼容性；不需要的 starter 会增加依赖及启动成本。复杂系统仍要设计模块边界、事务、数据库索引、错误处理和安全策略；Boot 不保证应用天然是微服务，也不保证性能更高。
    Ограничения: поведение по умолчанию нужно понимать; обновление зависимостей влияет на условия и совместимость; лишние starter увеличивают зависимости и стоимость запуска. В сложной системе по-прежнему проектируют границы модулей, транзакции, индексы, обработку ошибок и безопасность. Boot не делает приложение микросервисом автоматически и не гарантирует более высокой производительности.
  • 与本实验对照：pom.xml 中使用 Jakarta EE API、以 WAR 打包，不能据此称它为 Spring Boot。若选择 Boot，需要引入相应启动与依赖体系，配置数据源和持久化提供者，并重接 Web / 注入 / 事务组件。若保留原有领域模型，业务规则可以复用；框架转换不应改变业务语义。
    Сопоставление с лабораторной: использование Jakarta EE API в pom.xml и упаковка WAR не делают приложение Spring Boot. При выборе Boot подключают соответствующий запуск и зависимости, настраивают источник данных и провайдер сохранения, связывают веб-компоненты, внедрение и транзакции. При сохранении доменной модели бизнес-правила можно использовать повторно; смена фреймворка не должна менять смысл операций.

Spring Data：Repository 抽象与数据访问 Spring Data: абстракция Repository и доступ к данным

Spring Data 是面向多种存储技术的项目家族；Spring Data JPA 是其中基于 Jakarta Persistence 的模块。它减少 Repository 实现样板，但不替代 ORM 提供者、SQL、事务和查询优化。
Spring Data — семейство проектов для разных технологий хранения; Spring Data JPA — его модуль на основе Jakarta Persistence. Он сокращает шаблонную реализацию репозиториев, но не заменяет ORM-провайдер, SQL, транзакции и оптимизацию запросов.

1. 一条完整的数据访问链1. Полная цепочка доступа к данным

在典型 Spring Data JPA 应用中，调用链是：Controller → 业务 Service → Repository 代理 → JPA EntityManager → Hibernate / EclipseLink → JDBC → 数据库。Spring Framework 提供容器与事务集成，Boot 可自动装配相应设施，Spring Data JPA 提供 Repository 层实现，ORM 提供者负责对象状态、映射与 SQL。这几层可以分别解释，也可以分别调整。
В типичном приложении Spring Data JPA цепочка такова: Controller → бизнес-сервис → прокси Repository → JPA EntityManager → Hibernate / EclipseLink → JDBC → база данных. Spring Framework обеспечивает контейнер и интеграцию транзакций, Boot может автоматически настроить инфраструктуру, Spring Data JPA реализует слой репозиториев, а ORM-провайдер управляет состоянием объектов, отображением и SQL. Эти уровни объясняют и настраивают отдельно.
Spring Data 不是一种数据库，也不等于 Spring Data JPA。家族中有 JPA、JDBC、MongoDB、Redis、R2DBC 等模块；它们共享部分 Repository 概念，却不保证查询语言、事务范围、映射能力完全一致。Spring Data 可以在没有 Spring Boot 的应用中配置使用，Boot 只是降低集成成本。
Spring Data не является базой данных и не равен Spring Data JPA. В семействе есть модули JPA, JDBC, MongoDB, Redis, R2DBC и другие. Они разделяют часть концепций Repository, но язык запросов, границы транзакций и возможности отображения не обязаны совпадать. Spring Data можно настроить без Spring Boot; Boot лишь упрощает интеграцию.

2. 为什么只写接口也能调用2. Почему работает репозиторий, заданный только интерфейсом

应用声明带领域类型与 ID 类型的接口，如 JpaRepository<Movie, Long>。Repository 基础设施发现接口并创建代理：标准 CRUD 方法交给基础实现，查询方法按声明查询或方法名生成查询，也可组合自定义实现片段。因此并不是 Java 语言突然允许实例化接口，而是框架提供了运行时实现。接口本身仍需要被正确发现、注册，并连接到合适的 EntityManager。
Приложение объявляет интерфейс с типом сущности и идентификатора, например JpaRepository<Movie, Long>. Инфраструктура обнаруживает его и создаёт прокси: стандартный CRUD делегируется базовой реализации, запросы берутся из явного объявления либо выводятся из имени метода; можно добавить собственные фрагменты реализации. Java не начинает непосредственно создавать экземпляры интерфейсов: реализацию предоставляет фреймворк. Интерфейс нужно корректно обнаружить, зарегистрировать и связать с подходящим EntityManager.
按名称派生查询适合短而明确的条件。方法名很长、包含大量可选筛选或复杂关联时，可改用显式 @Query、基于 Criteria 的 Specification，或自定义 Repository 实现。减少样板代码不意味着必须把所有 SQL 或业务流程藏在一个巨大方法名里。
Вывод запроса из имени удобен для коротких, ясных условий. Для длинных имён, множества необязательных фильтров или сложных связей используют явный @Query, Specification на основе Criteria либо собственную реализацию репозитория. Сокращение шаблонного кода не требует прятать весь SQL или бизнес-процесс в одном огромном имени метода.

4. 方法名、JPQL 和原生 SQL4. Имя метода, JPQL и нативный SQL

派生方法使用实体属性名，而不是数据库列名，例如 findByNameContainingIgnoreCase。@Query 默认使用 JPQL，以实体类型和属性表达查询；nativeQuery=true 表示原生 SQL，以表和列为对象。命名参数必须绑定值，不要拼接不可信字符串；动态排序字段通常不能作为普通值参数绑定，应限制为允许的属性集合。
Производные методы используют имена свойств сущности, а не колонок базы, например findByNameContainingIgnoreCase. @Query по умолчанию задаёт JPQL с типами сущностей и их свойствами. nativeQuery=true означает нативный SQL с таблицами и колонками. Значения связывают параметрами, не собирая запрос из непроверенных строк. Имена полей сортировки обычно нельзя связать как обычные значения; их ограничивают допустимым набором свойств.
修改查询通常需要 @Modifying 及适当的事务配置。批量 JPQL / SQL 更新直接作用于数据库，不能假定已经加载的实体状态会同步更新，也不能假定逐个实体的回调都会执行；要安排 flush、clear 或重新读取。查询能生成不代表查询便宜，仍需查看实际 SQL、索引和执行计划。
Для изменяющего запроса обычно нужны @Modifying и подходящая транзакция. Массовый JPQL / SQL меняет базу напрямую: уже загруженные сущности не обязательно обновятся, и индивидуальные callbacks сущностей не обязательно выполнятся. Нужно продумать flush, clear либо повторное чтение. Возможность построить запрос не означает, что он дешёвый: проверяют SQL, индексы и план выполнения.

5. save 的真实语义：新实体检测、persist 与 merge5. Реальная семантика save: определение нового объекта, persist и merge

Spring Data JPA 的 save 先判断实体是否为新对象，再选择 EntityManager.persist 或 merge。默认通常先检查非 primitive 的版本属性；若没有这种属性，再检查 ID 是否为 null。实现 Persistable 可通过 isNew 自定义判断。手动赋值 ID、版本类型等会影响这一路径，不能简单背成“有 ID 就是 UPDATE，没有 ID 就是 INSERT”。
Spring Data JPA сначала определяет, новая ли сущность, затем выбирает EntityManager.persist или merge. По умолчанию обычно сначала проверяется версия непримитивного типа; если такой версии нет — равен ли ID null. Реализация Persistable позволяет задать isNew самостоятельно. Присвоенный вручную ID и тип версии меняют этот путь, поэтому правило «есть ID — UPDATE, нет ID — INSERT» слишком грубое.
merge 把传入状态复制到受管实例，并返回受管实例；传入对象本身不因此自动变成受管对象，所以应使用 save 的返回值。对当前持久化上下文里已经受管的实体，事务内修改通常由脏检查同步，并不总需要再调用 save。save 不承诺立即发 SQL；saveAndFlush 触发同步也不等于提交事务。
merge копирует состояние переданного объекта в управляемый экземпляр и возвращает его; исходный объект сам по себе не становится управляемым. Поэтому используют возвращаемое значение save. Изменения уже управляемой сущности в текущем контексте обычно синхронизируются проверкой изменений в транзакции, без обязательного повторного save. save не обещает немедленную отправку SQL; saveAndFlush синхронизирует состояние, но не означает фиксацию транзакции.
save 不是数据库原子 UPSERT 的通用保证，也不自动解决并发覆盖。是否插入、更新以及何时访问数据库由状态与提供者决定；并发更新可结合 @Version、数据库约束和适当事务策略处理。数据库专用 ON CONFLICT / MERGE 与 JPA merge 的含义不同。
save не является общей гарантией атомарного UPSERT базы данных и не решает автоматически потерю конкурентных изменений. Вставка, обновление и момент доступа к базе зависят от состояния и провайдера. Конкурентные изменения обрабатывают через @Version, ограничения базы и подходящую транзакционную стратегию. Специальные ON CONFLICT / MERGE базы и JPA merge имеют разный смысл.

6. 事务边界通常放在业务用例层6. Транзакционная граница обычно проходит по бизнес-сценарию

标准 CRUD 实现为部分方法提供默认事务配置，但自己声明的查询方法不能一概假定都拥有所需事务。一个业务操作包含多个 Repository 调用时，通常在 Service 上定义外层 @Transactional，使它们在同一事务管理器与资源配置下共同完成或回滚。仅让每个 Repository 方法分别提交，不保证整个业务操作原子。
Для части стандартных CRUD-методов реализация задаёт транзакции по умолчанию, но для собственных запросов нельзя автоматически предполагать нужную транзакционность. Если бизнес-операция включает несколько вызовов репозиториев, внешнюю @Transactional обычно задают в сервисе, чтобы при одном менеджере транзакций и соответствующих ресурсах они выполнялись или откатывались вместе. Отдельная фиксация каждого метода не обеспечивает атомарность всего сценария.
外层事务的传播、只读和回滚规则需要设计；调用多个不同数据库或混合不同事务管理器时，不会因为 Service 上出现一个注解就自然获得分布式原子性。还要记住 Spring 默认代理模式的自调用限制，并避免把业务事务无限延长到远程调用或用户交互。
Распространение внешней транзакции, readOnly и откат нужно продумать. Вызовы разных баз или сочетание разных менеджеров транзакций не получают распределённую атомарность от одной аннотации на сервисе. Нужно также учитывать ограничение внутренних вызовов в стандартном режиме прокси Spring и не растягивать бизнес-транзакцию на длительные удалённые вызовы или взаимодействие пользователя.

7. 性能与延迟加载：Repository 不消除 ORM 代价7. Производительность и отложенная загрузка: Repository не устраняет стоимость ORM

  • N+1：先查询 N 部电影，再逐个访问 director，可能产生额外 N 次查询。可按用例使用 fetch join、EntityGraph、DTO 投影或批量抓取；实际效果取决于提供者与查询，必须检查 SQL。把所有关联一律改为 EAGER 会增加无用数据及笛卡尔积风险。
    N+1: после чтения N фильмов обращение к director каждого из них может вызвать ещё N запросов. По сценарию выбирают fetch join, EntityGraph, DTO-проекцию или пакетную загрузку. Результат зависит от провайдера и запроса, поэтому проверяют SQL. Повсеместный EAGER увеличивает ненужные данные и риск декартовых произведений.
  • 延迟加载需要仍可用的持久化上下文。事务结束、上下文关闭后再访问尚未加载的关联，可能失败；Hibernate 常表现为 LazyInitializationException。优先在业务边界内准备所需数据或 DTO。Open EntityManager in View 可延长上下文，但可能把查询推迟到视图阶段，不能当作事务设计和查询优化的通用解法。
    Отложенной загрузке нужен доступный контекст сохранения. Обращение к незагруженной связи после завершения транзакции и закрытия контекста может завершиться ошибкой; для Hibernate типичен LazyInitializationException. Нужные данные или DTO лучше подготовить в бизнес-границе. Open EntityManager in View продлевает контекст, но может переносить запросы в этап представления и не заменяет проектирование транзакций и оптимизацию.
  • 分页需限制 page size，并给出稳定排序，例如 name 后追加 id。Page 为总数可能执行 count；大偏移量仍会使数据库扫描大量数据。列表页通常只需投影字段，不应默认加载完整对象图。集合 fetch join 与分页的组合尤其需要核对提供者行为和生成 SQL。
    В пагинации ограничивают размер страницы и задают стабильную сортировку, например name, затем id. Page может выполнять count ради общего числа; большой offset всё равно заставляет базу обрабатывать много данных. Для списка обычно достаточно проекции полей, а не полного графа объектов. Сочетание fetch join коллекции с пагинацией особенно требует проверки поведения провайдера и SQL.

容易说错 Неточная формулировка

JPA / Jakarta Persistence 是规范；Hibernate 和 EclipseLink 是不同实现。
JPA / Jakarta Persistence — спецификация; Hibernate и EclipseLink — разные реализации.
容易说错 Неточная формулировка
“Bean 的单例作用域保证线程安全。”
«Singleton-область бина гарантирует потокобезопасность.»
准确表述 Точная формулировка
作用域规定实例与上下文的关系；可变共享状态仍需并发设计。
Область задаёт отношение экземпляра к контексту; изменяемое общее состояние требует отдельного проектирования конкурентного доступа.
容易说错 Неточная формулировка
“flush 后不能回滚。”
«После flush откат невозможен.»
准确表述 Точная формулировка
flush 是同步 SQL；事务是否提交由 commit 决定，活动事务仍可回滚。
flush синхронизирует SQL; фиксация определяется commit, активную транзакцию ещё можно откатить.
容易说错 Неточная формулировка
“EAGER 表示一定用一条 JOIN。”
«EAGER обязательно означает один JOIN.»
准确表述 Точная формулировка
EAGER 规定加载要求，不规定唯一 SQL 形态；仍可能出现额外查询。
EAGER задаёт требование загрузки, но не единственную форму SQL; дополнительные запросы возможны.
容易说错 Неточная формулировка
“有 @Entity 就自动成为 CDI Bean。”
«@Entity автоматически делает класс CDI-бином.»
准确表述 Точная формулировка
实体状态由持久化上下文管理；CDI 发现和生命周期有独立规则。
Состоянием сущности управляет persistence context; у CDI отдельные правила обнаружения и жизненного цикла.
容易说错 Неточная формулировка
“Spring Boot 是应用服务器或 ORM。”
«Spring Boot — сервер приложений или ORM.»
准确表述 Точная формулировка
Boot 整合配置、依赖与运行方式；Web 服务器和 ORM 由具体依赖提供。
Boot объединяет настройку, зависимости и запуск; веб-сервер и ORM предоставляются конкретными зависимостями.
容易说错 Неточная формулировка
“Spring Data 的 save 就是数据库 UPSERT。”
«save в Spring Data — это UPSERT базы данных.»
准确表述 Точная формулировка
具体模块定义 save；Spring Data JPA 通常依据新实体检测选择 persist 或 merge。
Семантику save задаёт модуль; Spring Data JPA обычно выбирает persist или merge по определению новой сущности.
容易说错 Неточная формулировка
“Jakarta Data 替代 JPA，并强制共享上下文。”
«Jakarta Data заменяет JPA и требует общий контекст.»
准确表述 Точная формулировка
Data 规定 Repository 抽象；映射与存储取决于提供者，1.0 不统一规定与 JPA 持久化上下文的集成。
Data задаёт абстракцию репозиториев; отображение и хранение зависят от провайдера. Версия 1.0 не унифицирует интеграцию с persistence context JPA.
