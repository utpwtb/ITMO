# 10 并发写入、版本冲突与客户端自动同步

## 1. 三个不同问题，不要用同一个词概括

| 问题 | 示例 | 本实验机制 |
|---|---|---|
| 同时执行的修改互相干扰 | 两个请求同时加奖，少加一次 | 锁定 AppState 行 |
| 人拿旧表单覆盖新数据 | B 用一分钟前的内容覆盖 A 刚保存的内容 | 实体 version 检查 |
| 别人的页面不知道发生了改变 | A 保存后 B 仍显示旧列表 | revision + 定时轮询 |

前两项关乎数据正确性，后一项关乎界面是否及时看到新数据。自动刷新不能替代事务锁。

## 2. 丢失更新怎样发生

假设原奖项为 5，A 和 B 都想加 1：

```text
A 读 5 → A 算出 6
B 读 5 → B 算出 6
A 写 6
B 写 6
```

两次操作后是 6，不是 7，这叫丢失更新（потерянное обновление）。不能因为两个请求使用了不同 Java 对象，就认为不会竞争同一条数据库记录。

## 3. 当前悲观锁如何工作

源码：[Database.write()](<C:/develop/NOTE_UTP/StudyNote/5 Information Systems/Lab/Lab1/movie-lab/src/main/java/ru/itmo/movie/persistence/Database.java>)。事务开始后执行：

```java
em.find(AppState.class, 1L, LockModeType.PESSIMISTIC_WRITE,
        Map.of("jakarta.persistence.lock.timeout", 10000));
```

这是对数据库固定行申请写锁。所有正常的应用写操作都先锁这一行，再执行业务。B 需要等 A 结束后才能进入业务部分，因此 B 会读到 A 提交后的结果。

它不是 Java `synchronized`，多个使用同一数据库和同一锁协议的服务进程也能遵守这条数据库协调规则。反过来，绕过应用直接执行 SQL 的其他程序如果不遵守协议，就不受这套全局业务入口协调。

锁超时参数是 JPA hint，其支持和实际行为受提供者/数据库影响。不要把代码中的 10000 简化成“所有环境都保证正好 10 秒返回”。

代价很明确：修改不同电影也需要等待同一行锁。它方便保证实验中跨电影操作的正确性，但限制写吞吐量，不能称为高并发最优方案。

## 4. 已经串行化了，为什么还要 version

锁只覆盖数据库事务，不覆盖用户盯着表单思考的一分钟。

```text
12:00 A、B 都打开电影，version=3
12:01 A 保存成功，version 变为新值
12:02 B 才点击保存，携带的仍是 version=3
```

即便 B 的事务发生在 A 之后、没有同时持锁，B 的输入仍基于旧数据。服务端必须拒绝旧 version，而不是把锁当成“用户输入永远最新”。

实体有 `@Version`，服务层也显式比较表单旧值。在 JPA 同步时，提供者还会使用版本信息执行乐观并发检查。不要在业务里自己随意设置版本，也不要让用户决定新版本是多少。

## 5. version 和 revision 的区别

| 值 | 范围 | 用途 |
|---|---|---|
| `Movie.version` 等 | 单个对象 | 识别旧表单与对象并发变化 |
| `AppState.revision` | 整个应用共享数据 | 提醒浏览器重新读取 |

一次修改可能涉及很多电影，但 revision 只需表示“有一笔写事务完成”。它不是“电影总数”，也不是“每个字段修改次数”。当前 write 即使业务最终没有改变对象（例如删除匹配 0 条），成功走完仍会加一次 revision。

## 6. revision 为什么在同一事务中更新

如果先通知再提交，客户端可能收到变化信号却读不到新数据。如果电影提交了但通知记录失败，其他页面又可能一直不知道变化。

当前把数据修改和 revision 加一放在同一个事务中：成功一起提交，失败一起回滚。这让“已公布的 revision”与提交边界对应。

## 7. 自动同步其实是轮询

源码：[app.js 的 setInterval](<C:/develop/NOTE_UTP/StudyNote/5 Information Systems/Lab/Lab1/movie-lab/src/main/webapp/app.js>)。

```text
每 2 秒
→ 如果没登录或上一轮还没完成，就暂不执行
→ GET revision
→ 和页面保存的旧 revision 比较
→ 不同才刷新当前列表/详情
→ 保存新 revision
```

本项目没有实现 WebSocket 或 SSE，也不是服务器主动推送。约两秒是定时间隔，不是网络有延迟、后台标签被限速时仍保证两秒内刷新。

如果编辑弹窗打开，系统保留用户尚未保存的输入，显示“集合已变化”的提示。保存时再检查 version。不能自动拿新对象覆盖正在输入的表单，否则用户会丢失尚未提交的内容。

## 8. 怎么验证这些机制不是口头描述

历史 JUnit 测试用四个线程提交 12 次加奖任务，检查初始 1 是否变成 13。版本测试用旧 version 再保存，确认被拒绝。浏览器测试使用两个独立浏览器上下文，确认 A 创建/修改/删除之后 B 自动看到变化。

线程测试验证业务并发；双浏览器测试验证网络、会话和 UI 更新。两者互补。

## 检查题

1. 全局写锁能阻止用户用旧表单覆盖新数据吗？
2. revision 增长一次一定表示增加了一部电影吗？
3. 为什么浏览器不每两秒无条件覆盖编辑表单？

参考答案：不能，用户思考时间不属于持锁事务；不是，它表示完成了一次应用写事务；那样会破坏未保存输入，应保留输入并在提交时检查版本。
